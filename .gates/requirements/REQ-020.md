## 1. 需求分解

### 背景与问题

REQ-019 立项时撞上一个**门禁无法自举**的事实：把填好的需求清单 `git add` 后，
`git commit` 被 `req-guard check --staged` 硬拦，报

```
⛔ 拦截：无法确定本次改动属于哪份需求（仓库内有多份未归档清单，
   且没有任何已批清单声明这些路径）。 [Ambiguous]
  本次改动：（无受管路径）
```

四条实测复现（均可重跑，非代码走读推测）：

| # | 复现命令 | 实测结果 |
| --- | --- | --- |
| **1** | `git add .gates/requirements/REQ-019.md && req-guard check --staged` | 退出码 1，`[Ambiguous]`，「本次改动：**（无受管路径）**」 |
| **2** | `sh .gates/hooks/req-guard-touch-check.sh` | 退出码 0，报「✅ 变更范围合规」——**同一批改动，两个钩子结论相反** |
| **3** | `HOOK_REQ=REQ-019 req-guard check --staged` | 退出码 1，改报 `[StepNotApproved]`（REQ-019 三段未批）——**换了个理由，仍然拦** |
| **4** | 查 `.gates/audit/gate-audit.log` | `BLOCK-AMBIGUOUS` 在 2026-10-04 22:21、10-05 10:47、10-07 01:48、10-07 11:37、10-08 01:04 各有 1 条，均对应「提交新清单」——**不是新回归，是每次都要撞** |

根因链（`core/src/resolve.rs`，判定唯一真相）：

1. `.gates/requirements/**` 命中 `touch.exempt`，`judge` 剥除豁免后 `managed = []`；
2. `owned_by` 用 `managed` 反查已批清单的 `GATE:TOUCH` 声明 → 空集命中不到任何一份 → `H = ∅`；
3. `live.len() == 19 > 1` 且无 hint → 候选集为空 → **R8 → `Block(Ambiguous)`**。

一句话：**`touch.exempt` 的语义是「不需要 `GATE:TOUCH` 声明」，不是「不需要归属」**，
而 `judge` 里从来没有「受管路径为空 → 放行」这条规则（只有 `live.len() == 1` 的单需求退化分支）。
空集既不降级为全量（G4 明文要求），也没有放行出口，于是在多需求仓库里必然撞歧义。

三处既有证据表明「空集应放行」才是原意，实现只是漏了：

- `core/src/gate.rs` 的 `touch_exempt_patterns` 注释白纸黑字写着 `.gates/requirements/**`
  「**在任何清单被批准之前**它就得先写出来」，并点名后果「清单改动无法提交，
  AI 永远无法把填好的清单 commit 上去」——**作者预见并否决了这个死循环，但判定侧没跟上**；
- `core/src/gate.rs:752` 已备好文案「✅ 门禁放行：本次改动不涉及任何受管路径」，
  但它对应的 `Verdict::Pass { reqs: [] }` 在当前判定流下**不可达**（死代码）；
- `core/src/resolve.rs::audit_verdict` 已为 `Pass { reqs: [] }` 预留 `PASS no-managed-path`
  审计行——**审计侧早就等着这个裁决，判定侧却永远产不出它**。

由此形成的死循环是：清单要入库才能走三段审批，可未批清单自身的提交被拦；
`--no-verify` 也救不了，因为 CI 模板跑 `req-guard check --base origin/main`，
同样算出 `managed` 为空 → 同样 `Ambiguous` → **服务端也红**。

### 目标

- **G1** 剥除豁免后受管路径为空、且**本次确实带变更集**时，判定为放行，
  并在审计与输出上**显式标注**「未做任何归属判定」，不得与「三段已批准」混淆。
- **G2** 裸 `req-guard check`（无变更集的全局判定 / TUI 状态面板）**保持 `Ambiguous` 不变**：
  无变更集就无从归因，放行会把「能不能开工」变成永远「能」——这是漏拦，不是解堵。
- **G3** 内容冻结（R15）与「hint 指向不存在清单」（R3）**优先于**新的放行分支：
  放行只发生在「证据完好 + 选择合法 + 改动全在豁免区」三者同时成立时。
- **G4** 消除 `.gates/req-guard.yaml` 里与 `gate.rs` 事实相反的过时注释，
  使「哪些路径在豁免内」只有一个可读的真相。
- **G5** 修复后，本仓库自身能把 REQ-019（及后续任何新清单）正常提交入库——**自举验证**。

### 非目标

- **N1** 不改动 `touch.exempt` 的**条目**（只改注释）。收窄或扩张豁免集是独立议题，
  且 `gate.rs` 的 RUNTIME 注释已就 `ledger.md` 给出过一次「改回去 → 必然被绕开 → 改回来」的教训。
- **N2** 不动 `multi.mode` 的候选推导（`owned_by` / `hit_list` 语义逐字不变），
  避免 `touch --scope strict` 与门禁裁决在「这份改动属于谁」上产生第二处真相。
- **N3** 不引入分级档位（`trivial` / `light` / …）。那是 REQ-019 的范围；
  本需求只补上「空集怎么判」这一处前置缺口。
- **N4** 不改应急绕过窗口的判定顺序（`resolve` 里绕过先于变更集）。
- **N5** 不为豁免区引入新的完整性机制：清单正文仍由 `sum=` 冻结 + `hsum=` 头部摘要 +
  `doc_write_guard` 的 GATE 行校验三道承担，本需求不新增第四道。

## 2. 技术方案

### 总体思路

一句话：**豁免 = 不要求声明，也不要求归属**；把「受管路径为空」从「无从归因」里
单独拎出来判成放行，但只对**确实带变更集**的判定生效，裸 `check` 一字不改。

### 关键设计

#### 设计 1：为什么必须区分「有变更集但为空」与「根本没有变更集」

两者在 `judge` 眼里都是 `&[]`，但语义相反，判错就是漏拦：

| 情形 | 例子 | 正确裁决 | 判错的后果 |
| --- | --- | --- | --- |
| 有变更集，剥除豁免后为空 | `--staged` 只暂存 `.gates/requirements/REQ-019.md` | **放行** | 误拦 → 清单永远无法入库（现状） |
| 无变更集 | 裸 `req-guard check` / TUI 状态面板 | **`Ambiguous`** | 误放行 → 「能不能开工」永远答「能」，**漏拦** |
| 有变更集，但**取不到路径** | `--stdin` 的 payload 解析不出 `file_path` | **`Ambiguous`**（落回原判定） | 误放行 → AI 用解析不出路径的 payload 穿过 L1，**漏拦** |

前两行是立项时就识别的；**第三行是实施期发现的**，故本需求修订了一次（见边界节 B-01 / B-02）：
「空集 ⊆ 豁免区」这个推导只在**确实拿到了路径**的前提下成立 —— 空变更集不是「没东西可归属」，
而是「根本不知道改了什么」，后者必须 fail-closed。

裸 `check` 在单需求仓库下今天是**有意义的**：`owned_by` 走 `live.len() == 1` 退化分支，
把那一份（哪怕未批）作为候选去判三段，等价于「能不能开工」。若空集一律放行，
这条语义会被静默抹掉——**那是把门禁调松，不是解堵**。

因此 `judge` 需要一个显式形参承载这个区别。用两变体枚举而非布尔值：
`judge` 有约 10 处调用点（多为单测），布尔实参在调用点不可读
（`judge(&live, &paths, None, MultiMode::All, &ex(), true)` 无法自解释）。

```rust
/// 本次判定是否带变更集。
///
/// 区分「有变更集但剥除豁免后为空」与「根本没有变更集」：前者是真实的
/// 「改动全部落在 `touch.exempt` 豁免区」，必须放行；后者是裸 `req-guard check`
/// 与 TUI 状态面板的全局判定，无从归因 —— 放行会把「能不能开工」变成永远「能」。
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Changeset {
    /// 无变更集：全局判定（`PathSource::None`）。
    Absent,
    /// 有变更集（可能为空集，例如 `--staged` 时无暂存文件）。
    Provided,
}
```

#### 设计 2：R2b 的插入位置（顺序即语义）

`judge` 现有规则顺序为 R1 → R15 → R3 → 候选推导 → R11 → R12。R2b 插在 **R3 之后、
候选推导之前**，三处理由缺一不可：

| 约束 | 理由 |
| --- | --- |
| **在 R15 之后** | 「证据已被篡改」比「没审批」更严重，且与变更集正交。只改豁免区也不能豁免内容冻结 |
| **在 R3 之后** | hint 指向不存在的清单是**用户犯错**，不是「改动无需归属」。若 R2b 抢先，`HOOK_REQ=REQ-999` 会被静默放行，`UnknownSelection` 这条防呆失效 |
| **在候选推导之前** | 无 hint 时 `owned_by` 会先返回空并直接落进 R8。放在其后则 R2b 永远不可达 |

```rust
    // ── R2b 受管路径为空 → 放行（改动全部落在豁免区，无需归属） ──────────
    //
    // 为什么不是报错：`touch.exempt` 的语义是「这些路径不要求 `GATE:TOUCH` 声明」，
    // 而豁免区内根本没有可归属的对象。要求归属，等于要求「先有已批清单才能提交
    // 第一份清单」—— `gate.rs` 的 `touch_exempt_patterns` 注释已预见并否决了
    // 这个循环（「AI 永远无法把填好的清单 commit 上去」），但判定侧当时没跟上。
    //
    // 为什么只在 `Changeset::Provided` 下生效：`Absent` 是裸 `req-guard check` 与
    // TUI 状态面板，无变更集就无从归因 —— 放行会把「能不能开工」变成永远「能」。
    //
    // 为什么还要求「至少有一条非空路径」：**空变更集 ≠ 全豁免变更集**。
    // `PathSource::Stdin` 在 payload 里取不到 `file_path` 时返回空集（`collect_paths`
    // 的既定行为：「不是一次可识别的文件写操作」）。若此时也放行，AI 工具只要发一个
    // 解析不出路径的 payload，L1 hook 就会从「拦」变成「放行」——这正是本项目定义的
    // 最坏失效「看着在拦、其实没拦」。故空集必须落回原路径（多需求 → `Ambiguous`），
    // 保持 fail-closed。同一条约束也让 `--staged` 空暂存不产生「与裸 check 明细不一致」
    // 的存量感知差异（边界节 B-01 / B-02）。
    //
    // 可追溯性：放行**必须**携带 `note`，审计侧叠一条 `NOTE`，使之在台账上与
    // 「三段已批准」明确区分 —— 「看着在放行、其实没判」与「看着在拦、其实没拦」
    // 是同一类失效。
    let has_path = paths.iter().any(|p| !p.trim().is_empty());
    if has_path && managed.is_empty() && changeset == Changeset::Provided {
        return Verdict::Pass {
            reqs: vec![],
            note: Some("本次改动全部落在 touch.exempt 豁免区，未做任何归属判定".to_string()),
        };
    }
```

于是 R2b 的完整判据是**三条同时成立**（缺一即不放行）：

| # | 条件 | 防的是什么 |
| --- | --- | --- |
| ① | `changeset == Provided` | 裸 `check` 被当成「无改动」放行 → 「能不能开工」永远答「能」 |
| ② | `paths` 至少 1 条非空路径 | `--stdin` 取不到路径时放行 → AI 用解析不出路径的 payload 穿过 L1 |
| ③ | `managed.is_empty()` | 放行面大于豁免区 → 混合变更集被松口 |

#### 设计 3：调用点改造

| 调用点 | 传值 | 理由 |
| --- | --- | --- |
| `resolve` 正常路径（第 552 行） | `ctx.source != PathSource::None` 时 `Provided`，否则 `Absent` | 唯一需要按上下文取值的点 |
| `resolve` 的 R14 分支名消歧重判（第 567 行） | 同上 | 重判必须与原判同参，否则同一变更集两次裁决口径不同 |
| `resolve` 的 `live` 为空分支（第 542 行） | `Absent` | 该分支在 R1 就返回，`changeset` 不参与判定 |
| `decide`（第 462 行） | 形参透传 | `decide` 供薄壳与单测以显式路径驱动，调用方知道有没有变更集 |
| 单测 | 显式写出 | 每个用例的期望依赖它，不写默认值以免掩盖语义 |

#### 设计 4：审计与输出收口（不新增文案通道）

- `audit_verdict` 已处理 `Pass { reqs: [] }` → `PASS no-managed-path`（既有，无需改）；
- `note` 已有 `NOTE` 逐行落审计的通道（既有，无需改）；
- `gate.rs` 的 `verdict_to_gate` 对 `reqs` 为空已有文案
  「✅ 门禁放行：本次改动不涉及任何受管路径」（既有，本次才首次可达）。

**刻意不新增任何文案分支** —— 三处都是既有设施，改动集中在判定本身。

#### 设计 5：`.gates/req-guard.yaml` 注释订正（只改注释）

现状注释与代码事实相反：

```yaml
  # REQ-012 T9：`.gates/**` 通配已拆成具名清单。`.gates/req-guard.yaml` 与
  # `.gates/audit/ledger.md` **刻意不在豁免内** —— 它们是门禁配置与审批轨迹，
  # 放进豁免区等于允许 AI 自己把门禁调松。改它们须由 REQ-012 声明 + CI 漂移检测兜住。
```

而 `gate.rs` 的 `RUNTIME` 常量里 `.gates/audit/ledger.md` **就在豁免内**，
且 `gate.rs` 第 1448–1460 行有一段专门注释说明这是 REQ-012 实施期的**刻意修正**：
台账是工具在每次审批时自动追加的产物，移出豁免区等于「每次 approve 都让工作区变成
`NotDeclared`」，团队只会被迫 `--no-verify`。

**订正方向：改注释，不改条目。** 按注释去「修正」列表会让审批流程自锁，
而真正与注释相符的只有 `.gates/req-guard.yaml`（它确实不在豁免内，靠声明 + 漂移检测兜）。

### 涉及的文件与模块清单

见下方 `GATE:TOUCH` 块（精确到文件，未使用 `**` 通配——
`core/**` 会把本需求不涉及的模块一并圈进来，正是 REQ-012 反对的宽口径）。

### 兼容性、性能与安全影响

- **兼容性**：`judge` 是 `pub`，签名变化属破坏性变更；但全仓调用点均在 `resolve.rs` 内
  （`cli` / `tui` / `gui` 只用 `resolve` / `decide`），`decide` 亦同步透传，对外行为不变。
- **性能**：新增分支是常数时间，且在候选推导之前短路，只会更快。
- **安全**：放行面严格等于「改动集 ⊆ `touch.exempt`」。门禁配置
  （`.gates/req-guard.yaml`）不在豁免内，改它仍走完整判定；
  清单正文的完整性仍由 `sum=` / `hsum=` / `doc_write_guard` 三道承担（N5）。
- **一个必须点名的安全后果**：AI 现在可以提交 `.gates/drafts/**`、`.gates/hooks/**`
  与清单正文而无需任何清单批准。这与「豁免」的既有语义一致（REQ-012 T9 已就 hooks/ci/drafts
  作出同样取舍），不构成本需求新增的攻击面；但**必须**写进残留风险随 PR 披露。

### 风险点与回滚方案

| 风险 | 严重级 | 缓解 |
| --- | --- | --- |
| 空集放行被当成「门禁形同虚设」 | 中 | `note` + `NOTE` 审计行显式标注；放行面 = 豁免集，一行可查 |
| `Changeset::Absent` 漏传导致裸 `check` 误放行 | **高** | 单测 U-02 专门锁死；`decide` 不设默认值，逼调用点显式写 |
| 单需求仓库的 `live.len() == 1` 退化语义被绕过 | 中 | 单测 U-03 覆盖（该场景修复后由拦转放，属**预期变化**，须显式锁定而非默认继承） |
| `judge` 签名变动漏改调用点 | 低 | 编译器兜（非 `#[allow]` 位置全量报错）；`cargo clippy --workspace --all-targets` |

**回滚**：T1–T3 是同一处判定的三个面，整体 revert 即回到当前行为
（`Ambiguous`）；T6 的注释订正独立可 revert，无副作用。

### 端到端用例（编号 + 执行步骤）

- **E-01** 本仓库自举（T5）：`git add .gates/requirements/REQ-019.md` 且不暂存其他文件 →
  `req-guard check --staged` 退出码 **0**（现状为 1）
- **E-02** 同一次改动跑 `sh .gates/hooks/req-guard-touch-check.sh` → 退出码 0，
  与 E-01 结论一致（现状是两者相反，正是本次要消掉的裂缝）
- **E-03** `HOOK_REQ=REQ-019 req-guard check --staged` → 退出码 **0**
  （现状为 1 且报 `StepNotApproved`）；**R2b 在候选推导之前，故 hint 走到这里也不再判三段**
- **E-04** 裸 `req-guard check`（不暂存任何文件）→ 退出码 **1** 且含 `Ambiguous`，与修复前一致
- **E-05** `git commit` 全流程：暂存 REQ-019 后提交成功，`pre-commit` 两个钩子均放行

### 边界 / 异常 / 并发场景

- **B-01** `--staged` 无任何暂存文件（`HOOK_STAGED_FILES` 为空）→ **不得**放行，落回既有判定
  （多需求 → `Block(Ambiguous)`，单需求 → R7 退化分支）。
  **修订说明（本次 amend 的唯一原因）**：初版写的是「→ `Pass`」，实施时发现它让
  `--stdin` 解析不出 `file_path` 的返回空集也被判放行 —— 而该场景修复前是**拦**的。
  空变更集与「全豁免变更集」是两件事：后者确实没东西可归属，前者是**根本不知道改了什么**。
  同理，B-01 若按初版实现还会破坏 `gui::app` 的「存量项目零感知」用例
  （空暂存 + `--staged` 的明细会与裸 `check` 不一致）
- **B-02** 变更集只含空串与空白路径 → 与 B-01 同路径（均按「取不到路径」处理，不得放行），
  且不得 panic —— `trim()` 后的空集不得被当成「豁免区改动」蒙混过关
- **B-03** 变更集只含 `.gates/req-guard.yaml`（**不在**豁免内）→ 走完整判定，
  不得因本需求而放行（门禁配置不可由豁免区旁路）
- **B-04** 变更集只含 `.gates/audit/ledger.md`（**在**豁免内）→ `Pass`
  （与 `gate.rs` RUNTIME 的既有决定一致，审批台账必须可提交）
- **B-05** `multi.mode: all` 下 R2b 是否生效 → **生效**。
  保守档的语义是「候选恒为全部清单」，其前提是**有候选可判**；
  改动全在豁免区时归属问题根本不存在，强行要求全部清单三段全批，
  等于让一份起草中的需求阻断一次纯文档提交 —— 正是 `All` 档自述的「互锁制度化」

### 回归范围与影响面

- `core/src/resolve.rs` 全部既有用例（约 30 条）必须全绿；
- `req-guard ac check` 对全部未归档清单零 Error；
- `scripts/verify_gate.py` 与 `packaging/scripts/selfcheck.{sh,ps1}` 的自检项不回归；
- `req-guard install --verify` 仍 PASS。

### 验收门槛（全部可机械判定）

- **放行路径与拒绝路径各有用例**：U-01/U-03 锁放行，U-02/U-04/U-05/U-06/U-08 锁拒绝；
  只有放行用例等于没测（与 `scripts/mutation-manifest.txt` 的收录标准一致）
- **fail-closed 边界不得被放行分支吃掉**：U-08（空变更集 / 空白路径）与 U-02（无变更集）
  是本需求引入放行分支后**新出现**的两条漏拦路径，缺任一条即视为不合格
- **E-01 / E-03 由红转绿**，E-04 保持红 —— 三者缺一即证明修偏了方向
- **不新增依赖**：`core/Cargo.toml` 保持零依赖
- **零新增 `unwrap()`**：用户输入路径的失败一律走 `GateError::Validation`
- **签名变动无默认值兜底**：`decide` 的 `changeset` 形参不设默认，逼每个调用点表态

### 残留风险（必须随 PR 一起披露）

1. **豁免区改动现在免于归属判定**：AI 可提交 `.gates/drafts/**`、`.gates/hooks/**`、
   `.gates/ci/**` 与清单正文而无需任何清单批准。这与 REQ-012 T9 的既有取舍同源，
   但**后果此前被 `Ambiguous` 无意间挡住了**，本需求等于把这道意外的墙换成明示的豁免，
   需要 CODEOWNERS 覆盖 `.gates/hooks/**` 才能真正兜住。
2. **放行不校验豁免区内容**：只认路径不认内容。清单正文靠 `sum=` / `hsum=` /
   `doc_write_guard` 三道，hooks / ci 两项目前**没有任何内容校验**（`install --verify`
   只做就位检查），这是既有缺口，本需求未补。
3. **`Changeset::Absent` 的判断依赖调用点自觉**：编译器只在**漏传**时报错，
   传错值（该 `Absent` 传 `Provided`）不报错。缓解是 U-02 与 E-04，不是类型系统。
4. **单需求仓库行为变化**：U-03 场景由拦转放。存量单需求仓库里「只改清单也要先批准」
   的隐式保护消失，属预期变化，需在 CHANGELOG 明示。
