## 1. 需求分解

### 背景与问题

GUI 正文由 `gui/src/markdown.rs` 的**自研零依赖渲染器**画出（不引 crate 的理由见
`docs/设计/UI架构细化方案.md` §4.4）。审核人实测报了两个现象，均可稳定复现：

1. **单元格里的竖线被当成列分隔符**。AI 写的清单里，"字段用 `a|b|c` 分隔"这类说明
   极常见，而表格拆列是 `t.split('|')` —— 一行

   ```text
   | 编号 | 子任务 | 预估工时 |
   | --- | --- | --- |
   | T1 | 变异清单文件格式（`file|anchor|replacement|test-filter|理由`） | 2h |
   ```

   会被切成 8 格。列数取"表头与数据行的最大格数"，于是整表变成 8 列：子任务被拆成
   5 段分列显示、`2h` 被甩到最后一列，表头与数据完全对不上。GFM 本来就规定反引号
   代码段内与转义过的 `\|` 都是**内容**，拆列这一步漏了这条规则。

2. **表格宽度由内容决定，于是"忽宽忽窄"**。列宽上限写死 300px、整表再按内容收缩：
   两列短表只有 200px 宽（贴左、右边缘悬在半空），三列长表顶到面板边缘还要出横向
   滚动条；单元格每行能显示的字数也跟着变（300px 处的折行与段落按版心折行不是一回事）。
   同一篇正文里段落一律按版心宽、表格却忽宽忽窄，观感就是"有的行字多、有的行字少"。

   顺带查明一处相邻隐患：列表项曾用 `ui.horizontal_wrapped` 排版，wrap 布局会把
   "这一行还剩多少宽度"掺进折行与对齐（egui 的 `Label` 在 wrap 布局里还会按首行缩进
   重排）。实测当前内容下尚未触发（两项总是各占一行），但一旦两项排到同一行，第二项
   的折行宽度就变成"版心 − 上一项宽度" —— 与现象 2 同源，且更难归因。

### 目标

- **G1** 拆列只在**真的分列**时发生：反引号代码段内的竖线、转义过的 `\|` 都算内容；
  判定按 GFM（代码段**等长**反引号成对闭合；不成对仍是普通字符，否则整行并成一格、
  后面几列静默丢失）。
- **G2** 表格宽度由**版心宽度**决定，不由内容决定：表与正文同宽、右边缘对齐；
  放不下时压缩，且压到下限的短列保住完整内容、由长列折行承担。
- **G3** 宽度基准唯一：段落 / 列表 / 标题 / 表格共用同一栏宽度；列表一项一行，
  不给 wrap 布局掺入折行宽度的自由度。
- **G4** 可判决：两条修复各有一条"在旧实现下必然失败"的自动化断言。

### 非目标

- **N1** 不做完整 CommonMark/GFM 表格解析（不处理跨行单元格、不做转义重排等边角）。
- **N2** 不改解析层对 `\|` 的解释归属：拆列只判定"不切"，反斜杠仍由 `parse_inlines`
  解释一次（GFM 里转义在代码段内不生效，两处各解释一遍迟早对不上）。
- **N3** 不动 `core` 的清单校验（`section.rs` 的分隔行判定与本缺陷无关，不受影响）。
- **N4** 不改清单格式，不要求存量清单迁移。
- **N5** 不修代码块（`pre`）不折行的既有行为：折行会破坏缩进层级，是刻意选择。

## 2. 技术方案

### 总体思路

**拆列按 GFM 判竖线；排版按"版心"一个宽度基准分配列宽。**

### 关键设计

1. **`cells_of` 改成单遍状态机**（T1）：`\` 带上下一个字符整体入格（`|` 因此不切）；
   反引号取连续长度 `n` 并**向前找等长闭合**，找到则整段原样入格、找不到则按普通字符
   处理。单元格原文保留反斜杠，交给 `parse_inlines` 解释（N2）。
   为什么不"先粗切再合并"：合并需要在行内层知道代码段边界，两处各判一次必然漂。

2. **列宽由版心分配**（T2/T3）：先按 `f32::INFINITY` 排一遍每格得到**自然宽**
   （表头是粗体，必须按粗体量 —— 细体量出来的宽度偏小，标题会被挤出列外），
   `distribute` 再把自然宽摊到 `ui.available_width() - 列间距`：
   - 合计 ≤ 目标 → 按比例放大到**刚好填满**（表与正文同宽、右边缘对齐）；
   - 合计 > 目标 → 每轮从**原始自然宽**重新按比例缩放，压到 `MIN_COL_W` 的列退出、
     预算在还能压的列里重分（**短列先保内容，长列去折行**）；
   - 连下限都分不完 → 每列取下限，总宽超版心，交横向滚动条（不把字挤成竖条）。
   定稿阶段只用**放得下的自然宽那份**排版，放不下的才按列宽折行重排第二遍
   （`Painter::layout_job` 走 egui 的 galley 缓存，第二遍不是白排）。
   为什么不引 `egui::Grid`：Grid 最后一列吃掉剩余宽度，且没法给列设软上限
   （原注释里已记过这个坑，见 `table` 的文档注释）。

3. **列表一项一行**（T4）：`ui.horizontal_top` 取代 `ui.horizontal_wrapped`，
   符号与正文顶端对齐；有序/无序缩进统一为 `LIST_INDENT_W`（此前 20px / 16px 不一致）。

4. **离屏测试装字体**（T5）：`Context::default()` 里没有可用的中文字形，长出来的
   galley 尺寸全为 0，几何断言只会拿到 NaN —— 也就是既有离屏测试只能验"有没有画东西"，
   验不了"画在哪、画多宽"。抽出 `fonts::definitions()` 供窗口启动与测试共用一份。

### 兼容性、性能与安全影响

- **兼容性**：解析出的表格 AST 列数会变（这正是修复点）；其余块级结构与行内解析
  行为不变，由 T6 的既有行为用例与既有 23 条 markdown 单测兜底。
- **性能**：每帧每格多一次"不折行"排版（量自然宽）。`Painter::layout_job` 走 egui 的
  galley 缓存，同样的 job 每帧只真排一次，增量是一次 job 构造 + 哈希；清单表格
  规模在几十行量级，可忽略。
- **安全**：方向不变 —— 渲染器仍**永不激活链接、永不加载图片**（模块注释的取舍未动）。

### 风险点与回滚方案

- **风险 1（中）**：转义与代码段的边界写法判断错，把本该切列的地方并成一格 →
  后面几列静默丢失（"看不见"比"难看"更坏）。缓解：未闭合反引号**不**当代码段
  （fail-closed 到"照常切列"）+ 该场景单测。
- **风险 2（中）**：`distribute` 的压缩循环把总宽顶出版心 → 表格溢出。
  缓解：`distribute` 是纯函数，四种情形各有单测（填满 / 等比压缩 / 短列保底 / 全下限）。
- **风险 3（低）**：表格一律填满版心，短表列变宽、留白变多（观感变化）。
  这是为"宽度一致"刻意选的取舍，写进 `distribute` 的文档注释。
- **回滚**：`git revert` 即可，无数据迁移、无格式变更。

### 边界 / 异常场景

- **B1** 代码段用不等长反引号包裹（`` `a``b` ``）→ 段内不因 `` `` `` 提前闭合。
- **B2** 行内只有未闭合反引号 → 按普通字符，仍切列。
- **B3** 列多且面板窄到连列宽下限都分不完 → 横向滚动条出现，不 panic、不竖条。
- **B4** 空单元格 / 缺失单元格（数据行比表头少）→ 列数仍按最大格数，不 panic。
- **B5** 右对齐列（`---:`）在填满版心后 → 数值仍与表头右边缘对齐。

### AC-002
- Given: 清单含一行表格，其单元格为 `` `a|b` `` 与 `c\|d`
