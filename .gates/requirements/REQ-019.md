## 1. 需求分解

### 背景与问题

门禁现在只有一档：任何改动都要走「需求分解 → 技术方案 → 测试计划」三段，  
逐段由人类在真实终端批准。三处成本都可以从仓库自身数据里量出来，不是主观感受：

1. **单需求清单过重**。`.gates/requirements/` 里 18 份清单，行数中位数约 330 行，  
   REQ-006 达 876 行、53 条验收标准，其中 56% 是三段式验收条目。清单成本与  
   改动大小不成比例——改一个错别字和改一个并发裁决器走同一条路。
2. **交互次数有硬下限**。`auth.level: 3` 下审批凭据是**一次性范围票据**  
   （`core/src/token.rs`，绑定 `<需求ID>:<步骤>`，用后即废），因此三段批准  
   必然对应三次人类在场交互，无法靠"打包"省掉两次。台账里每份需求的  
   `APPROVE` 都是三条独立记录，与 `strict_order` 的逐段推进一一对应。
3. **续改重复收费**。`.gates/audit/ledger.md` 里 REQ-004 / 006 / 010 都有  
   `AMEND` 与紧随其后的 `APPROVE` 成对出现，REQ-006 的 testplan 改了两轮、  
   还伴随两次 `RESEAL`。已批准清单改一行也要重跑内容校验、重签摘要绑定。

于是形成一个自我实现的死循环：流程对小事太重 → 小事被迫走 `bypass`  
→ README 第 96-97 行又把 bypass 定义为「流程失控信号」→ 指标与现实互相打脸，  
门禁退化成表演。**这不是执行纪律问题，是档位缺失**：只有重流程和绕过两条路，  
没有第三条。

### 目标

- **G1** 引入四档（`trivial` / `light` / `standard` / `critical`），档位由  
  **改动集派生**（有效改动行数 + 路径敏感度），AI 不能自行选择。
- **G2** 「有效改动行数」剔除注释行与空行，使**只改注释/空行的变更自然落到  
  免审档**（有效行 0），无需额外规则即可覆盖 typo 类改动。
- **G3** 高危路径配置化（支持目录前缀与 glob），且**门禁自身源码恒为最高档、  
  不可通过配置降级**。
- **G4** 轻档走一条命令批三段，但**审批记录一条不少**（三段独立留痕）。
- **G5** 轻档验收标准选填；写了就必须全量合规。
- **G6** 三层（L1 hook / L2 pre-commit / L3 CI）用同一份判定函数，  
  且各自的输入边界写进文档（谁能看全量、谁只能看局部）。
- **G7** 阈值由本仓历史变更集**回放校准**，不允许拍脑袋写死。

### 非目标

- **N1** 本需求**不做**「已批准清单的小幅 amend 走 delta 免重审」（前一轮分析中的  
  方案 D）。理由：它直接削弱 REQ-002 建立的内容摘要绑定（`sum=`），而摘要绑定  
  是「批准后偷改」的唯一检测手段；这类改动必须自带判决性实验证明不回归，  
  应当另起一份 REQ 单独评审，不与档位机制捆绑。
- **N2** 不改三段步骤名与 `pending → approved/rejected` 状态机，不引入「升档」新状态。  
  升档表现为**同一份已批准清单被重新批准到更高档**（见技术方案 §2.5）。
- **N3** **不为规避 doc-guard 的检查而另立平行键**。档位直接用 frontmatter 既有的  
  `tier` 键（取值扩为四档），不让门禁的表达需求去扭曲数据模型。
- **N4** 不做阈值自适应、不做按团队学习的自动调参。
- **N5** 不在 req-guard 仓内代改 doc-guard（FRS 族定义属 doc-guard 仓），  
  但**必须在其发版后才能收口**，见技术方案 §2.9 的跨仓前置依赖。

## 2. 技术方案

### 总体思路

**把「这份改动有多重」变成一个可复算的函数，三层共用它。**

`classify(changes, config) -> (Tier, reasons)` 是纯函数：入参是变更集的有效行  
明细与路径，输出是档位与**人类可读的理由**（命中了哪条 glob、每个文件多少有效行、  
命中的是内建锁定项还是配置项）。档位最终取

```text
final_tier = max(声明档 frontmatter.tier, 派生档 classify(...))
```

声明只能往上抬，不能往下压；而派生值由 L3 的完整变更集算出，是权威。


### 关键设计

#### 1. 有效改动行：为什么不能直接数 diff 行

`git diff --numstat` 给出的是物理增删行。把「加 120 行注释」和「加 120 行逻辑」  
算成同一个数，分级就失去意义——这是 G2 的落点。但**按 diff 行逐行判注释是错的**：  
`-U0` 的 diff 只含变更行、不含上下文，一个跨 hunk 的块注释（开头 `/*` 在未改动的  
上下文里，结尾 `*/` 在变更行里）无法从 diff 本身判定。

因此采用**按文件全量重建**：

1. 解析 `git diff -U0 --no-color` 的 hunk 头 `@@ -a,b +c,d @@`，得到每个新增行的  
   **新文件行号**、每个删除行的**旧文件行号**（两侧行号恰好对应两侧全文）；
2. 对每个文件，按**变更后**全文（`git show :<path>`，pre-commit）或  
   **base 侧**全文（`git show <base>:<path>`，CI）跑一遍注释状态机，得到该版本的  
   「哪些行是注释/空行」集合；
3. 用行号过滤：新增行按新侧集合过滤，删除行按旧侧集合过滤；
4. `effective = 有效新增 + 有效删除`。删除行必须计入——删掉一段校验代码  
   和加一段同样重。

注释语法按扩展名映射：`rs` → `//` 与 `/* */`（含 `///` `//!`）、`sh`/`ps1`/`yml`/`py` → `#`、  
`md`/`txt` → 不剔除（文档的每一行都是内容）、`json` → 无注释语法。  
**未知扩展名一律不剔除**（等于全算）——这是 fail-closed 方向：认不出来时倾向高估，  
低估才是门禁失效。

这个口径使「只改注释、只加空行」的变更有效行为 0，自动落进免审档，  
不需要为「注释改动」单开一条规则。

#### 2. 路径敏感度：可配置高危 + 不可配置锁定

| 表              | 来源                                           | 语义                              | 可否被配置改 |
| -------------- | -------------------------------------------- | ------------------------------- | ------ |
| `locked_paths` | **core 内建常量**                                | 恒为 `critical`                   | 否      |
| `risky_paths`  | `.gates/req-guard.yaml` 的 `tier.risky_paths` | 至少 `standard`（跳过 light/trivial） | 是，可增可删 |
| —              | 其余                                           | 交由行数档决定                         | —      |

匹配复用 `core/src/touch.rs` 里的 `glob_match`（`touch.rs:414`）：`**` 跨层级、  
`*` 单层、精确文件名，另接受目录前缀写法（`core/src/`）并按向下递归归一，  
降低配置门槛，且**与变更范围契约用同一份 glob 语义**——判定逻辑只有一份是本仓  
的架构前提（见 `core/src/lib.rs`）。

「门禁源码默认最高档不可修改」的实现口径必须**报错而不是忽略**：  
配置里出现 `locked_paths` 键、或 `risky_paths` 试图与内建锁定项语义冲突时，  
直接 `GateError::Validation` 并在消息里点名冲突路径。静默忽略会让维护者以为  
降级生效了——那是「看着在拦、其实没拦」的同族失效。

本仓初始化时把 `core/src/**`、`cli/src/**`、`gui/src/**`、`tui/src/**`、  
`scripts/**`、`templates/**`、`.gates/**` 放进 `risky_paths`；  
内建 `locked_paths` 至少覆盖 `core/src/**`、`templates/hooks/**`、  
`templates/ci/**`、`.gates/req-guard.yaml`（判定逻辑与拦截脚本本身）。

#### 3. 档位与阈值

| 档位         | 判定（取最高者）                                                                           | 审批形态                          | AC  |
| ---------- | ---------------------------------------------------------------------------------- | ----------------------------- | --- |
| `trivial`  | 有效行 ≤ `trivial_max_lines`（默认 5）且未命中 risky/locked                                   | 免审（免建清单；已建清单则只留 audit 行）      | 不要求 |
| `light`    | 有效行 ≤ `light_max_lines`（默认 80）且**未命中 risky/locked**（risky 命中即至少 `standard`，见 §2.2） | `approve --all-steps`（一条命令三段） | 选填  |
| `standard` | 其余                                                                                 | 三段逐段批准                        | 必填  |
| `critical` | 命中 `locked_paths`                                                                  | 三段逐段批准 + 附加检查                 | 必填  |

阈值默认 5 / 80 是**待校准的初值，不是结论**。T9 的 `calibrate_tier.py` 用  
REQ-001..REQ-018 的真实 diff 回放，输出各档分布；G7 要求把回放结果与阈值一起提交，  
若分布不合理则改阈值（改阈值不改口径）。

#### 4. 两阶段定档与升档

档位在**建清单时**无法知道（那时还没有 diff），在**提交时**才知道。所以：

- **声明阶段**（建清单 / 批准）：frontmatter 写 `tier: light`  
  （复用既有 `tier` 键，取值扩为四档）。缺省或非法值 → 取 `standard`  
  （保守，存量 18 份清单全部写着 `tier: standard`，零行为变化）。
- **裁决阶段**（pre-commit / CI）：按实际变更集算派生档。  
  `派生档 ≤ 声明档` → 放行；`派生档 > 声明档` → 报 `TierEscalation`，  
  要求把清单按更高档**重新批准**。

「重新批准更高档」在现有状态机里就是已有语义：轻档补 `standard` 差额 =  
再执行两次分段 `approve`；`standard → critical` = 走一遍 critical 的附加检查。  
因此**不需要新状态、不需要新转移**（N2 得以成立）。

#### 5. 轻档一条命令批三段

`req-guard approve <ID> --all-steps`，四条硬约束：

1. **原子性**：三段任一段校验失败（实质正文为空 / AC 不合格 / `source_refs` 为空）  
   → **整体拒绝，不留部分批准**。「批了两段」的状态比「一段没批」更危险。
2. **留痕不减**：仍写三条 `APPROVE` 台账行，各自带 `sum=`、`updated=`、`sig=`，  
   `channel=quick`。quick 省的是**交互次数**，不是记录。清单的 `GATE:STEP`  
   标记行 schema 不变（不新增字段）。
3. **凭据不放宽**：`auth.level: 3` 下 `--all-steps` 需要一张 scope 匹配  
   `<需求ID>:*` 的**通配票据**，且这张票据**只允许消费一次**（批三段算一次）。  
   精确 scope 票据不得用于 `--all-steps`；通配票据不得用于分步批准。  
   即：省掉了两次交互，没有省掉「人类在场」与「不可重放」。
4. **实质正文不放松**：第 3 段虽免 AC，但仍要求实质正文非空  
   （`section.rs` 的 `EmptySection` 判定继续生效），轻档至少要写  
   「改了什么 + 怎么自测」。

`strict_order` 在此场景是**显式豁免**（同批三段），豁免事实进台账。

#### 6. 轻档 AC 选填的准确口径

「选填」只放松两条：**A1**（无 `GATE:AC` 标记块）与 **A8**（块内 0 条目）  
在轻档下降级为提示；**A2–A7、A9–A12 一律不放松**——写了就必须格式合规。  
`standard` / `critical` 档的 A1/A8 仍是 error。

残余风险（明确披露）：档位来自 frontmatter，AI 可以把 `tier` 写小来逃避 AC。  
但两处收口：① 派生档由 CI 复算，逃逸只在 CI 之前有效；② 即使 AC 被逃逸，  
三段实质正文判定仍在，一条命令批三段**不可能批出一份三段空话的清单**。  
另注：`tier` 是 doc-guard FRS007 校验的字段，AI 写非法值（如 `urgent`）会同时被  
两侧判为非法——**枚举本身也参与防伪**，不能靠编一个值蒙混过去。

#### 7. 三层输入边界（为什么 L1 只能取下界）

| 层                    | 可见信息                               | 档位来源                  | 定位                            |
| -------------------- | ---------------------------------- | --------------------- | ----------------------------- |
| L1 `hook-check`      | 单次 Write/Edit 的 payload 内容 + 清单声明档 | `max(声明, 本次写入有效行)`    | **下界，乐观放行**；输出明示「最终以 CI 复算为准」 |
| L2 pre-commit        | 索引内变更集（看不见未暂存改动）                   | `max(声明, staged 有效行)` | 下界                            |
| L3 CI `check --base` | base...HEAD 完整变更集                  | `max(声明, 全量有效行)`      | **权威**                        |
| **前置（三层之上）**         | 剥除 `touch.exempt` 后是否为空            | 空 → **不走定档**，直接放行     | REQ-020 R2b，见 §2.10           |

L1 拿不到整体 diff 是物理事实（`hook-check` 只解析 PreToolUse 的 stdin JSON，  
`core/src/json.rs`）。把它写成文档里的显式契约，比留一层看起来能拦其实拦不住的  
假象要好：L1 放开、CI 兜住，且两层输出都带档位与理由，人能看出分歧来源。

**R2b 是三层之上的公共前置**：剥除豁免后为空的变更集在 L1 / L2 / L3 都不进入定档。  
这条必须逐层一致 —— 只要有一层不做短路，就会出现「本机放行、CI 要求批方案」  
这类无法解释的分歧（REQ-020 之前 `check --staged` 与 `touch-check` 结论相反的  
裂缝就是同一类问题）。

#### 8. 输出必须带理由

`req-guard tier check [--base <ref>]`（新命令）与 `check` 的拦截消息都要输出：  
最终档位、每文件有效行明细、命中的 glob、声明档 vs 派生档。  
理由可复算是这套机制能被人工复核的前提——否则「AI 少走流程」又变成一个  
无法质疑的黑箱。

#### 9. 为什么用 `tier` 而不另立键（跨仓契约）

档位与 doc-guard 的 `tier` 是**同一个概念的两个视角**：doc-guard 用它决定  
文档的关键度与复审节奏，req-guard 用它决定审批路径的重量。合并后两者不允许背离——  
`tier: critical` 的文档必然走最重的审批路径，这是一条值得要的约束。

**不另立平行键的工程理由**（原方案被否的原因）：

1. `core/src/specmeta.rs` 的模块注释明确写着「真正需要共享的是**字段名与取值枚举**，  
   不是代码」。平行键恰好违背它声明的契约，等于把一份规格复制成两份，  
   而 `section.rs` 里已经因为同类问题写过红线（"副本等于给文档漂移开一个口子"）。
2. 一个概念两个键会产生**合法但荒谬的状态**（`tier: critical` + `gate_tier: light`），  
   取高还是取低都要靠 `max()` 在两套词汇上定义——这是 bug 工厂。
3. 平行键对 doc-guard 是**未知字段、被静默忽略**。而 README:154-156 已经把这种  
   失效模式点名过：「`source_refs: []` 在声明侧留空，在 doc-guard 侧完全静默，  
   规格看似接入时效治理、实则永远不会被判过期」。**响亮的红优于沉默的分歧**。

**doc-guard 侧的改动范围（已核实行号）**：

- `crates/doc-guard-core/src/rules/freshness.rs:422` 的  
  `const TIERS: [&str; 2] = ["critical", "standard"]` 扩为四个值（一行）；
- FRS007 的报错文案由 `TIERS.join("/")` 生成（`freshness.rs:462`），随之自动更新；
- **规则行为等价**：全仓只有 `tier == critical` 会触发额外约束  
  （FRS005 `freshness.rs:326/352`、时效节奏 `freshness.rs:116`），  
  其余取值一律按「非 critical」处理。新增的 `light` / `trivial` 因此  
  在 doc-guard 侧不改变任何一条判定结果。

**依赖顺序**：doc-guard 先发版（枚举扩展）→ 本仓再启用四档。反序的失败态是  
**响亮的**：旧版 doc-guard 对 `tier: light` 报 FRS007「tier 非法」，  
文案自带可用取值清单，一眼可定位；不存在"配置生效但无人发现"的静默态。  
本仓存量清单全部是 `tier: standard`，新旧枚举都合法，因此**不依赖发版顺序**即可保持兼容。

#### 10. 定档与 R2b 的先后：豁免区改动不参与定档

REQ-020（已落地，`e9a34ed`）在 `judge` 里新增 **R2b**：改动集整体落在 `touch.exempt`  
豁免区时**直接放行**，位置在**候选推导之前**。由此产生一条必须在本需求里写死的  
先后关系 —— 不写的话，实施期有两个可选落点（定档在内 / 定档在外），选错就是  
「流程与改动不匹配」这个本需求要解决的反面：

| 顺序                      | 结论                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------- |
| R2b **先于**定档（**本需求采用**） | 豁免区改动不参与定档、不消耗档位；定档只对「剥除豁免后仍有受管路径」的变更集生效                                                     |
| 定档先于 R2b（**否决**）        | 清单正文 / 草稿 / `target/**` / `Cargo.lock` 会被算进有效行，推高档位 —— 提交一份新清单可能因此落到 `critical`，正是 G1 要消除的错配 |

据此三条实施细则：

1. **定档函数的入参是 `managed`（剥除豁免后的路径集），不是 `paths`**。  
   `classify` 不得自己再读一次 `touch.exempt` —— 豁免集单源（REQ-005 G3），  
   两处各剥一次必然漂移。
2. 这与 **G2** 是两条不同的路，不得混为一谈：G2 是「算了之后判为 0 有效行」  
   （只改注释/空行 → `trivial`），R2b 是「**根本不进入计算**」。  
   两者都导向免审，但留痕不同：G2 在输出里留下档位与理由（§2.8），  
   R2b 在审计里留下 `PASS no-managed-path`（REQ-020）。
3. L1 / L2 / L3 **三层都在 R2b 之后**（见 §2.7 的表补充一行）。  
   `hook-check` 尤其要注意：单次 Write 的 payload 路径常常就是  
   `.gates/requirements/REQ-xxx.md`，若 L1 不做 R2b 短路，AI 填清单正文  
   会被自己的档位机制要求先批方案 —— 与 REQ-020 修掉的死循环同源。

### 兼容性、性能与安全影响

- **兼容性**：无声明时行为逐字不变；存量清单零迁移；`install --verify` 的既有  
  体检项（`gate.rs:1571` 起）全部保留。
- **性能**：`tier check` 需要一次 `git diff -U0` + 每个变更文件两次 `git show`。  
  变更文件通常个位数、`git show` 走索引缓存；CI 侧对全量变更集一次性计算，  
  不引入新依赖（仍是纯 Rust 标准库，与「零外部依赖」不冲突）。
- **安全**：档位机制**削弱**的是流程强度而非密码学强度——`sig` 仍是公开可复算的  
  派生值（README 已披露），`--all-steps` 的通配票据仍是一次性、仍需真实 TTY。  
  通配 scope 是新的凭据形态，须明确限定只对 `--all-steps` 生效。

### 风险点与回滚方案

| 风险                                          | 等级    | 缓解                                                         |
| ------------------------------------------- | ----- | ---------------------------------------------------------- |
| 有效行口径实现错（块注释跨 hunk、字符串里的 `//`）              | **高** | 按文件全量重建 + T2 专项单测（`"//"` 在字符串内的反例必须测到）                     |
| 阈值拍脑袋导致轻档被滥用                                | **高** | T9 回放校准；输出理由供人工复核；`check` 记录每次档位便于事后统计                     |

| `docs/**` 改动量巨大（REQ-006 本身 876 行）           | 低     | 文档本就是最高频改动，误判为 light 代价低；`docs/**` 不进 risky                |

回滚：`tier` 配置段全部置空 → 派生档不生效，判定退回现行三段语义

（`standard` 在新旧枚举下都合法，回滚不需要再改任何清单）。新增命令与模块  
保留但不被调用，无需回滚二进制。

### 单元测试用例（编号 + 断言点）

**有效行口径（T2）**

- **U-01** Rust 文件新增 10 行 `//` 注释 → 有效新增 0（**本需求的地基用例**，  
  必须证明"剔除注释"真的发生，而不是恒等于 numstat）
- **U-02** 块注释跨 hunk：`/*` 在未改动上下文、`*/` 在变更行 → 该行被正确剔除；  
  块内**含代码**的那一行仍计入
- **U-03** 新增 3 行代码 + 5 行注释 → 有效新增 3
- **U-04** 删除 4 行注释 → 有效删除 0；删除 4 行代码 → 有效删除 4  
  （**必须构造"只删代码"的反例**，防止把删除侧整体当 0）
- **U-05** 字符串字面量里的 `//`（如 `"https://x"`）→ 计入有效行，不被误剔
- **U-06** `.md` 新增 20 行 → 有效 20（文档不剔除）
- **U-07** 未知扩展名（如 `.xyz`）新增 10 行 → 有效 10（fail-closed，不剔除）

### 端到端用例（编号 + 执行步骤）

- **E-01** 在临时仓库造一份 `tier: light` 的清单并批准 → 提交 3 行文档改动：  
  `check --staged` 输出 `tier=trivial` 放行，台账无新 `APPROVE`
- **E-02** 同一仓库提交 `gui/src` 内 3 行代码 → 报升档为 `standard` 并给出补救命令
- **E-03** 补齐两次分段 `approve` 后重跑 `check --base` → 放行，  
  台账新增 2 条 `APPROVE`（前一条 quick 记录仍在）
- **E-04** `approve --all-steps` 中途 Ctrl-C → 清单无任何段被批准（原子性）
- **E-05** `install --verify` 在启用 tier 配置的仓库 → 全项通过（既有体检不回归）

### 边界 / 异常 / 并发场景

- **B-01** 空变更集 → **不得**按「有效行 0 → `trivial`」放行，落回既有判定  
  （多需求 → `Ambiguous`；单需求 → 退化到唯一清单）。  
  **修订说明**：初版写的是「档位 `trivial`，`check` 退出码 0（不误拦空提交）」，  
  与 REQ-020 冲突 —— R2b 要求 `paths` 至少含 1 条非空路径才放行，  
  因为 `--stdin` 解析不出 `file_path` 时也返回空集，那时放行等于让 AI 用  
  一个解析不出路径的 payload 穿过 L1。「有效行 0」与「根本不知道改了什么」  
  是两件事，后者必须 fail-closed。**「空提交」这个场景本身不存在**：  
  `git commit` 在无暂存文件时根本不会触发 pre-commit
- **B-07** 变更集整体落在 `touch.exempt` 内（例如只暂存  
  `.gates/requirements/REQ-004.md`）→ **不参与定档**，按 §2.10 走 R2b 放行；  
  审计记 `PASS no-managed-path`，**不得**出现档位输出（出现即说明定档插错了位置）
- **B-02** 新增文件（无旧侧内容）→ 删除侧为空，不 panic；有效行按新侧全量计
- **B-03** 二进制文件变更 → 该文件按 1 有效行计（无法判注释）
- **B-04** `tier` 段 YAML 语法错误 → `GateError::Validation` 并报行号，  
  **不静默退回不启用**
- **B-05** 未提交（`git show :path` 失败）→ 报错而非按 0 有效行放行（fail-closed）
- **B-06** 同一提交命中多份清单的 TOUCH（多需求并行，REQ-006 场景）→ 档位按  
  **并集**计算一次，逐份清单各自按声明档校验
