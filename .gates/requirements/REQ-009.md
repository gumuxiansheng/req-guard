## 1. 需求分解

### 背景与问题

《AI 工具合规保证规范》§8.2 已把「改完测试必须做判决性实验」写成纪律：
**把实现改坏，看测试是否失败，然后才提交**。理由是「测试通过」与「测试有效」
是两件**无法区分**的事 —— REQ-008 里就有一个断言方向写反的测试，一直绿，
却什么都没验。

但纪律写在文档里就有 §8.1 那条老问题：**它没有执行机制**。本项目的经验反复
验证过同一件事 —— 没有执行机制的纪律等于建议：

- 「`.gitignore` 必须幂等」写在注释里，改坏时没人发现，直到手工连跑两次才发现重复；
- 「`replace_section` 必须保留 GATE 块」写在注释里，第一次实现整段覆盖，
  是**测试**抓到的，但那时测试断言的前提也是错的；
- 「`--comment` 必须写入审核记录」从没人写过测试，于是一直静默丢弃直到手工核对。

三类问题的共同形态：**判据存在于人的意图里，不存在于可执行的检查里**。
本需求把 §8.2 从纪律变成命令。

### 目标

- **G1** `scripts/verify_tests_have_teeth.sh`：对**指定的关键判据**做变异检验 ——
  注入一个已知会破坏该判据的变异，确认对应测试**变红**。
- **G2** 变异清单与检验逻辑**分离**：变异的定义放清单文件，脚本只负责执行。
  理由：脚本里硬编码变异等于把「要验什么」藏在代码里，加一条要改两处。
- **G3** 变异体必须能**自证落地**：注入后先确认变异确实进了文件（比对内容），
  再跑测试。否则「测试变绿」可能只是因为变异根本没注入 —— 那种绿是假的。
- **G4** 任一变异存活（测试仍全绿）→ 退出码非 0，且指名道姓报出是哪个判据
  没有被任何测试覆盖。
- **G5** 三种结果**互斥且都可判定**：`killed`（守住了）/ `survived`（没人守）/
  `build_failed`（编译不过，**不算守住**）。第三种最要紧：把它算成「守住」，
  一份让整个 crate 编译不过的清单会全绿通过 —— 那是「看着在查、实际什么都没查」。

### 非目标

- **N1** 不做通用变异测试框架（全项目自动生成变异体、自动选测试）。
  理由：通用变异测试的价值在于**统计变异得分**，而这里要回答的是另一个问题
  ——「这个判据有没有被守住」，逐条手写变异更直接、误报更少。
- **N2** 不追求变异体数量。只覆盖**失效方向最坏**的那些判据
  （如「静默失效」类：门禁看着在拦、实际没拦）。
- **N3** 不把脚本接入 pre-commit 强制门禁。它需要改工作区文件，与提交并存的
  语义要单独设计；先作为 CI / 人工按需运行的检查。
- **N4** 不自己实现断言求值。「哪些测试红了」由 `cargo test` 判定，
  本脚本只负责注入、观测、还原 —— 少一份判断就少一处能漂移的地方。

## 2. 技术方案

### 总体思路

**变异清单 = 「这些判据必须有人守着」的书面合同；脚本 = 合同的可执行检查。**

对每条判据，手写一个「注入它就坏」的变异，跑对应测试，**测试仍全绿就说明这条判据
没人守**。三态判定（`killed` / `survived` / `build_failed`）互斥，任一 `survived`
或 `build_failed` 都让退出码非 0。

关键在于**判据与变异体的绑定是显式写下来的**：清单里每条都带一句「为什么这条
判据失效方向最坏」。这样「为什么验这个」不会随着时间丢失 —— 而丢失正是
判据腐化的起点。

### 关键设计

1. **变异清单格式**（每行一条，5 段以单个 TAB 分隔，无转义、无多行）：

   ```
   <文件>\t<锚点原文>\t<替换文本>\t<测试过滤串>\t<理由>
   ```

   **为什么是 TAB 而不是 `|`**：锚点与替换都是 Rust 源码行，而 `|` 在 Rust 里
   是高频字符 —— 闭包参数 `|c|`、`or_else` 里的 `||`、字符串 `"|"`。
   本仓库的实证：`core/src/section.rs` 有 17 行含 `|`，其中 157–158 行正在
   `mask_fenced` 内：

   ```rust
   .take_while(|c| **c != '\n')
   .all(|c| c.is_whitespace());
   ```

   用 `|` 分隔只有两种结果：正向切分则段数错；从右往左取理由则**锚点被静默截断**，
   注入到别的行去。后者正是本项目最坏的失效模式 —— 看起来在验，实际验的是别的东西。

   **TAB 也不是零风险，但风险可机械拦住**：条目里任何一段含 TAB 或换行即拒绝
   并指出行号（AC-011）。Rust 缩进用空格，源码行含 TAB 是异常形态，拒绝它
   比猜它更安全。

   用 TAB 而非 YAML/TOML：core 零外部依赖同理，脚本不应引入解析依赖；
   且清单要能被人一眼读完。理由是**必填**的 —— 没有理由的变异条目会被后来人
   当成噪音删掉，而它可能是整份清单里最重要的一条。

2. **单行约束与「插入型」变异**：锚点与替换**各占一行、逐字对应**，不做正则。
   因此「把函数体短路」不能写成多行块替换，而写成**在签名行后插入**：

   ```
   core/src/section.rs\tpub fn mask_fenced(text: &str) -> String {\tpub fn mask_fenced(text: &str) -> String { return text.to_string();\tmask_fenced\t围栏掩码失效时 touch 与 requirement 会静默切错段落
   ```

   锚点命中后，把该行替换为「锚点 + 空格 + 替换」= 在原行尾追加。
   这是刻意选的形态：**行数不变**（`mask_fenced` 的调用方依赖行号，见
   `docs/规范/AI工具合规保证规范.md` 的「掩码而非删除」），且不需要多行语法。

3. **注入手段：python3，不用 sed**。理由是具体的，不是风格偏好 ——
   sed 的替换文本里 `&` 是「整个匹配」的反向引用，而 `&&` 在 Rust 里满地都是；
   一条含 `&&` 的替换会被 sed 展开成匹配内容，**注入出语法不同的代码并静默跑测试**。
   `python3` 是仓库既有依赖（`scripts/verify_gate.py` 是 REQ 验收门槛的一环），
   逐行 `str.replace` 无此问题。

4. **自证落地（G3）**：注入后**断言文件内容确实变了**，且断言的是「恰好一行被改」
   （读回文件，比对锚点行是否等于「锚点 + 空格 + 替换」）。若锚点不存在或替换未生效，
   立即报错退出，绝不继续跑测试。理由：未生效的变异 → 测试当然全绿 → 被判成
   「判据没人守」→ **误报**，而误报会让整个检查被习惯性忽略。

5. **还原是硬约束（T4）**：用 shell `trap` 覆盖 `EXIT INT TERM`；
   还原方式是 `git checkout -- <file>`（脚本开头就检查，脏则拒绝运行）。用 git
   而非备份文件，是因为 git 能覆盖「被注入的文件本来就是未提交修改」这种情形
   —— 而那恰恰是最危险的。

   **脏检查只针对「本次要改的文件」**，不是整个仓库：

   ```sh
   git status --porcelain -- "$file"
   ```

   理由：开发者随时在工作区里改别的东西（写文档、跑格式化），若要求整个仓库
   干净，这个脚本在日常开发里几乎跑不了 —— 一个只在 CI 才好用的检查等于没有。
   对**本次要注入的文件**仍然 fail-closed：那里有未提交改动时 `git checkout`
   会丢改动，宁可不跑。

   **目标文件必须是 git 已跟踪文件**：`git checkout -- <file>` 对未跟踪文件
   无效，还原会静默失败并把工作区留在坏状态。清单里写了未跟踪文件即拒绝
   （AC-012）。

   **还原后校验**：trap 里还原完要比对「文件内容 == 注入前的内容」，不一致则
   明确告知并建议 `git stash list` / `git fsck`，且退出码非 0（AC-004）。

6. **三态判定**：

   | 结果 | 判据 | 计入守住 |
   | --- | --- | --- |
   | `killed` | 目标测试**跑起来了**且有失败 | 是 |
   | `survived` | 目标测试跑起来了且全绿 | 否 |
   | `build_failed` | `cargo test` 没跑起来（编译失败等） | **否** |

   **编译失败不算守住**，这是与初稿最大的一处分歧。理由：`survived` 的教训是
   「没人守」，而编译失败连这个结论都得不到 —— 它只说明「代码和这个文件有耦合」。
   若算成守住，一份让 crate 编译不过的清单会**全绿通过**，检查等于不存在。
   代价是失去一部分变异（§8.2 里那种「短路成编译不过」），但那些本来也没验到逻辑。

   「跑起来了」的判据用 `cargo test --no-run` 先确认可编译，再跑带过滤的那次，
   两次的退出码分开记录 —— 不靠解析输出文本（N4）。

7. **先跑基线（B3）**：全量运行前先在**未注入**状态下跑一遍每条变异的过滤串，
   任一不绿就中止并说明是哪个判据本来就红。不绿就注入等于拿一个已知红的
   基线去证明「变异杀死了它」。

8. **首版清单只收「失效方向最坏」的判据**（N2）。判据是：这条判据失效时，
   门禁表现为**看起来在拦、实际没拦**。REQ-008 的围栏边界正属此类 ——
   当时四条判定里三条**静默判错段落**，只有一条报错。

### 兼容性、性能与安全影响

- **兼容性**：不改任何 Rust 源码（仅运行时临时注入并还原）。
- **依赖**：新增 `python3`（注入与清单解析）。仓库验收门槛已在用
  （`python3 scripts/verify_gate.py`），不是新引入的依赖类别。
- **性能**：每条变异跑两次 `cargo test`（基线 + 变异），全清单预计 20–30 分钟。
  脚本接受 `--only <行号或理由关键字>` 按需跑单条；全量留给 CI。
  注意 `--only`（筛**条目**）与清单里的 `<测试过滤串>`（筛**测试**）是两个
  不同维度的过滤，参数名与文档都要写清，别混。
- **安全**：脚本会写工作区文件。三道保证：注入前的脏检查（限目标文件）、
  `trap` 还原、还原后一致性校验；此外脚本**拒绝**在非 git 仓库内运行
  （无处还原）。

### 风险点与回滚方案

- **风险 1（高）**：还原失败把工作区留在坏状态 → 开发者丢改动。
  缓解：目标文件脏则拒绝运行 + 未跟踪文件拒绝 + `trap` 还原 + 还原后**校验内容
  与注入前一致**（不一致则退出码非 0，并建议 `git stash list` / `git fsck`）。
- **风险 2（中）**：变异锚点随代码演进而失效 → 脚本误报「没人守」。
  缓解：自证落地失败时**明确报「锚点未命中，请更新清单」**，与「判据没人守」
  用不同措辞、不同退出码段 —— 前者是清单腐化，后者才是真问题。
- **风险 3（中）**：变异体让测试编译失败却被判「守住」→ 检查永绿。
  缓解：已在关键设计 6 里改为 `build_failed` 第三态，不计入守住。
- **风险 4（低）**：注入手段的转义语义把代码改成了别的东西（sed 的 `&`）。
  缓解：用 python3 逐行字面替换，且注入后断言「恰好一行被改」（G3）。
- **回滚**：删掉新增的脚本、清单与 `verify_gate.py` 场景即可；
  `verify_gate.py` 的改动是纯增量场景。

## 3. 测试计划

### 单元测试用例

跑在 `scripts/verify_gate.py` 里（T7），**不需要 cargo**，因此能在 CI 秒级回归。

| 编号 | 用例 | 断言点 |
| --- | --- | --- |
| U1 | 清单每行 5 段齐全 | 解析失败即报错并指出行号 |
| U2 | 缺理由的条目被拒 | 明确报「理由必填」 |
| U3 | 锚点不命中时报「锚点未命中」 | 不误报成「判据没人守」 |
| U4 | 变异注入后文件内容确实改变 | 自证落地检查有效 |
| U5 | 跑完/中断后工作区文件已还原 | 与注入前逐字相同 |
| U6 | **目标文件**脏时拒绝运行 | 退出码非 0，且不改动任何文件 |
| U7 | 条目含 TAB / 换行被拒 | 报「清单格式非法」并指出行号 |
| U8 | 目标文件未被 git 跟踪时被拒 | 报「目标文件未跟踪」 |
| U9 | 锚点含 `\|` 时不被截断 | 注入到正确的行 |
| U10 | 编译失败记为 `build_failed` | 退出码非 0，不计入 `killed` |
| U11 | 基线不绿时中止 | 报出是哪个判据本来就红 |

### 端到端用例

需要真实 cargo 项目，手工或 CI 跑。

| 编号 | 步骤 | 期望 |
| --- | --- | --- |
| E1 | 干净工作区运行全量清单 | 每条变异 `killed`，退出码 0 |
| E2 | 人为把某条变异改成「不破坏行为」 | 该条报 `survived`，退出码 1，指名判据 |
| E3 | 运行中 `timeout -s INT` | 工作区已还原（与 E4 同一手法，只是信号源不同） |
| E4 | 有未提交改动时运行 | 拒绝运行且不丢改动 |
| E5 | 目标文件干净、但**别处**有未提交改动 | 正常运行（脏检查不误伤） |

### 边界 / 异常场景

- **B1** 锚点在同一文件多处出现 → 报歧义，拒绝执行（不猜要改哪一处）。
- **B2** 替换文本与锚点原文相同 → 该变异无效，拒绝（否则测试必然全绿）。
- **B3** `cargo test` 因**与变异无关**的原因失败（如本来就红）→ 先跑基线，
  基线不绿就中止并说明。
- **B4** 清单为空 → 明确报「没有变异条目」，不退化成静默通过。
- **B5** 清单里出现未跟踪文件 → 拒绝（`git checkout` 还原不了）。
- **B6** 目标文件是未提交的新文件 → 同 B5，还原手段不成立。

### 回归范围与影响面

- 本需求**不改 Rust 源码**，故对既有测试无影响。
- 变异注入期间 `cargo test` 会编译到被改坏的文件，属预期。
- `verify_gate.py` 新增场景是纯增量，不改既有场景的判定。

### 验收门槛

- `shellcheck` 无告警（若本机可用）；`bash -n` 语法检查通过。
- `python3 scripts/verify_gate.py` 全场景通过，含本需求新增的 U1–U11。
- `cargo fmt --all --check` 与 scoped `clippy -- -D warnings` 零输出。
- **判决性实验**（§8.2）：交付前跑一次全量清单，确认每条变异确实变红；
  再人为做坏一处（如把还原后的校验关掉），确认脚本能报出来。
