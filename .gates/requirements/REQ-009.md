## 1. 需求分解

### 背景与问题

《AI 工具合规实施规范》§8.2 已把「改完测试必须做判决性实验」写成纪律：
**把实现改坏，看测试是否失败，然后才提交**。理由是「测试通过」与「测试有效」
是两件**无法区分**的事 —— REQ-008 里就有一个断言方向写反的测试，一直绿，
却什么都没验。

但纪律写在文档里就有 §8.1 那条老问题：**它没有执行机制**。本项目的经验反复
验证过同一件事 —— 没有执行机制的纪律等于建议：

- 「`.gitignore` 必须幂等」写在注释里，改坏时没人发现，直到手工连跑两次才发现重复；
- 「`replace_section` 必须保留 GATE 块」写在注释里，第一次实现整段覆盖，
  是**测试**抓到的，但那时测试断言的前提也是错的；
- 「`--comment` 必须写入审核记录」从没人写过测试，于是一直静默丢弃直到手工核对。

三类问题的共同形态：**判据存在于人的意图里，不存在于可执行的检查里**。
本需求把 §8.2 从纪律变成命令。

### 目标

- **G1** `scripts/verify_tests_have_teeth.sh`：对**指定的关键判据**做变异检验 ——
  注入一个已知会破坏该判据的变异，确认对应测试**变红**。
- **G2** 变异清单与检验逻辑**分离**：变异的定义放清单文件，脚本只负责执行。
  理由：脚本里硬编码变异等于把「要验什么」藏在代码里，加一条要改两处。
- **G3** 变异体必须能**自证落地**：注入后先确认变异确实进了文件（比对内容），
  再跑测试。否则「测试变绿」可能只是因为变异根本没注入 —— 那种绿是假的。
- **G4** 任一变异存活（测试仍全绿）→ 退出码非 0，且指名道姓报出是哪个判据
  没有被任何测试覆盖。

### 非目标

- **N1** 不做通用变异测试框架（全项目自动生成变异体、自动选测试）。
  理由：通用变异测试的价值在于**统计变异得分**，而这里要回答的是另一个问题
  ——「这个判据有没有被守住」，逐条手写变异更直接、误报更少。
- **N2** 不追求变异体数量。只覆盖**失效方向最坏**的那些判据
  （如「静默失效」类：门禁看着在拦、实际没拦）。
- **N3** 不把脚本接入 pre-commit 强制门禁。它需要改工作区文件，与提交并存的
  语义要单独设计；先作为 CI / 人工按需运行的检查。

### 子任务拆解

### 影响范围

- **模块**：新增 `scripts/verify_tests_have_teeth.sh`、变异清单文件；
  `docs/规范/AI工具合规保证规范.md`（§8.2 指向脚本）、`README.md`。
- **配置**：无。
- **清单格式**：无。
- **接口 / 数据表 / 外部 API**：无。
- **向后兼容**：不改任何 Rust 代码（除**变异注入目标文件**，但脚本运行时会还原）。
- **风险**：脚本会**临时改工作区文件**。T4 的还原保证是本需求的硬约束 ——
  一条变异卡住不退出会把工作区留在坏状态，那比不做这个检查更糟。

### 本次事故暴露的相邻缺陷（不在本需求范围）

`--comment` 静默丢弃那个 bug（REQ-007 提交时修复）**没有对应的变异条目**：
「若 CLI 把 `--comment` 读成 `--reason`，测试是否变红」。清单只能覆盖
**已经想到的**失效方向，本需求不解决「没想到的」——那是 T5 清单质量的问题，
需要靠每次复盘追加，而不是自动化。

## 2. 技术方案

### 总体思路

**变异清单 = 「这些判据必须有人守着」的书面合同；脚本 = 合同的可执行检查。**

对每条判据，手写一个「注入它就坏」的变异（把 `section::mask_fenced` 的函数体
短路成 `return text.to_string()`），跑对应测试，**测试仍全绿就说明这条判据没人守**。

关键在于**判据与变异体的绑定是显式写下来的**：清单里每条都带一句「为什么这条
判据失效方向最坏」。这样「为什么验这个」不会随着时间丢失 —— 而丢失正是
判据腐化的起点。

### 关键设计

1. **变异清单格式**（每行一条）：

   ```
   <文件>|<锚点原文>|<替换文本>|<测试过滤串>|<理由>
   ```

   用 `|` 分隔而非 YAML/TOML：core 零外部依赖同理，脚本不应引入解析依赖；
   且清单要能被人一眼读完。理由是**必填**的 —— 没有理由的变异条目会被后来人
   当成噪音删掉，而它可能是整份清单里最重要的一条。

2. **自证落地（G3）**：注入后**断言文件内容确实变了**。若锚点不存在或替换未生效，
   立即报错退出，绝不继续跑测试。理由：未生效的变异 → 测试当然全绿 → 被判成
   「判据没人守」→ **误报**，而误报会让整个检查被习惯性忽略。

3. **还原是硬约束（T4）**：用 shell `trap` 覆盖 `EXIT INT TERM`；
   还原方式是 `git checkout -- <file>`（**要求工作区干净**，脚本开头就检查，
   脏则拒绝运行）。用 git 而非备份文件，是因为 git 能覆盖「被注入的文件本来就是
   未提交修改」这种情形 —— 而那恰恰是最危险的。

   **工作区脏就拒绝运行**：否则 `git checkout` 会**丢掉开发者未提交的改动**。
   宁可不跑，也不能毁掉别人的工作。

4. **判定存活 = 测试仍全绿**。测试失败（含编译失败）都算「守住了」——
   编译失败也算，因为「变异体把代码改到编译不过」同样证明了测试与该代码位置
   有耦合，只是不够精确。

5. **首版清单只收「失效方向最坏」的判据**（N2）。判据是：这条判据失效时，
   门禁表现为**看起来在拦、实际没拦**。REQ-008 的围栏边界正属此类 ——
   当时四条判定里三条**静默判错段落**，只有一条报错。

### 兼容性、性能与安全影响

- **兼容性**：不改任何 Rust 源码（仅运行时临时注入并还原）。
- **性能**：每条变异跑一次 `cargo test`，全清单预计 10–15 分钟。**建议加
  `--filter` 按需跑**，全量留给 CI。
- **安全**：脚本会写工作区文件。T3 的脏检查 + T4 的 trap 还原是两道保证；
  此外脚本**拒绝**在非 git 仓库内运行（无处还原）。

### 风险点与回滚方案

- **风险 1（高）**：还原失败把工作区留在坏状态 → 开发者丢改动。
  缓解：脏检查拒绝运行 + `trap` 还原 + 还原后**校验内容与注入前一致**（不一致则
  明确告知并建议 `git stash list` / `git fsck`）。
- **风险 2（中）**：变异锚点随代码演进而失效 → 脚本误报「没人守」。
  缓解：自证落地失败时**明确报「锚点未命中，请更新清单」**，与「判据没人守」
  区分开 —— 前者是清单腐化，后者才是真问题。
- **风险 3（低）**：变异体恰好让测试**编译失败**而未真正测到逻辑 →
  判成「守住了」，实际没验到。缓解：清单里每条都带理由，评审时可人工判断；
  长期可考虑要求变异后仍能编译（但那会排除掉一批有价值的变异）。
- **回滚**：纯新增脚本与清单，删掉即可。

## 3. 测试计划

### 单元测试用例

| 编号 | 用例 | 断言点 |
| --- | --- | --- |
| U1 | 清单每行 5 段齐全 | 解析失败即报错并指出行号 |
| U2 | 缺理由的条目被拒 | 明确报「理由必填」 |
| U3 | 锚点不命中时报「锚点未命中」 | 不误报成「判据没人守」 |
| U4 | 变异注入后文件内容确实改变 | 自证落地检查有效 |
| U5 | 跑完/中断后工作区文件已还原 | 与注入前逐字相同 |
| U6 | 工作区脏时拒绝运行 | 退出码非 0，且不改动任何文件 |

### 端到端用例

| 编号 | 步骤 | 期望 |
| --- | --- | --- |
| E1 | 干净工作区运行全量清单 | 每条变异都被杀死，退出码 0 |
| E2 | 人为把某条变异改成「不破坏行为」 | 该条报存活，退出码 1，指名判据 |
| E3 | 运行中 Ctrl-C | 工作区已还原 |
| E4 | 有未提交改动时运行 | 拒绝运行且不丢改动 |

### 边界 / 异常场景

- **B1** 锚点在同一文件多处出现 → 报歧义，拒绝执行（不猜要改哪一处）。
- **B2** 替换文本与锚点原文相同 → 该变异无效，拒绝（否则测试必然全绿）。
- **B3** `cargo test` 因**与变异无关**的原因失败（如本来就红）→ 先跑基线，
  基线不绿就中止并说明。
- **B4** 清单为空 → 明确报「没有变异条目」，不退化成静默通过。

### 回归范围与影响面

- 本需求**不改 Rust 源码**，故对既有测试无影响。
- 变异注入期间 `cargo test` 会编译到被改坏的文件，属预期。

### 验收门槛

- `shellcheck` 无告警（若本机可用）。
- `cargo fmt --all --check` 与 scoped `clippy -- -D warnings` 零输出（虽然没改代码，
  但变异清单里引用的锚点必须仍然存在 —— 由 E1 保证）。
- `python3 scripts/verify_gate.py` 全部场景仍通过（证明本需求没碰坏任何东西）。
- `bash -n` 语法检查通过。

### AC-001
- Given: 一份含 5 段字段的变异清单与干净的工作区
- When: 执行 `bash scripts/verify_tests_have_teeth.sh`
- Then: 退出码为 0，且每条变异的状态为 `killed`，条数与清单行数相等

### AC-002
- Given: 一条变异把 `section::mask_fenced` 的函数体短路为原样返回
- When: 执行该脚本
- Then: 5 个围栏相关单测的失败数不少于 5，`killed` 计数比存活计数多 5

### AC-003
- Given: 一条变异的锚点文本在目标文件中不存在
- When: 执行该脚本
- Then: 输出含 `锚点未命中` 且不含 `存活`，退出码为 1

### AC-004
- Given: 脚本因 Ctrl-C 中断
- When: 检查目标文件内容
- Then: 文件内容与注入前的 sha256 之差为 0，且 `ls` 该还原文件返回 1 条记录

### AC-005
- Given: 工作区存在一处未提交修改
- When: 执行该脚本
- Then: 退出码为 1，输出含 `工作区不干净`，且该未提交修改仍完整存在

### AC-006
- Given: 变异清单中有一条缺少理由字段
- When: 执行该脚本
- Then: 退出码为 1，输出含 `理由必填` 与该行行号

### AC-007
- Given: 一个锚点原文在目标文件中出现 2 次以上的变异条目
- When: 执行该脚本
- Then: 退出码为 1，输出含 `锚点有歧义`，且目标文件未被修改

### AC-008
- Given: 一条变异的替换文本与锚点原文完全相同的条目
- When: 执行该脚本
- Then: 退出码为 1，输出含 `变异无效`，且目标文件未被修改

### AC-009
- Given: 一份空的变异清单文件
- When: 执行该脚本
- Then: 退出码为 1，输出含 `没有变异条目`，且不执行任何 cargo 命令

### AC-010
- Given: 脚本已正常执行完毕
- When: 执行 `git status --short` 观察工作区
- Then: `git status --short` 的行数与执行前之差为 0，且还原文件数为 0
