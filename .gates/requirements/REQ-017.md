## 1. 需求分解

### 背景与问题

前两份需求补的是「动作」与「体检」，本份补的是**工程卫生与可自证性**——
五项能力 core 里都有、CLI 里都有、界面上一个都没有，且其中两项属于
「界面不提供就等于不存在」的性质。逐条查证：

1. **需求编号冲突检测在界面上没有，而它的失效后果是门禁语义失真**。
   `idcheck::check`（`core/src/idcheck.rs:56`，CLI `ids --check`，`main.rs:297-342`）
   做三类检测，每一类都对应一个真实故障形态（`idcheck.rs:3-9` 模块文档）：
   - ① **同 id 多文件**：slug 不同时 git **零冲突静默共存**，
     `find()`（`requirement.rs:410`）按文件名字典序**任取其一**——
     「审批、评论、拦截判定都可能落到错误的文件上，门禁语义失真」。
     这是 `docs/规范/需求编号防冲突命名规范.md §2.1` 定义的**最坏形态**；
   - ② **自动编号污染**：`REQ-` 后紧跟 ≥5 位数字（典型为 8 位日期）
     会把 `next_id()` 的自增基线永久顶到日期量级；
   - ③ **前缀歧义**：文件名 A 恰为另一文件的 `<A>-` 前缀，`find(A)` 会命中其一。
   界面上新建需求时走 `create(root, None, title)`（GUI `app.rs:175`、
   TUI `app.rs:769`），**自动编号 + 无冲突检查**；
   即界面上**创建 20 份需求这件事本身没有任何冲突预警**。

2. **界面不能指定自定义编号，而团队规范推荐的正是自定义编号档**。
   `create(root, Some(id), title)` 支持（`requirement.rs:266`），
   `idcheck::lint_id`（`idcheck.rs:141`）会对自定义编号给出形态提示
   （规范 §1 的推荐格式 `REQ-<owner>-<YYYYMMDD>-<rrrr>`，CLI `create --id`）。
   本仓库的 `docs/规范/需求编号防冲突命名规范.md` §5.1 已经把推荐格式写清楚了，
   **但界面上无法使用**——多人/多分支协作时只能回终端。
   更矛盾的是：规范 §8 的 P2 要求「CI / pre-push 调用 `ids --check`」，
   而**界面上创建的编号从未被检查过**，CI 那一关迟早会红。

3. **返工率指标在界面上不可见**。
   `requirement::amend_counts`（`requirement.rs:2208`）从台账统计每段的 `AMEND`
   次数，CLI 在 `status` 输出里带一行（`cli/src/render.rs:64-75`）。
   这个指标的意义写在 `requirement.rs:2203-2207`：「高返工率是需要复盘的工程信号，
   不是一条可机械判定的硬伤；做成门禁只会催生『少写 amend 刷分』」。
   界面上没有它，审核人在批准下一段时**看不到「这一段已经改过 4 次」**。

4. **门禁安装自检在界面上没有**。
   `gate::verify_install_with`（`gate.rs:1813`，CLI `install --verify`）
   与 `gate::verify_warnings`（`gate.rs:2843`）检查门禁资产是否齐全、
   主脚本是否真的委托 core 判定。REQ-012 已实测出「`install --verify`
   只做子串存在性检查，形同虚设」（REQ-012 背景表第 5 条），
   并在 `gate.rs:1809-1812` 的注释里记录了 `semantic` 参数（REQ-012 T11 的实跑语义自检）。
   **结论：判断「门禁自己还活着吗」只能敲终端**，而这恰恰是最该随手可查的事。

5. **票据状态与身份在界面上完全不可见**。
   - `token::load_any`（`token.rs:108`）读当前凭据配置（模式 / 范围 / 到期）；
   - `auth::effective_level`（`auth.rs:132`）给等级；
   - `identity::describe`（`identity.rs:191`）给姓名 / 邮箱 / sig；
   - `auth::is_ai_context`（`auth.rs:115`）判当前是否 AI 会话。
   CLI 有 `whoami`（`main.rs:456-494`）与 `token status`（`main.rs:534+`）。
   界面上用户**无法回答「我现在为什么点不动按钮」**——
   REQ-015 的 G6 只覆盖了身份与等级，票据形态与到期时间仍缺，
   而 L3 下一枚票据 10 分钟就废（`auth.rs:220` 的 `UI_CRED_TTL_MIN`），
   「过期了」是最常见的失败原因却完全不可见。

   ⚠️ **但这里必须划一条线**：界面上**不提供 `token issue` / `revoke`**。
   `auth.rs:332-348` 写得很清楚：恢复路径刻意做得比正常路径更贵
   （人类在场 + 强制留痕 + TTY 挑战码 `prove_presence`，`auth.rs:417`），
   而 `token::revoke`（`token.rs:252`）**甚至不走 `ensure_human`**
   （它只写一个 `enabled=false` 的配置文件）。把凭据管理搬进界面 =
   给「签发 / 撤销审批资格」开一个无 TTY 挑战的旁路。
   本需求只做**只读可见**（G5），不提供任何票据写操作（N4）。

### 目标

- **G1 界面可见编号冲突检测**：两个界面都能展示 `idcheck::check` 的结果
  （三类问题分色：Error 与 Warn），并在**新建需求对话框里先跑一次预检**
  ——即用户填完编号、点创建之前就看到冲突预警，而不是等 CI 红。
- **G2 新建需求支持自定义编号**：GUI 的新建对话框与 TUI 的 `n` 弹窗
  增加编号输入（留空 = 自动编号，与现状逐字一致），填了则
  ① 调 `idcheck::lint_id` 展示形态提示（**不阻断**，与 CLI 一致）；
  ② 调 `create(root, Some(id), title)`。
  预检与创建都要显示 `create` 返回的冲突错误（`create` 对重复编号会 `Err`，
  `requirement.rs:2981-2986` 的单测已覆盖）。
- **G3 返工率可见**：两个界面的需求详情里显示 `amend_counts`
  （段标签 + 次数），并在次数 ≥ 阈值时给出「建议复盘」的提示。
  **明确不做成门禁**（`requirement.rs:2203-2207` 的既有决定）。
- **G4 门禁自检可查**：两个界面都能展示 `verify_install_with(root, None, true)`
  的完整问题列表 + `verify_warnings` 的告警。`base` 传 `None`
  （界面没有「PR 视角」，`gate.rs:1809-1811` 明说本地不给即跳过漂移检测），
  `semantic` 传 `true`（**不要**用 `--quick` 的子串快筛——那已被 REQ-012 证明形同虚设）。
- **G5 票据与身份只读可见**：顶栏（或「环境」面板）显示
  `identity::describe`、`auth::effective_level`、`auth::is_ai_context`、
  以及 `token::load_any` 的**脱敏**摘要（模式、是否有范围、剩余分钟数——
  **绝不显示凭据原文**）。界面**不提供**任何票据签发 / 撤销入口。
- **G6 失败原因自解释**：界面上任何「按钮点不动 / 动作失败」的情况，
  若错误来自鉴权（缺凭据 / 等级不足 / AI 上下文），
  必须把 core 的原始文案**原样**显示，并在旁边附上
  `auth.rs:294` 那种三选一取解（改 git 身份 / 切等级 / 走 CLI）。
  **不许包装成「操作失败」**——那会让用户反复点同一个按钮。
- **G7 核心判定零改动**：不改 `idcheck` / `token` / `auth` / `identity` /
  `gate::verify_install_*` 的任何语义。新增 core 符号仅限
  `token` 的**脱敏摘要**读取（见关键设计 3）。

### 非目标

- **N1** 不在界面上提供 `token issue` / `token revoke` / `token status --i-lost-it`。
  理由见背景第 5 条的 ⚠️：`revoke` 不走 `ensure_human`，`issue` 在 L1+ 要 TTY
  挑战码，界面没有 TTY。这不是 UX 取舍，是**不能削弱鉴权**。
- **N2** 不让 `ids --check` 的结果变成门禁阻断项。它在 CLI 里也是
  「硬伤退出码 1 即拦截」（规范 §8 P2），但那是**CI 调用**的职责；
  界面上只展示，不阻断任何动作。
- **N3** 不做 `lint_id` 的阻断。`idcheck.rs:141` 的文档明说「**不阻断**」，
  界面照抄。
- **N4** 不实现规范 §8 的 P2（CI / pre-push 自动调用 `ids --check`）——
  那是 CI 配置改动，属 `.cnb.yml` / `.github/workflows/` 的地盘，
  不在本需求（`touch.exempt` 里也没有这些路径，本需求不扩范围）。
- **N5** 不改 `.gates/req-guard.yaml`，不碰 `touch.exempt`。
- **N6** 不把审计摘要（`gate::audit_digest`）放进来——它已在 REQ-016 的 G7
  作为「体检面板的一组」实现，避免两个需求抢同一个动作。
- **N7** 不做「多项目根目录的编号冲突合并视图」。GUI 有切换目录
  （`gui/src/app.rs:594` 的 `rfd`），但本需求不做跨项目聚合
  ——编号冲突是**单仓内**的判定。

## 2. 技术方案


### 总体思路

**五项能力全部是「把 core 已有的只读判定显示出来」，不新增任何判定。**
唯一的 core 改动是给 `token` 加一个**脱敏**摘要读取面，且必须证明它不含凭据原文。
界面上不提供任何票据写操作——那不是取舍，是鉴权底线。

### 关键设计

1. **`token` 脱敏摘要：为什么必须新增，而不是让界面直接读 `load_any()`**（G7 的落点）：
   `token::load_any()`（`token.rs:108`）返回的 `TokenCfg` **含 `hash`**，
   即凭据的 SHA-256。虽然是哈希而非原文，但：
   - 它足以让界面「不小心」显示出一段看起来像凭据的十六进制，
     用户截图/贴 issue 时就等于泄露了一半凭据材料；
   - 更实际的问题是**权限**：`TokenCfg` 是完整配置结构，
     前端拿到它就会想要打印全部字段（`fmt::Debug` 一打印就全有了）。
   故新增：
   ```rust
   pub struct TokenSummary {
       pub enabled: bool,     // enabled
       pub mode: String,      // "static" / "scoped" / "off"
       pub scoped: bool,      // scope 非空
       pub minutes_left: Option<u64>, // expires_epoch 换算，None = 已过期或未启用
   }
   pub fn summary() -> Option<TokenSummary>
   ```
   **刻意不实现 `Debug` 的自定义脱敏**（那容易被后续 `{:?}` 绕过），
   而是**结构体里就不含任何凭据材料**——白名单式设计，
   T2 用「字段白名单断言」锁死（关键设计 2）。
   `minutes_left` 用 `gate::now_epoch()` 换算；已过期给 `None`
   且界面显示「已过期」（这是 L3 下最常见的失败原因，见背景第 5 条）。

2. **字段白名单单测怎么写才有牙**（T2 的落点）：
   断言方式不是「`summary()` 的字符串里不含 hash」，
   而是**枚举 `TokenSummary` 的字段名**（用编译器辅助或 `std::mem::size_of`
   + 显式字段名列表），断言集合恰为
   `{enabled, mode, scoped, minutes_left}`。
   前者可以被「哈希恰好没被格式化出来」蒙混通过，后者不能。
   再加一条判决性实验：给 `TokenSummary` 加一个 `hash: String` 字段，
   该单测必须 FAIL。

3. **自定义编号的三条路径**（G2，T13）：
   | 输入 | 行为 |
   | --- | --- |
   | 空 | `create(root, None, title)`——**与现状逐字一致** |
   | 合法 | 先 `lint_id` 展示提示（不阻断，`idcheck.rs:141`），再 `create(root, Some(id), title)` |
   | 与已有冲突 | `create` 自身 `Err`（`requirement.rs:2981-2983` 的单测已覆盖重复编号），界面原样显示 |

   **不用 `idcheck::check` 做创建前预检**——`check` 扫的是**磁盘上已有的**清单
   （`idcheck.rs:55`），新建前磁盘上还没有这份，查不出「与它冲突」。
   创建前能做的只有 `lint_id`（形态检查，如 C2 数字开头、C4 超长）。
   真正的冲突检测靠 `create` 返回 `Err`。这一点必须在实现时认清，
   否则会写出「新建对话框里跑 `check` 然后报告无冲突」的假预检。
   G1 的编号冲突面板查的是**已存在**清单之间的冲突，是另一件事。

4. **返工率的展示阈值**（G3）：
   `amend_counts`（`requirement.rs:2208`）返回 `Vec<(String, usize)>`（段 key → 次数）。
   阈值取 **3**，理由：0–2 次属正常打磨（`amend` 的设计意图就是「方向没错、只是要改」，
   `requirement.rs:730-735`），≥3 次说明方案本身没想清楚
   （这正是 `requirement.rs:2203-2205` 那句「哪几段反复返工 = 方案当初没想清楚」）。
   **阈值提为单一常量**，可一行改；单测只断言「≥ 阈值时提示出现、< 阈值时不出现」，
   不锁死「必须恰好是 3」。
   ⚠️ 明确**不做成门禁**：`requirement.rs:2206-2207` 写明
   「做成门禁只会催生『少写 amend 刷分』」。界面上也只是提示，不阻断任何动作。

5. **门禁自检必须用 `semantic = true`**（G4）：
   `verify_install_with(root, base, semantic)`（`gate.rs:1813`）：
   - `base` 传 `None` —— 文档明说「本地没有『PR 视角』，硬判只会误报」
     （`gate.rs:1809-1811`）。**传 `Some("origin/main")` 是错的**；
   - `semantic` 传 `true` —— 这是 REQ-012 T11 引入的实跑语义自检。
     REQ-012 背景表第 5 条已实测「`install --verify` 只做子串存在性检查，形同虚设」
     （往主 hook 顶部插 `exit 0` 仍报 PASS）。
     界面若传 `false`，等于把一个**已知无效**的自检显示给用户，
     比不显示更坏。`semantic = true` 会在临时沙箱里实跑脚本
     （`gate.rs:2869` 的 `sandbox_repo`），耗时略长但只在点击时发生。
   界面必须把耗时性质说清（「首次约需数秒，会在临时仓库实跑脚本」）。

6. **鉴权失败文案必须逐字透传**（G6，T8/T12/T15）：
   `auth::ensure_human` 的三类错误各自已有完整取解文案：
   - 缺凭据 → 「获取票据：在真实终端执行 `req-guard token issue`…」（实测输出即此）；
   - 身份冲突 → `identity.rs:243-250` 的三条取解；
   - AI 上下文 → `auth.rs` 的 `ai_ctx_err`。
   实现纪律：**界面不重写、不摘要、不加「操作失败：」前缀**。
   界面的包装层只能是「在原文下方追加一行灰字提示指向面板」，
   原文必须完整可见（`TestBackend` 缓冲区可检索到核心片段）。
   ⚠️ 这条单测要断言**具体片段字符串**（如 `一次性范围票据`）出现在最终渲染文本里，
   否则「原样透传」很容易被后来者改成摘要而测试仍然通过。

7. **TUI 的「环境」信息放哪**（T11）：
   TUI 没有 GUI 那样的顶栏（`ui.rs:84` 的 `render_header` 只有仓库根与解锁态）。
   放法：在 `?` 帮助浮层（`Overlay::Help`，`ui.rs:268`）底部追加一节
   「当前环境」，显示身份 / 等级 / AI 上下文 / 票据摘要。
   理由：这是「偶尔要看一眼」而非「频繁操作」的信息，
   塞进主界面会挤占本已紧张的高度（`ui.rs` 的三栏布局 + footer）。
   帮助浮层正是「偶尔查」信息的既有落点。

8. **TUI 新建需求从一步变两步的代价**（影响范围末条的缓解）：
   `Prompt::NewTitle`（`tui/src/app.rs:31`）拆为
   `Prompt::NewId`（可留空）+ `Prompt::NewTitle`。缓解三招：
   ① `NewId` 步骤的提示文案写明「直接回车用自动编号」；
   ② 两步在**同一浮层**内完成，回车后焦点自动落到标题框；
   ③ 提供 `Esc` 一步取消（回退到 `n` 之前的状态）。
   ⚠️ 仍要在 UI 的提交说明里写明「`n` 现在多一步」——这是本需求的已知代价，
   不掩饰（T12 的验收覆盖）。

### 兼容性、性能与安全影响

- **兼容性**：**不改任何既有 core 语义与签名**，唯一新增是
  `token::{TokenSummary, summary}`。CLI 行为不变、清单格式不变、配置不变。
  界面新建需求留空编号时与现状逐字一致。
  ⚠️ TUI 的 `n` 键交互从一步变两步（见关键设计 8），是**唯一**的行为回归，
  已给出缓解但如实记录为代价。
- **性能**：
  - `idcheck::check` 是 O(N) 读盘 + 分组（N = live 清单数，本仓库 15）；
  - `verify_install_with(.., semantic = true)` 会在 `std::env::temp_dir()`
    造一个 `git init` 沙箱并**实跑脚本**（`gate.rs:2869` 的 `sandbox_repo`），
    耗时秒级。**必须只在点击时调用**，绝不进 3 秒轮询
    （`gui/src/app.rs:161`、`tui/src/app.rs:240`）；
  - `amend_counts` 读一次台账全文并正则统计（`requirement.rs:2211-2215`），
    每次调用 O(台账长度)。台账是本仓库唯一随审批增长的文件，
    故**详情面板打开时算一次并缓存**，切段不重算；
  - `token::summary()` 读一个配置文件，可忽略。
- **安全**（本需求**不放宽**任何东西）：
  - **不提供票据签发 / 撤销**（N1）。这是本需求最重要的一条：
    `token::revoke`（`token.rs:252`）**不走 `ensure_human`**
    （只写一个 `enabled=false` 的配置），而 `token issue` 在 L1+ 要求
    TTY 挑战码（`auth.rs:348`、`:372`）。界面没有 TTY，
    把它们搬进来等于给「签发 / 撤销审批资格」开一条无在场证明的旁路。
    **只读可见，不写**。
  - `TokenSummary` 结构体不含凭据材料（关键设计 1/2），
    所以「在界面上看到票据状态」不会变成「在界面上泄露凭据」。
    ⚠️ 特别注意：`token.rs:150-152` 附近已有「L2 起不读 `REQ_GUARD_TOKEN`
    环境变量」的设计（`auth.rs` 的 `provided_credential`），
    界面**不得**为了显示票据状态而新增任何读环境变量的路径——
    那会直接击穿 L2 的防线。
  - `idcheck::check` / `lint_id` / `amend_counts` / `verify_*` 全是只读，
    界面上**不得**提供「修复」按钮（那会变成写操作且绕过设计者意图）。
    `idcheck` 的三类问题里只有「编号污染」有明确修法（改文件名），
    而改名会影响 git 历史，**绝不提供一键改名**。
  - 本需求不产生任何审计事件（见影响范围末条），台账不被只读查询污染。

### 风险点与回滚方案

- **风险 1（高）**：顺手把 `token issue` / `revoke` 也做成界面按钮
  （实现时很自然：「既然能看状态，撤销一下更方便」）。
  缓解：G7/N1 明确只读；`revoke` 不走 `ensure_human` 这一事实写进方案正文
  与 README（T17），让后续修改者读到理由而不是只看到禁令。
  验收：断言界面**不存在**签发 / 撤销入口。
- **风险 2（中）**：`verify_install_with` 传 `semantic = false`（图快），
  把 REQ-012 已证明无效的子串快筛显示给用户。
  缓解：关键设计 5 明确 `true`；单测断言调用点传的是 `true`。
- **风险 3（中）**：鉴权错误被界面包装成「操作失败：…」，用户反复点同一按钮。
  缓解：G6 + 关键设计 6；单测断言具体片段字符串出现在渲染文本里。
- **风险 4（中）**：`TokenSummary` 后续被加上 `hash` 或 `raw` 字段
  （有人想「顺便显示更多信息」）。
  缓解：关键设计 2 的字段白名单单测 + 判决性实验。
- **风险 5（低）**：`idcheck::check` 被误当新建前的冲突预检（会得出假的无冲突）。
  缓解：关键设计 3 明确区分；单测覆盖「填冲突编号时 `create` 返回 `Err`」。
- **风险 6（低）**：体检被放进轮询，尤其 `verify_install_with(semantic=true)`
  造临时 git 仓库会持续在磁盘上建垃圾。
  缓解：设计约束「点击时才算」；验收用计数断言。
- **风险 7（低）**：TUI 的 `n` 变两步被老用户当成 bug。
  缓解：关键设计 8 的三招 + UI 提交说明；如实记为已知代价。
- **回滚**：`git revert` 即可，无数据迁移、无格式变更、无配置变更、
  无新增审计事件。⚠️ 唯一不可回滚的是用户在界面上**创建过的自定义编号清单**
  （文件已落盘）——但那是正常产出，不是副作用。

### 边界 / 异常场景

- **B1** 归档区里的清单：`idcheck::check` 只扫 live 目录
  （`idcheck.rs:55` 调 `requirement::list`），编号冲突面板**不显示归档区**。
- **B2** 编号冲突面板在 0 份清单时：显示明确空态，不 panic。
- **B3** 新建编号填了含中文 / 空格 / 点的字符串：`normalize_id` 会归一或拒绝，
  界面原样显示 core 的错误（不自行截断或替换），
  并同时展示 `lint_id` 的 C1 提示。
- **B4** 自定义编号与自动编号撞号：既有 `REQ-003` 存在时填 `REQ-003` → `Err`；
  填一个比当前最大值大的号（如 `REQ-099`）→ `Ok`，
  且此后自动编号从 100 起（`next_id` 取 max，`requirement.rs:2471`）——
  界面**必须**在成功后提示这一点，否则用户会困惑「为什么下一个编号跳了」。
- **B5** `verify_install_with(semantic=true)` 在非 git 目录：沙箱自建 `git init`
  （`gate.rs:2869`），不应报错；若无 git 可执行则如实显示失败原因。
- **B6** 门禁资产缺失（`.gates/hooks/` 被删）：面板逐条列出缺失资产
  （`gate.rs:1822-1830` 的固定清单），并提示执行安装。
- **B7** 返工率台账不存在：`amend_counts` 返回全 0（`requirement.rs:2210-2212`
  的容错分支），面板显示 0 而非报错。
- **B8** 票据文件的 `expires_epoch` 已过：`minutes_left` 为 `None`，
  界面显示「已过期」（不是负数）。
- **B9** `HOME` / `USERPROFILE` 未设置：`token::guard_dir()` 返回 `None`
  （`token.rs:92-95`），`summary()` 返回 `None`，界面显示「未启用凭据」而非崩溃。
- **B10** 同一台机器上多个项目共用一份凭据（凭据按用户目录存，非按仓库存）：
  界面**必须显示该凭据是全局的**（提示文案含「对所有项目生效」），
  否则用户会以为撤销 A 仓的票据不影响 B 仓。这是本需求的诚实边界。
- **B11** TUI 终端高度很小（20 行）：帮助浮层加环境节后内容被截断，
  环境节必须**排在末尾且可滚动到**，不得把已有帮助条目挤出视野。
