## 1. 需求分解

### 背景与问题

三段清单目前只有第 3 段有内容校验（`GATE:AC` 的 A1–A12）、第 2 段有声明校验
（`GATE:TOUCH` 的 T1–T6），**第 1 段完全裸奔** —— `create` 出来的模板占位
`- [ ] 背景与问题：为什么要做这件事` 等五行可以原样留着、0 行实质正文，
一路走到提交，没有任何一处会拦。

**这不是假想**：本仓 REQ-002 的 `## 1. 需求分解` 就是这样 —— 我填了第 2、3 段，
漏了第 1 段，模板占位原样留着，`ac check` 绿、`touch-check` 绿、`check` 绿、
提交通过。靠人工自查才发现。也就是 REQ-001 立项要消灭的「三段都是空话」，
在第 1 段上**至今仍然成立**，因为没有任何机器判据。

后果与「三段空话」同级：审核人看到的是一份排版完整的清单，实际上没有任何人写过
背景、目标、影响范围 —— 审批退化为逐个文件盖橡皮章，而且比"格式错"更难发现，
因为所有格式工具都通过了。

### 目标

- **G1** 判定可机械执行：某段实质正文行数为 0 即报错，不依赖"读起来像不像话"。
- **G2** "什么不算实质正文"必须**精确且可推导**：占位文案不得另写一份，
  从模板常量派生，否则模板一改判定就与文档脱节。
- **G3** 与既有规则交叉一致：`GATE:AC` 空块（A8）与 `GATE:TOUCH` 空块（T1）
  各自已有判定，本规则不得与它们矛盾或重复报同一件事。
- **G4** 强制点同样挂审批：该步对应的段为空时拒绝 `approve`，而不只是 `check` 时报。
- **G5** 存量影响可控：报错文案必须可直接执行，不只说"不通过"。

### 非目标

- **N1** 不做质量判断（写得清不清晰、方案是否可行）。本规则只判"有没有"。
- **N2** 不设"行数下限"。一段 3 行的具体内容比 50 行的复述更有价值；
  设阈值会把"写短但写到了"判成不合格。
- **N3** 不检测"复制粘贴的实质正文"（把上一段的段落原样粘过来仍算实质）。
  判定不了，且不值得为它引入相似度比较。
- **N4** 不改动模板文案。占位文案是给作者的提示，改它会让本规则的派生集合漂移。
- **N5** 不重复 REQ-002 的"批准后不冻结内容"。本需求判"批的那份不是空的"，
  REQ-002 判"批的那份不被改" —— 互补，不重叠。

## 2. 技术方案

### 总体思路

**一条规则**：某段的"实质正文行数"为 0 → 报 `EmptySection`。

关键全在"什么算实质正文"的定义 —— 定义不精确，这条规则就会变成误报源，
而误报会让门禁被习惯性绕过，等于没有门禁。

### 关键设计

1. **占位文案从模板常量派生，不另写一份**：占位行判定 = "该行去掉列表符与勾选框后
   **整行等于**某条模板占位文案"。文案源是 `DECOMPOSITION_BODY` / `SOLUTION_BODY` /
   `TESTPLAN_BODY`，由调用方传入。模板一改，判定自动跟着变；另写一份副本
   就等于给文档漂移开一个口子（AC-010 用例专门锁这条）。

2. **用整行相等而非前缀匹配**：作者完全可能写"背景与问题：本次要解决…"——
   前缀匹配会把它误判成占位而杀掉正常内容，这是最危险的误报方向。

3. **不计入实质正文的行**（穷举，每条都有理由）：
   - 空行与纯空白 —— 没有信息
   - HTML 注释整块（含 `<!-- GATE:… -->` 与其说明文字）—— 元信息，不是清单内容
   - 与模板占位文案同源的 checkbox 行，**勾选与否都不算** ——
     勾上框不等于写了内容，这正是本需求要抓的形态
   - Markdown 标题行（`## N.` / `###`）—— 结构骨架
   - 表格分隔行（`|---|`）与水平线（`---` / `***`）
   - 块引用行（`> …`）—— 模板顶部的门禁说明用的就是它

4. **GATE 块内的条目也不算**：第 3 段的 AC 条目由 A8 管、第 2 段的 TOUCH 声明由
   T1 管。若把它们计入实质正文，会出现"只有一个空 AC 骨架的段落被判为有内容"，
   两条规则互相掩护 —— 那是最坏的组合。**交叉一致性由此保证**：A8 命中时
   本规则必然也命中，两条独立路径指向同一结论（AC-006 / AC-007）。

5. **只判"有没有"，不判"有多少"**：无行数阈值（见非目标 N2）。

6. **不新增命令、不新增问题类型**：并入 `ac check`，判定放在新模块
   `core/src/section.rs`，问题类型**复用 `AcIssueKind`**（新增一个变体
   `EmptySection`），而不是另立 `SectionIssueKind`。

   理由：`ac check` 一次遍历就要输出两类问题（AC 规则 + 段落实质性），
   两个平行枚举意味着 CLI 要为同一份报告维护两套类型、两套排序逻辑
   （Error 在 Warn 前），而它们回答的是同一个问题——"这份清单的内容是不是空话"。
   一个枚举更简单，且新增 kind 仍受既有的枚举覆盖门槛保护。
   （实现如此，本条即对规格的修正：原设想是独立的 `SectionIssueKind`。）

7. **挂审批**：与 REQ-001 的教训一致 —— 只提供命令等于没有命令。
   `review()` 在 `pass && step == <该段>` 时检查该段，为 0 则拒绝。

### 兼容性、性能与安全影响

- **兼容性**：不新增字段、不改模板、不改格式，纯读判定。唯一影响是存量清单中
  "某段无实质正文"者新增报错。
- **性能**：逐行集合判定 O(段长)；占位文案集合每次 `check` 构造一次（几十条），可忽略。
- **安全**：不引入凭据、不新增逃逸口。

### 风险点与回滚方案

| 风险 | 处置 |
| --- | --- |
| **误报**：把合法的精简段落判成空 | 占位只认模板同源且整行相等；自定义行一律算实质；无行数阈值（AC-003） |
| 占位文案副本与模板漂移 | 文案从模板常量派生；U-03 反向断言模板每条占位都被识别 |
| 与 A8 / T1 重复报同一件事 | GATE 块条目不计入实质；两者命中时错误文案互相指明对方规则 |
| 存量清单大面积报错 | 报错文案给出"该补什么、去哪补"；`check` 与审批两处一致，不藏着 |
| 有人把正文写进 HTML 注释里规避 | 注释整块不计入实质 —— 规避不成立，且注释内容对审核人本就不可见 |

**回滚**：移除 `core/src/section.rs`、`ac::check` 的汇总与 `review()` 的挂钩即可，
清单格式零影响（无字段可留）。

### 单元测试用例（编号 + 断言点）

- **U-01** `section::is_substantive`：空行 / 注释 / 标题 / 分隔线 / 占位 checkbox → false
- **U-01b** 空段文案每段指向自己的标记（技术方案→`GATE:TOUCH`，测试计划→`GATE:AC`）
- **U-02** `section::placeholder_texts`：从三段模板常量派生，条数与内容与模板一致
- **U-03** **防漂移**：模板里每个 `- [ ] 占位` 行都被判为非实质（模板一改即红）
- **U-04** 占位判定用**整行相等**而非前缀匹配（自定义续写不算占位）
- **U-05** 勾选态（`- [x] <占位文案>`）仍判为非实质
- **U-06** `GATE:AC` / `GATE:TOUCH` 块内条目不计入实质正文
- **U-07** 三段各自独立判定，段边界不串（`## N.` 为界）

### 端到端用例（编号 + 执行步骤）

- **E-01** 新建清单未填任何内容 → `ac check` 报 3 个 EmptySection
- **E-02** 填完三段 → `ac check` 绿 → `approve` 三段 → `check` 绿
- **E-03** 只填第 3 段（含合规 AC）→ 仍报第 1、2 段 EmptySection
- **E-04** 对存量仓库跑 `ac check`（REQ-001 / REQ-002）→ 零新增报错

### 边界 / 异常 / 并发场景

- **B-01** 段标题被写成 `### 三、需求分解`（非法形式）→ 报 SectionNotFound，不重复报 EmptySection
- **B-02** 正文全被格式化工具重排（行序变化但内容不变）→ 仍判有内容
- **B-03** 单段超过 5000 行 → 判定耗时仍为线性，无栈溢出
- **B-04** 正文写在引用块 `> …` 里 → 不计入实质正文（模板顶部说明用的就是它）

### 回归范围与影响面

- 全量：`cargo test --workspace`、`python scripts/verify_gate.py`
- 受影响：`core/src/section.rs`（新增）、`core/src/ac.rs`（汇总）、`core/src/requirement.rs`
  （审批挂钩）、`core/src/lib.rs`、`cli/src/main.rs`（文案）
- **重点回归**：`ac check` 对 REQ-001 / REQ-002 必须仍为绿（它们是本规则的存量样本）

### 验收门槛（可机械判定）

- `AcIssueKind::EmptySection` 纳入既有的**枚举覆盖门槛**（REQ-001 立的那条：
  遍历全量变体断言每个都被用例命中）——新增变体漏测即红
- U-01..U-07 全绿；`cargo clippy --workspace --all-targets -- -D warnings` 零告警
- `verify_gate.py` 新增 2 场景：第 1 段为空的清单 `ac check` 红；三段齐全的清单绿
- `ac check` 对 REQ-001 与 REQ-002 零新增报错（存量兼容的硬证据）
