## 1. 需求分解

### 背景与问题

**同一类事故已经发生四次**（REQ-020 / REQ-019 / REQ-021 / REQ-022），且每次形态都比上次更靠前：

| # | 日期 | 形态 | 当时能否靠版本库恢复 |
| --- | --- | --- | --- |
| 1 | 10-04 | 提交前被抹，`\---` 转义 frontmatter + GATE 块整段消失 | 能（`git checkout HEAD --`） |
| 2 | 10-08 | 同上，REQ-019 / REQ-020 | 能 |
| 3 | 10-10 | 提交**后**工作区被格式化（HEAD 版本完好） | 能 |
| 4 | 10-10 | 清单**尚未提交**时被抹，`tier` 一并被退回 `standard` → 连需求 ID 都解析不出 | **不能**：HEAD 里没有，只能从 `git checkout-index` 捞暂存区 |

本次（第 4 次）拿到了**判定侧的完整实证**。审计日志 `.gates/audit/gate-audit.log`：

```
19:53:36 BLOCK-AI-TAMPER-STATUS .../REQ-022-reqguardbin.md
19:53:42 BLOCK-AI-TAMPER-STATUS .../REQ-022-reqguardbin.md
19:53:52 BLOCK-AI-TAMPER-STATUS .../REQ-022-reqguardbin.md
```

判定**完全正确**（GATE 标记行集合被改，一条不差地识破了），但改写照样落地。三处断点各断一环：

1. **L1 判定之后没人听**：拦截脚本 `exit 1`，而 Claude/CodeBuddy 的 PreToolUse 协议把 exit 1 当
   **非阻断错误**，只有 exit 2 才是"拒绝"。于是"记录了，没拦住"——最坏的一种：看着在拦，其实没拦。
2. **入库前根本没人看**：`.gates/requirements/**` 在 `touch.exempt` 豁免区，于是 pre-commit 与 CI
   **都不校验清单结构**，抹坏的清单能一路提交。
3. **改写源头没被收敛**：仓库没有任何"别格式化 `.gates/**`"的配置，格式化器每次都照改不误。

### 为什么第 1 条不是猜测（反证就在本仓库里）

项目**自己**给 Codex/Cursor 做了 `DENY_SH` 包装，把 `exit 1` 转成 `exit 2`，注释写明
"这二者把非 exit 0 视为 fail-open、只认 exit 2 为拒绝"。也就是说**"exit 2 才是工具能识别的
拒绝"是本项目早就知道的事实**——只是 Claude/CodeBuddy 这条直连路径漏了。规范 §附录至今仍写着
"Claude/CodeBuddy 直连 `check`（exit 0/1）"，与实测冲突。本需求补的是既有认知的漏洞，不是新发明。

### 目标

- **G1** 拦截时用**工具能识别的拒绝编码**（exit 2），并在 stdout 输出**结构化的拒绝理由**
  （各工具原生 schema 的 permission decision），让模型知道为什么被拒而不是懵着重试。
- **G2** 入库前做**清单结构体检**：`GATE` 五个包裹块在位、ID 可解析、三段齐备，坏了就拦；
  同一份判定命令能在 CI 复用（L3）。
- **G3** 仓库自带**格式化排除配置**，把改写源头收敛掉。
- **G4** 不改判定语义：`resolve` / `pretool` 的裁决逻辑、放行编码（exit 0 / `AllowDoc`）**一字不动**。
- **G5** `req-guard check` 子命令自身的退出码约定（0 放行 / 1 拦截）**保持不变**——
  变的是**拦截脚本**包裹后的编码，不是判定命令的编码（CI 直接调 `check` 的场景不受影响）。

### 非目标

- **N1** 不把 `.gates/requirements/**` 移出 `touch.exempt`：豁免的语义是"不需要 `GATE:TOUCH`
  声明"（归属问题），本需求只补"结构必须完好"（完整性问题），两条不相干。
- **N2** 不做**自动修复**：体检只拦，不修。被抹的清单怎么恢复是人的决定（`git checkout` /
  重建候选稿），工具自作改动等于让嫌疑人改证据。
- **N3** 不动 Codex/Cursor 的 `deny` 包装（它已经是 exit 2；改造对它幂等）。
- **N4** 不改 Windows 侧 `.ps1` 的**判定**逻辑（只同步退出码编码，镜像关系不变）。
- **N5** 不引入新依赖，`core` 保持零依赖。

## 2. 技术方案

### 总体思路

一句话：**判定本来就是对的，缺的是"让判定被听见"和"入库前再看一眼"** ——
把拦截编码换成工具认的拒绝信号，再在提交前补一道只查结构、不管归属的体检，
最后把格式化器的手从 `.gates/` 上挪开。

### 关键设计

#### 设计 1：为什么必须改编码，而不是加一行 stderr

`stderr` 是给人看的，`exit code` 是给工具看的。现状三者齐全（判定对、审计写了、stderr 打了），
唯独工具没收到"拒绝"这个信号。再怎么丰富文案都改变不了 exit 1 在协议里的含义。

**改 `exit 2` 而非其他值的依据**：`DENY_SH` 的既有注释（Codex/Cursor 侧）已证明 exit 2 是通用拒绝信号；
对 Claude/CodeBuddy 而言 exit 2 同样是协议定义的"blocking error"。二者在 exit 2 上**收敛到同一个值**，
`deny` 包装因此变成幂等（`1|2 → 2`），不需要为它加分支。

#### 设计 2：编码与判定命令**分离**（避免误伤 CI）

| 调用方 | 编码 | 说明 |
| --- | --- | --- |
| `req-guard check`（人 / CI / pre-commit 直接调） | **0 / 1 不变** | CI 的既有约定，改了会静默破坏所有 `--base` 场景 |
| `.gates/hooks/req-guard-check.{sh,ps1}`（AI 工具调） | **0 / 2** | 协议层：2 = 拒绝 |

脚本内部是 `req-guard check ... || exit 2`（把子命令的非 0 统一成 2），
**不改动子命令本身**。这条分离必须写进文档，否则后来者会"顺手统一"成 1 或 2，两种方向都会出事：
统一成 1 → AI 侧继续漏拦；统一成 2 → CI 侧 `--base` 场景的既有断言全变。

#### 设计 3：结构化拒绝（JSON）只做增强，不做主信号

- **只在拦截时**输出 JSON 到 stdout；放行时 stdout 保持干净（避免被当成放行凭证或污染输出）。
- 键名按各工具原生 schema（`hookSpecificOutput.permissionDecision = deny` + reason）；
  工具不认识该键时会忽略它 —— **无害**，因为主信号是 exit 2。
- 顺序上先写 stderr 人读文案（现状保留，AI 看得见），再输出 JSON；两者内容同源，不各写一份。

**为什么不让 JSON 当主信号**：不同工具的 schema 与版本演进不可控，而 exit code 是契约里最稳的一层。
主信号必须是那个"即使对方不认识我也能生效"的。

#### 设计 4：结构体检是**独立脚本**，与 `touch-check` 同构

复用 `HOOK_TOUCH_SH` 的三条理由（见其文档注释）：单一上下文（pre-commit）、无 Windows 镜像负担、
不与 `HOOK_SH` 的 payload 启发式纠缠。

判定命令：`req-guard structure-check`（变更集来源与 `touch-check` 一致：`HOOK_STAGED_FILES` / `--base`）。

检查项（按严重级）：

| 项 | 判定 | 级别 |
| --- | --- | --- |
| `GATE:HEAD` 缺失或 ID 解析不出 | 本次事故形态（连 `status` 都报"未找到需求"） | **Error** |
| `GATE:STEP` 三条（decomposition / solution / testplan）缺任一 | 批准态无从表达 | **Error** |
| `GATE:TOUCH` 包裹块缺失（技术方案已批时） | 变更范围契约失去声明源 | **Error** |
| frontmatter 分隔行被转义（`\---`） | 本次事故形态：元数据整体失效 | **Error** |
| `GATE:AC` / `GATE:AUDIT` 包裹块缺失 | 只影响可追溯性，不阻断裁决 | **Warn** |

**为什么 AC / AUDIT 只 Warn**：既有清单存在空块或历史差异，一刀切 Error 会让存量仓库**集体恒拦** ——
那是"为了加一道墙而把门焊死"，与 REQ-020 修掉的 `Ambiguous` 死循环同类。体检只锁"没了就判不了"的项。

#### 设计 5：体检只检查**本次改动涉及的清单**，不扫全仓

扫全仓会让"仓库里任何一份历史清单不合规"阻断**所有人的所有提交** —— 那是把体检变成共债。
只查变更集内的 `.gates/requirements/*.md`（含归档区），与 `touch-check` 的变更集口径一致。
全量扫描另给一个显式开关（CI 可选），默认不开。

#### 设计 6：格式化排除（收敛源头）

- `.prettierignore`：`/.gates/**`
- `.vscode/settings.json`：对 `.gates/**` 关闭 `editor.formatOnSave`

这不属门禁代码，但**没有它，前两道会一直被触发**——拦得住不等于不用拦，减少触发面本身有价值。

### 兼容性、性能与安全影响

- **兼容性**：`check` 子命令退出码不变（设计 2）；放行编码不变；`deny` 包装幂等。
  **存量仓库需重跑 `install`** 才能拿到新脚本（未升级者行为是今天的 fail-closed，不产生放行）。
- **性能**：体检只扫变更集内清单，常数级；pre-commit 多一次子进程（与 touch-check 同量级）。
- **安全**：拦截面**只增不减**。结构体检是**新增拦截**，不会让任何原本被拦的变成放行；
  唯一的"放松"是把放行时的输出保持干净（本来就没输出 JSON）。
- **一个必须点名的后果**：exit 2 之后，AI 工具侧的"拦截"从"写进去了但留了日志"变成"真没写进去"。
  若某些流程**依赖**"AI 能改清单正文"（AllowDoc 场景）必须确认不受影响 —— 放行路径编码未变，理论上不受影响，
  但仍需 U-0x 显式锁定（放行路径的回归，比拦截路径更容易被忽略）。

### 风险点与回滚方案

| 风险 | 严重级 | 缓解 |
| --- | --- | --- |
| exit 2 被某工具当成"崩溃"而非"拒绝"，表现为恒拦且无原因 | **高** | 设计 3 的双通道（stderr 人读文案保留）；T7 探针实测**必须**给出结论，不实测就不算完成 |
| `scripts/verify_gate.py` 既有场景期望值未同步 → CI 大面积假红 | **高** | T6 明确列入；`verify_gate.py` 在声明范围内；验收门槛要求既有场景全绿 |
| 结构体检误伤存量仓库（集体恒拦） | 中 | 只扫变更集 + AC/AUDIT 降级为 Warn + 新清单（`create` 产物）必须合规（U-0x） |
| JSON 与工具 schema 不匹配 | 中 | JSON 只是增强，主信号是 exit 2；不匹配时工具忽略，行为退回今天的 exit 2 语义 |
| 拦截编码改变导致放行路径回归（AI 写不了正文） | 中 | U-0x 显式锁定 `AllowDoc` 场景仍为 exit 0 |
| 格式化排除不生效（未用 Prettier / 用了别的格式化器） | 低 | G3 是收敛不是根治；前两道仍独立生效 |

**回滚**：T1+T2 是同一处编码的两个面，整体 revert 即回到今天的 exit 1（漏拦但行为已知）；
T3+T4 是新增能力，revert 即取消体检；T5 独立可 revert。

## 3. 测试计划

### 单元测试用例（编号 + 断言点）

**拦截编码（T1 / T2）**

- **U-01** 拦截场景实跑 `HOOK_SH`（PATH 无二进制）→ 退出码为 **2**（不再是 1）
- **U-02** 拦截时 stdout 含结构化拒绝的键（字面量 `permissionDecision` 或本工具约定的等价键），
  且含 `deny`；stderr 仍含人读文案（不因加 JSON 而丢）
- **U-03** 放行场景（假二进制 `exit 0`）→ 退出码 0，且 stdout **不含** `permissionDecision`
- **U-04** `AllowDoc` 场景（payload 写清单正文、状态行未改）→ 退出码 **0**（放行路径不回归，对应风险表最后一行）
- **U-05** `HOOK_PS1` 镜像同步：拦截分支编码一致，且放行分支不含 JSON

**结构体检（T3 / T4）**

- **U-06** 抹掉 `GATE:HEAD` → 退出码 1（体检命令口径），输出含字面量 `GATE:HEAD`
- **U-07** 抹掉三条 `GATE:STEP` → 退出码 1，输出含字面量 `GATE:STEP`
- **U-08** 抹掉 `GATE:TOUCH` 包裹块 → 退出码 1，输出含字面量 `GATE:TOUCH`
- **U-09** frontmatter 分隔行被转义成 `\---` → 退出码 1（**本次事故形态**，对应设计 4 第 4 行）
- **U-10** 合规清单（`create` 刚生成的也算）→ 退出码 0
- **U-11** 仅缺 `GATE:AC` / `GATE:AUDIT` → 退出码 **0** 且输出含告警（Warn 不阻断，对应设计 4 的分级理由）
- **U-12** 变更集里没有清单文件 → 退出码 0（不扫全仓，对应设计 5）

### 端到端用例（编号 + 执行步骤）

- **E-01** 本仓：抹掉某清单的 `GATE:HEAD` 后 `git add` → `git commit` 被 **pre-commit 拦下**
  （现状：能一路提交；这是本需求最核心的由红转绿）
- **E-02** 同一次改动跑 `req-guard structure-check` → 退出码 1，与 E-01 结论一致（两条通道不打架）
- **E-03** 还原后提交成功（证明体检不误伤合规清单）
- **E-04** `req-guard check --staged` 退出码语义不变：拦截场景仍为 **1**（设计 2 的分离锁）
- **E-05** **探针实测（T7）**：在真实 AI 工具会话里对某清单执行"改写 GATE 行"的 Write →
  工具拒绝、文件未被改写；审计仍有记录。**结论（含工具名与版本）必须写回本清单的风险表或审核记录**，
  不实测则本需求不算完成

### 边界 / 异常 / 并发场景

- **B-01** 清单正文（非 GATE 行）被格式化工具改动 → 体检**不拦**（`AllowDoc` 语义不变）；
  本需求只锁结构，不锁排版
- **B-02** 清单处于 `draft`（三段 pending）→ 结构仍须完好，体检照查（起草中更要兜住）
- **B-03** 归档区 `archive/**` 的清单被改 → 同样体检（历史证据不该比活着的更容易被改）
- **B-04** 体检脚本缺执行位 → `install` 补位（沿用 `ensure_executable`，与既有 5 个脚本同一条纪律）
- **B-05** JSON 输出被工具忽略 → 行为退回 exit 2 语义，仍拒绝（设计 3 的兜底方向）
- **B-06** 仓库里同时存在新旧脚本（未重跑 `install`）→ 旧脚本仍是 exit 1（漏拦），
  **不得**因此判定本需求失败；由 `install --verify` 报"脚本版本待更新"

### 回归范围与影响面

- `scripts/verify_gate.py` **全部既有场景**退出码同步 1→2 后必须全绿（T6；这是本项目历来的兼容性门槛）；
- `core/src/gate.rs` 既有用例（约 430 条）全绿；
- `req-guard install --verify` 绿、`ac check` 零 Error、`ids --check` 通过；
- `packaging/scripts/selfcheck.{sh,ps1}` 自检项不回归。

### 验收门槛（全部可机械判定）

- **放行与拒绝各有用例**：U-03 / U-04 / U-10 / U-12 锁放行；U-01 / U-06…U-09 锁拒绝；
- **四类故障形态各有一条**（HEAD / STEP / TOUCH / frontmatter 转义），缺一即视为没覆盖本次事故；
- **E-05 探针必须给出实测结论**——本需求的价值全在"工具真的拒绝了"，只验脚本输出等于没验；
- **不回归**：E-04（`check` 子命令仍 1/0）与 `verify_gate.py` 既有场景全绿，缺一即不合格；
- **不新增依赖**，零新增 `unwrap()`。

### 残留风险（必须随 PR 一起披露）

1. **exit 2 的实测只在一种工具上做过**：本仓库 AI 工具配置覆盖 claude / codebuddy / codex / cursor，
   本需求只能保证编码正确；**各工具是否真据此阻断**，取决于它们的实现，需按工具逐一补探针（B-06 同理）。
2. **结构体检不锁内容**：只认"块在不在、解析得出"，不认"内容有没有漂移"。
   清单正文的完整性仍由 `sum=` / `hsum=` / `doc_write_guard` 三道承担。
3. **格式化排除依赖使用方的工具链**：用 Prettier 与 VSCode 有效，用别的格式化器需自行补配置；
   它是收敛手段，不是根治（G3 的定位）。
4. **工作区仍可能被改写**：本需求保证的是"坏版本进不了库"（HEAD 干净），
   不保证"工作区文件不被改"。恢复成本从"重建 + 重批三段"降到 `git checkout HEAD --`，
   但**未提交的新清单仍无 HEAD 可依** —— 故"新清单尽早 `git add`"仍是必要习惯（第 4 次事故的教训）。
