## 1. 需求分解

### 背景与问题

门禁第 2–5 段实际断言的是「**仓库存在唯一一份当前活跃需求**」（下称 S1 假设）：
`ls .gates/requirements/*.md | sort -r` 后取**第一份**状态非 `done` 的清单，
只对它判三段是否 `approved` 与有无未解决阻塞评论。

S1 的三个前提全部已被证伪：

1. **并发清单**：本仓 `docs/规范/需求编号防冲突命名规范.md` 的立项前提即「团队并行开发时
   本地各建 `REQ-NNN`」，且 `core/src/touch.rs` 早已按「全部未归档清单取并集」实现变更
   范围比对 —— 声明侧已承认多份并存，审批侧仍按单条假设在跑。
2. **逆序 ≠ 最新**：ID 三位补零时逆序近似倒序，但该规范推荐的并行默认档命名
   （`REQ-<owner>-<NNN>`、`REQ-<owner>-<YYYYMMDD>-<rrrr>`）下，字典序最大者恒定胜出。
3. **裁决对象本可以是「本次变更集」**：AI PreToolUse 的 payload 已带 `file_path`
   （`core/src/json.rs` 的 `file_path_of`），pre-commit 有 `HOOK_STAGED_FILES`，
   CI 有 `git diff <base>...HEAD`。

**实测（2026-10-04，临时目录实跑已安装的 `.gates/hooks/req-guard-check.sh`，stdin 接
`/dev/null` 走 pre-commit 形态）**：

| 场景 | 结果 | 方向 |
| --- | --- | --- |
| `REQ-001` 三段 pending + `REQ-002` 三段 approved | exit 0 放行，审计记 `PASS REQ-002.md` | **漏拦** |
| `REQ-001` 三段 approved + `REQ-002` 三段 pending | exit 1，文案「需求 `REQ-002` 尚未通过审核」 | **误锁** |
| `REQ-alice-001` approved（较新）+ `REQ-zoe-002` pending（较旧） | exit 1，文案点名 `REQ-zoe-002` | **误锁，且与「最新」无关** |

漏拦的含义：AI 可以在**零审批**的需求上写代码，而门禁显示绿灯、审计台账声称验证过的是
另一份清单 —— 这是本工具最坏的失效模式（`core/src/gate.rs` 的 `pretool_verdict` 文档注释
称之为「看着在拦、其实没拦」）。

**次生缺陷（同一逻辑的第 6 份副本）**：脚本用 `sort -r` 且**未固定 locale**，而 Rust 侧用
`Path::file_name().cmp(..)`（Unix 字节序）。实测 macOS 上 `REQ-a.md` 与 `REQ-B.md` 两文件
在 `LC_ALL=C` 下选中前者、在 `en_US.UTF-8` 下选中后者 —— 即**同一台机器上脚本与
`touch --declare` 可以指向不同需求**，开发机与 CI 也会得出不同的「活跃需求」。

**与本仓现状的直接关系（缺陷此刻正在生效，非"将来会发生"）**：
`REQ-001` ～ `REQ-008` 共 **8 份未归档清单**已同时存在（部分文件名带 slug 后缀，
如 `REQ-007-apply.md`）。本清单自身就是活样本：

```
$ grep -m1 GATE:HEAD .gates/requirements/REQ-006.md
<!-- (示例输出) GATE:HEAD id=REQ-006 status=approved created= -->
     ↑ 这一行**刻意不写成真正的标记行**：`is_marker_line` 认「以 `<!-- GATE:` 开头」，
       正文里的示例若照抄真标记，会被 `gate_lines` 收进状态行集合，
       于是日后 AI 改这段文字会被判成「篡改状态行」而拦死（REQ-001 P0-2 同款陷阱）

$ PATH="$PWD/target/release:$PATH" sh .gates/hooks/req-guard-check.sh
exit=0（放行）
$ tail -1 .gates/audit/gate-audit.log
2026-10-04 20:22:18 PASS REQ-008-isheading.md
```

即：**本清单零审批而门禁放行**，审计台账声称验证过的是编号更大的 `REQ-008`
（`sort -r` 选不中编号更小的）。推论：任何编号小于当前最大值的清单被打回重审，
门禁都不会察觉。本需求因此不是"提案"，而是**止血**。

### 目标（可机械判定）

- **G1 不漏拦**：任一 AI 写 / 提交 / CI 判定，只要能关联到未过审清单，必须拦。
- **G2 不误锁**：已批清单的开发不被**无关**的未批清单阻断。
- **G3 fail-closed 保持**：判不准就拦；每条拦截必须给出合法出路。
- **G4 单需求存量仓库零行为变更**：只有一份未归档清单时，裁决与今天逐字同语义。
- **G5 判定唯一真相在 core**：脚本不含任何裁决分支（locale 依赖随之消失）。
- **G6 误报可控**：每条拦截消息自含候选清单 + 各自状态 + 三条合法出路。
- **G7 内容冻结与裁决正交**：REQ-002 的「已批准段正文不得再改」必须覆盖**全部**
  非 `done` 清单，**与本需求的候选集无关**。候选集判的是「能不能写」，冻结判的是
  「批准后正文被改没被改」；把冻结绑到候选集就是放宽 REQ-002 = 造一个新的漏拦。

G1 与 G2 是**对立两个方向**，任何只朝一个方向优化的方案都不合格。

### 非目标

- **N1** 不做自然语言质量判断，不引入"这看起来像不像真需求"这类需要人判断的谓词。
- **N2** 不拦 `Bash` 工具里的 `sed -i`、格式化器批量改写（payload 无 `file_path`，
  只能 `Continue`）；这类改动由 pre-commit 与 CI 兜底。
- **N3** 不改 `GATE:TOUCH` 格式契约、不新增第二份「要改哪些文件」的声明源
  （`source_refs` 仍由 TOUCH 单向派生）。
- **N4** 不改 `GATE:AC` 格式契约。
- **N5** 不引入任何外部 crate（core 零依赖铁律）。
- **N6** 不做子仓库 / submodule 内的清单裁决（`requirement::list` 只扫顶层）。
- **N7** 不引入覆盖率工具门槛（本仓无 tarpaulin / llvm-cov / grcov / kcov）。

## 2. 技术方案

### 总体思路

**把门禁的问题本身换掉**：从「我抽到的那份清单批了吗」换成
「这次改动属于哪份清单，那份批了吗」。

前者是一次抽签（结果只取决于文件名序），后者是一次查表 —— 而表**已经存在**：
第 2 段的 `GATE:TOUCH` 声明就是天然的归属证明。裁决逻辑下沉到 core
（新增 `core/src/resolve.rs`），shell 脚本收缩为「取参 + 渲染」。

### 关键设计

#### 1. 解析算法（分层）

```
resolve(root, ctx):
  live = list(root) 过滤（head_status != "done" 且不在 archive/ 下）
  live 为空            → Block(NoRequirement)
  .gates/.bypass 有效  → Bypassed（语义与今天一致，输出 REQ_GUARD_BYPASS=1）

  paths = 按 ctx.source 取变更集（Stdin / Staged / Range / None）
  paths = 归一后剥掉 touch.exempt 命中的路径（豁免集单源）

  idx = { r ∈ live : r.approved }        # 未批清单不建索引
  H   = { r ∈ idx : r.declares 命中 paths 中任一路径 }

  若 ctx.hint 存在且 hint ∉ live            → Block(UnknownSelection)
  若 ctx.hint 存在且 H ≠ ∅ 且 hint ∉ H      → Block(SelectionMismatch)
  否则候选 = H ∪ ({hint} 若存在)
  若候选 = ∅ 且无 hint 且 |live| == 1       → 候选 = live      # G4 退化
  若候选 = ∅ 且无 hint 且 |live| >  1       → Block(Ambiguous)

  failed = 候选中（三段未齐 或 有 open 阻塞评论）的那些
  failed 非空 → Block(StepNotApproved 或 OpenBlockingComment，reqs = failed 的 id)
  否则        → Pass(reqs = 候选 id)
```

三条不可让步的设计决策：

1. **索引只收三段全批的清单**：起草中的需求人们会先写 `core/src/**` 兜着，
   若草案声明进索引，则在已批清单上写代码会因"命中未批清单的 `**`"而被拦 ——
   **必然误锁**。推论：未批清单的声明**没有放行权**。
2. **`--req` / `HOOK_REQ` 只收窄、永不覆盖**：若显式指定能直接覆盖判定，
   它就成了绕过口（指一份已批清单，为未批清单写代码）。故 hint 必须与本次变更集相交。
3. **`|H| > 1` 不是歧义**：重构常同时落在两个已批需求范围内，报"无法确定属于哪份"
   会制造无解误报。拦截只在**候选里确有未过审项**时发生，保证消息永远指名到
   那份真实未过审的清单。
4. **未批清单的草案声明有"零放行权"，但不做指名**（本期刻意不做）：把它当指名依据
   会频繁指错 —— 草案 glob 通常更宽（`**`、`core/src/**`），大量文件都会被指到同一份
   起草中的清单。故命中 0 份时一律报 `Ambiguous` 并列出全部候选，由人判断。
   该权衡的代价（文案可能不够精确）已在 P6 留出可选项。

#### 2. 数据模型（`core/src/resolve.rs`）

```rust
pub struct LiveReq {           // 一份未归档清单的裁决快照（一次读完）
    pub id: String, pub path: PathBuf,
    pub approved: bool,                      // 三段 GATE:STEP 的 status 是否全为 approved
    pub pending_steps: Vec<&'static str>,    // 未过审步骤（文案指名用）
    pub has_open_blocking: bool,             // 未解决阻塞评论
    pub declares: Vec<String>,               // GATE:TOUCH 声明（缺块按空）
    pub sum_errors: Vec<String>,             // 内容冻结违规（REQ-002），与候选集无关
}
pub enum PathSource { None, Staged, Range(String), Stdin }   // 三选一，互斥
pub struct Ctx { pub source: PathSource, pub hint: Option<String> }
pub enum BlockKind {           // 枚举即契约，由枚举覆盖门槛强制其被测
    NoRequirement, UnknownSelection, Ambiguous, SelectionMismatch,
    StepNotApproved, OpenBlockingComment, SumMismatch,
}
pub enum Verdict { Pass{..}, Bypassed{..}, Block{..} }
```

**`approved` 只读 `GATE:STEP` 的 status，不重复实现 REQ-003 的段落实质性判定**：
`core/src/section.rs` 的 `is_section_empty` 已挂在 `requirement` 的审批路径上
（空段在 `approve` 时就被拒），故 `status=approved` 已隐含三段非空。
在 `resolve` 里再判一次段空就是第二处真相，会与 REQ-003 的判据漂移。

**`sum_errors` 与候选集正交（G7）**：内容冻结遍历**全部非 `done` 清单**，
不受 `paths` / `hint` / 候选集影响 —— 它判的是"批准后正文被改没被改"，
与"这次改动能不能写"是两个问题。`judge` 先输出 `sum_errors`，有错即 `SumMismatch`
（先于三段判定，因为"证据已被篡改"比"没审批"更严重）。

**判定分层（可测性前提，同 `touch::check_changes` 的做法）**：

```
judge(live: &[LiveReq], paths: &[String], hint: Option<&str>, mode: MultiMode) -> Verdict
    ← 纯函数：不碰 git、不碰文件系统，R1–R14 全部在此，table-driven 单测覆盖
resolve(root, ctx) -> Verdict
    ← 薄壳：读 live 快照 + 取变更集 + 调 judge + 写审计 + 渲染
```

#### 3. 判定规则表（逐条可单测）

| 编号 | 规则 |
| --- | --- |
| R1 | 无未归档清单 → 拦（`NoRequirement`） |
| R2 | 命中 `.gates/.bypass` 未过期窗口 → 放行并输出 `REQ_GUARD_BYPASS=1` |
| R3 | hint 指向不存在 / 已归档的清单 → 拦（`UnknownSelection`，文案点明"已归档"） |
| R4 | 反查索引只含三段全批的清单 |
| R5 | 变更集先剥 `touch.exempt` 再参与判定（豁免集单源） |
| R6 | 命中集 `H` 非空 → 候选 = `H`（允许 >1） |
| R7 | `H` 为空且 `\|live\| == 1` → 候选 = 唯一 live（G4 退化，与今天同语义） |
| R8 | `H` 为空且 `\|live\| > 1` 且无 hint → 拦（`Ambiguous`） |
| R9 | hint 存在且 `H ≠ ∅` 而 `hint ∉ H` → 拦（`SelectionMismatch`） |
| R10 | hint 存在且 `H = ∅` → 候选 = `{hint}` |
| R11 | 候选中任一未过审 → 拦，且**只**点名未过审的那几份 |
| R12 | 候选全部过审 → 放行，审计记全部候选 ID |
| R13 | `multi.mode: all` 时候选恒为 live 全体（保守档） |
| R14 | 分支名 hint 只在 `H = ∅` 且 `\|live\| > 1` 时参与消歧，且同样受 R9 约束 |

#### 4. 三个上下文的取参（脚本职责，仅此而已）

| 上下文 | 取参 | `PathSource` |
| --- | --- | --- |
| AI PreToolUse | stdin payload 原样透传，路径由 Rust 真解析 JSON（**不得**在 sh 里 `sed` 抠） | `Stdin` |
| git pre-commit | `HOOK_STAGED_FILES`（`git diff --cached -z \| tr '\0' '\n'`） | `Staged` |
| CI / L3 | `--base origin/main` | `Range` |

**`None`（裸 `check`）在多需求仓库下命中 R8 → 拦**。这不是缺陷而是诚实答案
（无变更集就无从归因），但必须在模板层解决：`templates/ci/req-guard-ci.yml` 的
`./req-guard check` 必须改为 `./req-guard check --base "origin/${{ github.base_ref || 'main' }}"`，
并由 `verify_install` 锁住该步骤存在（漏改 = L3 服务端门禁静默失效）。

#### 5. 与 `GATE:TOUCH` 契约的收口（三处，否则裂缝从别处漏出）

| # | 现状 | 改为 |
| --- | --- | --- |
| 1 | `TouchScope::Strict` = 「只比逆序第一份 live」 | 只比本次 `resolve` 选中的那一份；候选 >1 时报 `AmbiguousScope`，**不再静默截断到 1**。**同时删除其文档注释里对「`HOOK_SH` 第 2 段」的引用** —— 该段在 P2 后不复存在，留着就是悬空引用，下一个维护者会回到脚本里找一段不存在的代码 |
| 2 | `touch --declare` 无 `--id` 时取逆序第一份 live | live >1 且无 `--id` → 报错要求 `--id`；live ==1 → 保持现状 |
| 3 | 脚本里两处独立的 `ls \| sort -r` 选活跃 | 全部删除，改调 `resolve` |

**声明源单一性不变**：反查索引读的就是 `GATE:TOUCH`，不产生第二份声明；
`source_refs` 仍由 TOUCH 单向派生。

**已核对、不受本需求影响的两处相邻事实**（列出以免评审重复推导）：

- **REQ-007 的草稿区**：`.gates/drafts/<id>.draft.md` 不在 `requirement::list` 的扫描
  范围（只扫 `.gates/requirements` 顶层），故不进 live 集、不参与反查；且
  `.gates/**` 在 `touch.exempt` 默认集内 → 草稿文件在判定中被豁免。
- **REQ-003 的段落实质性**：`section::is_section_empty` 挂在审批路径上，
  空段在 `approve` 时即被拒，`resolve` 无需也不得重复实现（见 §4.2）。

#### 6. 配置契约（`.gates/req-guard.yaml` 新增块）

```yaml
multi:
  # resolve（默认）= 按本次变更集反查 + 显式消歧
  # all            = 保守档：全部未归档清单都必须三段全批
  #                  （不会漏拦，但会在多需求仓库里互锁，仅在团队明确接受时开启）
  mode: resolve
  # 分支名消歧：分支名含 REQ-<id> 时作为 hint（只消歧、永不放行，R14）。默认关闭
  bind_branch: false
```

**hint 优先级**：`--req <ID>` > `HOOK_REQ` 环境变量 > 分支名（`bind_branch: true` 时）。
读取方式照抄 `touch_scope_strict` 的零依赖块级解析（复用 `yaml_scalar`，无需新解析器）。

#### 7. CLI 契约

```
req-guard check                          # 全局判定（无变更集）
req-guard check --staged                 # pre-commit：staged 文件集
req-guard check --base <ref>             # CI / L3：git diff <ref>...HEAD
req-guard check --stdin                  # AI PreToolUse：从 stdin payload 取 file_path
req-guard check [--req <ID>]             # 消歧（可与上面任一组合）
```

| 约束 | 理由 |
| --- | --- |
| `--staged` / `--base` / `--stdin` **互斥**，同时给两个 → 退出码 2 | 两个变更集混判必然产生无法解释的裁决 |
| `--stdin` 必须显式给出，不做"stdin 非空就自动读" | CI 里 stdin 常被重定向；隐式读会挂死（`scripts/verify_gate.py` 已为 `cat` 挂死踩过一次坑） |
| `touch --declare` 无 `--id` 且 live >1 → 退出码 2 | 不能往错的清单上写声明 |

**渲染契约**：`GateVerdict` 保持 `Pass{summary, detail, bypassed}` / `Block{summary, detail}`
两个形状（`cli/src/render.rs` 的 `print_verdict` 不改签名），变化的只有 `detail` 内容。

#### 8. 脚本改造（`HOOK_SH` / `HOOK_PS1`）

第 2–5 段（`ACTIVE` 定位 / 三段检查 / 阻塞评论 / 评论摘要）**与 §3.5（内容冻结）
一并整体删除**，替换为：

```sh
# ---------- 2) 裁决（判定在 core；脚本只取参与渲染） ----------
if ! command -v req-guard >/dev/null 2>&1; then
  log "BLOCK no-binary"
  echo "[req-guard] ⛔ 拦截：无法裁决（req-guard 不在 PATH），本次写/提交已被阻止。" >&2
  echo "          请把 req-guard 加入 PATH 后重试（安装见 req-guard install）。" >&2
  echo "          确需本次放行：git commit --no-verify / .gates/.bypass 应急窗口。" >&2
  exit 1
fi
if [ -n "${STDIN_DATA:-}" ]; then
  printf '%s' "$STDIN_DATA" | req-guard check --stdin || exit 1
else
  req-guard check --staged || exit 1
fi
exit 0
```

`HOOK_PS1` 逐行镜像（Windows 资产）。这是 G5 之后**仍然存在**的唯一镜像负债，
且只剩这一处。

**必须保留的三件事**（否则是能力回退，不只是重构）：

1. **评论摘要提示**（今天第 5 段每次都打，保证 AI 必然看到 open 评论）→ 移入 `Pass.note`；
2. **`REQ_GUARD_BYPASS=1` 标记**（`gate::BYPASS_MARKER` 契约）→ `Verdict::Bypassed` 路径打印。
   既有单测 `hook_脚本输出绕过标记` 锁的是脚本文本，改造后须改为锁 `resolve` 的输出；
3. **★ 内容冻结（REQ-002）不得回退**。脚本 §3.5 当前的条件是
   `grep -q 'sum=[0-9a-f]' "$REQ_DIR/$ACTIVE"` → 调 `req-guard verify-content`，
   **只覆盖被选中那一份**；而 core 的 `sum_check_detail` 遍历**全部非 `done` 清单**，
   覆盖面本就更大。故 §3.5 删除后由 core 独家承担，**不是能力丢失而是覆盖面扩大**
   —— 但必须显式写明，否则实现者会以为"漏了一段"而把它加回脚本，造成双重校验。

**`SUM_CHECKED_ENV` 与 `verify-content` 子命令的去留**（`gate_check` 现在用它向脚本
传递"core 已自查过 sum"）：

| 对象 | 处置 | 理由 |
| --- | --- | --- |
| `gate::SUM_CHECKED_ENV` | **删除** | 它的唯一用途是阻止脚本重复自查；脚本不再自查后无存在意义 |
| `req-guard verify-content` 子命令 | **保留** | 人可直接用（排查"我明明没改为什么报冻结"）；`verify_install` 仍须检出它存在 |
| `gate::sum_check_detail` | **保留并移入 `resolve`** | 改为填 `LiveReq.sum_errors`，覆盖面扩大到全部非 `done` 清单（G7） |

#### 9. 审计日志格式

| 判定 | 日志行 |
| --- | --- |
| 放行（单候选 / 多候选 / 无受管路径） | `PASS REQ-001` / `PASS REQ-001 REQ-003` / `PASS no-managed-path` |
| 绕过 | `BYPASS-HIT expires_epoch=<epoch> REQ-001 REQ-002` |
| 三段未批 | `BLOCK REQ-002 steps=decomposition,solution` |
| 阻塞评论 | `BLOCK-COMMENT REQ-002` |
| 歧义 | `BLOCK-AMBIGUOUS candidates=REQ-001(approved),REQ-002(pending)` |
| 选择不匹配 | `BLOCK-SELECTION hint=REQ-003 hit=REQ-001` |

**`PASS` 必须列出被裁决的清单**：今天的 `PASS REQ-002.md`（漏拦场景）会让审计读者
以为 REQ-002 就是被开发的那个 —— 这正是该缺陷被长期掩盖的原因。

#### 10. 拦截文案契约（三张牌，缺一即不合格）

`Ambiguous` 是本需求唯一的新拦截面，文案必须一次给全：本次改动路径、候选清单及各自状态、
处置三选一（① `touch --declare <ID> --glob` 补声明（会打回技术方案重审，这是唯一能长期
成立的出路）；② `HOOK_REQ=<ID>` 或 `--req <ID>` 显式指定；③ `req-guard done <ID>` 归档
无关清单）、以及 `git commit --no-verify`（服务端 `--base` 仍会挡住）。

**只有错误信息没有出路的门禁，会走向习惯性绕过** —— 误报是头号死因。

### 兼容性、性能与安全影响

| 维度 | 影响 |
| --- | --- |
| **G4 单需求存量** | `live.len() == 1` 时必走 R7 退化分支，与今天第 2–5 段逐字同语义（含三段检查、阻塞评论、评论摘要）；`verify_gate.py` 现有全部场景退出码不变 —— 这是兼容性硬门槛；场景编号规则见第 3 段「验收门槛」的兼容性门槛 |
| **多需求存量（本仓库即最坏样本，8 份 live）** | 升级即变严。且因 R8 存在，**本仓库的裸 `req-guard check` 在 P2 落地当天就会恒拦**，直到 CI 模板加 `--base`。因此升级顺序必须是"P0 + P5（只读诊断）先行"，见 §6 迁移动作。出路三张牌见 §4.10；声明过窄的清单需先跑 `touch --declare` 补声明 |
| **环境侧** | `req-guard` 不在 PATH 时全拦 —— **该行为已由 REQ-002 落地**（`HOOK_SH` §3.5 的 `BLOCK-SUM no-binary`，实测确认），本需求**不再引入新的收紧**；`req-guard check` 不再执行仓库里的 hook 脚本（否则脚本调 check、check 又调脚本 = 无限递归，故 `run_hook` 退役是**被迫的**而非可选） |
| **性能** | 每次写操作读全部 live 清单 + 建索引，IO 为 O(live 数 × 清单字节数)，匹配为 O(\|paths\| × 命中声明数)。门槛：20 份 live × 每份 200 条声明下单次 `judge` < 20ms（计时断言，不引 benchmark 框架）。超阈值的缓存本期不做 |
| **安全** | 裁决下沉 core 后 fail-closed 方向不变，且**hint 不是绕过口**（R9）。AI 无法通过改写声明获得放行 —— `GATE:TOUCH` 的标记行已在 `gate_lines` 保护内，AI 删块即被拦 |

### 风险点与回滚方案

| 风险 | 处置 |
| --- | --- |
| 歧义分支是新增拦截面，多需求仓库立刻感受到 | 配三张牌；歧义只发生在 `H = ∅` 且 live >1，即"确实无从归因" |
| 拦截消息可能不够精确：不用草案声明指名的代价 | 本期不做指名（P6 可选）；文案必须列出全部候选及状态与命中情况 |
| 纯文档 / 纯 `.gates/**` 提交在多需求仓库会被拦 | 与今天一致（今天也拦），不算回退；**不开"空集即放行"的口子** —— 那会让纯文档提交绕过三段审批 |
| CI 裸 `check` 在多需求仓库恒拦 | P2 同步改 CI 模板为 `--base`，并由 `verify_install` 锁 |
| 裁决从 sh 移到 core 是最大的行为面变化 | 分 P1（纯 Rust 化）与 P2（委托接线）两阶段，每阶段独立可回滚 |
| ★ **误删脚本 §3.5 导致静默回退 REQ-002** | §4.8 已把"内容冻结"列为必须保留的第三件事，并写明由 core `sum_check_detail` 独家承担且覆盖面**扩大**（全部非 `done` 清单 > 单一 `$ACTIVE`）；`verify_gate.py` 增一条场景：已批准段被改时经**委托路径**仍必须拦 |
| ★ **`GATE:TOUCH` 边界依赖 REQ-008 未落地的缺陷** | `section_span` 的围栏缺陷会让 `declares` 为空 → 误拦。已列为落地顺序第 1 条硬约束（REQ-008 → P0） |
| ★ **三方并发改同一批文件**（本需求 / REQ-007 / REQ-008） | §6 合流矩阵：P0 不碰既有文件可立即并行；P1/P2 等 007/008 合流后 rebase |
| `GATE:TOUCH` 缺失的老清单落入歧义分支 | 反查索引对缺失声明按空处理；迁移期用 `touch --declare` 补声明 |
| **P3 收口：候选推导只有一份实现** | 新增 `resolve::owned_by`（「这份改动属于谁」，不问能不能写），`judge` 与 `touch --scope strict` 共用它。两处各写一套就是第二个真相，且必然在「多份清单都声明了该文件」这类边界漂移 |
| **P4 收口：审计行的性质判定只有一份** | 新增 `gate::audit_kind`（`Pass/Block/Bypass/Note/Event`），两个界面只负责上色。界面各自猜前缀的话，改一种前缀就得改两处，而漏改的那处会把拦截显示成放行 |
| **回滚方案** | 按阶段回滚：P0/P5 是纯新增与只读诊断，可单独 revert；P1 是等价重构；P2 是唯一的行为收紧点，revert 后脚本恢复自带判定（届时需同步 revert `verify_gate.py` 场景组与 `verify_install` 断言，否则二者会因"实现了但没接线"而红） |

## 3. 测试计划

### 单元测试用例（编号 + 断言点）

- **U-01** `core/src/resolve.rs` 的 `judge` 为纯函数：不接受 `&Path`、不调 git；
  同一输入两次调用产出相同 `Verdict`（可 `assert_eq!` 直接比对）
- **U-02** `live_snapshot`：过滤 `status=done`、过滤 `archive/` 子目录、解析三段状态与
  `GATE:TOUCH` 声明（缺块 / 未闭合 / `..` 逃逸均按空处理，不 panic）
- **U-03** `judge` 的 R1–R14 逐条 table-driven 用例（用例清单见下方 `GATE:AC` 块）。
  **必须成对覆盖草案声明的两个方向**：① 草案声明不得造成误锁（已批清单范围内的文件
  不因某份未批清单声明了 `**` 而被拦）；② 草案声明不得造成漏拦（落在某份**未批**清单
  声明范围内的文件，不得因另一份已批清单存在而放行）。缺 ② 就是 G1 的对偶洞 ——
  任何人重构 `judge` 都可能悄悄打破 G1 而测试全绿
- **U-04**（**枚举覆盖门槛**）遍历 `BlockKind` 全量变体，维护 `kind → 用例名` 映射表，
  断言每个变体至少被一个 case 命中；新增变体未写测试即红
- **U-05** `core/src/gate.rs`：`HOOK_SH` / `HOOK_PS1` 含 `req-guard check` 委托调用，
  且**不含** `sort -r` / `ACTIVE=` / `verify-content`（反回归锁：防止把单条假设抄回来，
  也防止把已删除的 §3.5 加回去造成双重校验）
- **U-06** `core/src/gate.rs`：`gate_check` 不再执行 hook 脚本；既有
  `gate_check_未安装脚本时报错` / `gate_check_ps1占位存在时unix仍走sh`
  **改写**为「无脚本 / 有 ps1 占位时均给出同一裁决」（锁语义而非实现细节）
- **U-07** `core/src/gate.rs`：`BYPASS_MARKER` 由 `Verdict::Bypassed` 路径输出，
  既有 `hook_脚本输出绕过标记` 用例改为锁 `resolve` 输出
- **U-08** `core/src/gate.rs` 的 `verify_install`：CI 模板缺 `check --base` 即报缺口；
  已安装 hook 脚本仍含 `sort -r` 选活跃即报缺口；`verify-content` 子命令缺失即报缺口
- **U-09** `core/src/touch.rs`：`TouchScope::Strict` 候选 >1 时判 `AmbiguousScope`，
  不再静默截断到 1 份；其文档注释**不得**再出现「`HOOK_SH` 第 2 段」字样
- **U-10** `core/src/touch.rs` 的 `declare`：live >1 且无 `--id` 时返回
  `GateError::Validation`，且不写任何文件
- **U-11** `core/src/resolve.rs`：内容冻结覆盖**全部**非 `done` 清单（构造 2 份已批清单，
  只改与本次候选集无关的那一份 → 仍须 `SumMismatch`），验证 G7 不被实现成"只查候选集"

### 端到端用例（编号 + 执行步骤）

- **E-01** `create` → 填三段 → 逐段 `approve` → `check` 放行（新增 resolve 后仍放行）
- **E-02** 两份 live（一份已批一份未批），对已批那份声明范围内的文件走 AI hook →
  放行（互锁回归）；对未批那份范围内的文件 → 拦（漏拦回归）
- **E-03** `HOOK_REQ=<ID>` 消歧成功放行；`HOOK_REQ` 指向不相交的那份 → 拦
- **E-04** `touch --declare` 无 `--id` 且 live >1 → 退出码 2 并指名须 `--id`
- **E-05** CI 模板副本执行 `check --base <ref>` → 多需求仓库下按 diff 裁决而非歧义
- **E-06** `--no-verify` 提交后，服务端 `check --base` 仍按同一判定抵消本机绕过

### 边界 / 异常 / 并发场景

- **B-01** 非 git 仓库执行 `check --base <ref>` → 报可读错误（`GateError::External`），不 panic
- **B-02** 空 staged 集（空提交）+ live == 1 → 与今天同语义；+ live >1 → 歧义
- **B-03** 清单无 `GATE:TOUCH` 块或块内有 `..` 逃逸条目 → 索引按空处理（落 R7 / R8），不 panic
- **B-04** `archive/` 下的清单既不进 live 也不进索引
- **B-05** 20 份 live × 每份 200 条声明 → 单次 `judge` 耗时断言（见验收门槛）
- **B-06** 同一 fixture 下 `HOOK_SH` 与 `HOOK_PS1` 裁决一致（Windows 与 unix 不得分叉）
- **B-07** `.gates/.bypass` 过期 / 格式非法 → 不走绕过，按 R11 正常判定

### 验收门槛（全部可机械判定）

- **枚举覆盖**：`BlockKind` 每个变体至少被一个单测命中（U-04）。
  **不设行覆盖率门槛** —— 本仓库无覆盖率测量手段，写"行覆盖率 ≥ 90%"就是一条
  不可判定的门槛，与本需求立项理由直接矛盾。
- **兼容性门槛**：`scripts/verify_gate.py` **现有全部场景**退出码不变（G4）。
  场景编号**不在本清单里硬编码** —— 编号已被 REQ-002/003/004/005/007/008 占用到
  34b，写死具体数字必然与后续需求相撞（`docs/README.md` §5.3 同源理由：会腐坏的事实
  不该进契约）。实施时新增场景的编号取当时 `verify_gate.py` 最大号 +1。
- **性能门槛**：B-05 的 20ms / 2s 数字用计时断言（不引 benchmark 框架）。
- **文案门槛**：每种 `BlockKind` 的 message 都必须含候选清单 ID 与三条出路关键字（G6）。
- 用户输入路径零新增 `unwrap()`；解析失败一律走 `GateError::Validation`。
- `cargo clippy --workspace --all-targets -- -D warnings` 零告警；`cargo fmt --all --check` 通过。

  Note / Event（`BLOCK-AMBIGUOUS`、`BLOCK-SUM`、`BLOCK-SELECTION` 都算 Block）。
  **分类只有一份，两个界面只负责上色** —— 界面各自猜前缀的话，改一种前缀就得改两处，
  而漏改的那处会把拦截显示成放行。
- **U-13** `core/src/touch.rs`：`TouchScope::Strict` 在候选 ≠1 时判 `AmbiguousScope`
  （旧语义「只比文件名逆序第一份」已废除：那个选法与本次改动无关，别人的改动在
  strict 下就无人比对）；单需求仓库下 strict 与 union 判定必须一致。
- **B-11** 分支名消歧的边界：分支名含多个 `REQ-` 片段时取第一个并在 note 里告警；
  片段匹配不上一份真实清单（如 `feature/REQ-999`）时直接丢弃，不消歧 ——
  消歧到一份错的清单比不消歧更危险。

### 关于本次修订的通道限制（须知）

本段散文经草稿通道（`.gates/drafts/` + `apply`）修订，而 `GATE:AC` 块内的条目**不经该通道**：
`replace_section` 按位置配对草稿行与原段非 GATE 行，并把原有 GATE 块原样保留、不消耗草稿行，
因此块内条目（验收标准）必须由人经 `amend` 直接改。这不是缺陷 —— `GATE:AC` 是审批的验收基准，
让草稿改它等于开一条绕过 AC 校验的路（`ac check` 只能事后发现）。

P3 / P4 的机械验收项是 `GATE:AC` 块内**最后 11 条**（`strict` 的归属三态、
`touch --declare` 缺省 id 拒绝、`multi.mode` 两档、`multi.bind_branch` 三态、`audit_kind` 分类）。
它们与本段散文配套，缺任一半都不构成完整验收 —— 故须由人经 `amend` 补进块内。

草稿通道的另一处限制同样须知：新增行只能落在**段末**（多出的草稿行被追加到段尾），
无法在段中间插入 —— 位置配对模型决定的。相关改进见 REQ-010。
