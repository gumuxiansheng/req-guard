## 1. 需求分解

### 背景与问题

界面目前**只有写入动作、没有体检视图**。core 里已有一套成型的校验判定，
GUI/TUI 一个都没接。逐条查证：

1. **变更范围契约（`GATE:TOUCH`）在界面上完全不可见**。
   `touch::check`（`core/src/touch.rs:720`）是「本次改动是否都在方案声明的范围内」
   的唯一判定（CLI `touch-check`，`cli/src/main.rs:834-865`）。界面侧零引用。
   更关键的是 `touch::declare`（`touch.rs:791`）——**AI 不能自己扩范围**，
   只能由人类声明（`touch.rs:787-789`：「AI 能自己扩范围的话，
   `--declare` 就是绕过本身」）。也就是说：**界面上现在没有任何合法途径让人类
   应对「AI 改超范围了」这个高频状况**，只能切回终端敲 `req-guard touch --declare`。
   而 `touch --declare` 还会按 `touch.reapprove`（`gate.rs:1527`，本仓库为 `true`）
   把技术方案打回 pending，**这是一个必然发生的高频动作，却只能走 CLI**。

2. **内容冻结只在单段粒度显示一个小徽章，没有全局视图**。
   `requirement::verify_sums`（`requirement.rs:1494`）是「已批准段的正文是否被改过」
   的判定（CLI `verify-content`，`main.rs:942-992`），产出 4 类问题：
   `NotSealed`（已批准但未启用冻结，Warn）、`MalformedSum`（摘要格式非法，Error）、
   `SectionMissing`（标题定位失败，Error）、`ContentChanged`（正文与批准时不一致，Error）。
   界面现在只有 `seal_badge`（`gui/src/app.rs:952`、`ui.rs`）显示单个 `SealState`
   徽章（○未绑定 / ⚠已改动 / ✗无法校验）。**问题在于徽章只回答「这一段冻没冻」，
   不回答「这个仓库整体一致吗」，也没有任何地方汇总 `NotSealed` 这一类 Warn**——
   而 `NotSealed` 恰恰是最容易被忽略、又最影响门禁可信度的状态
   （`requirement.rs:1501-1507`：「批准后该段正文可被任意改动而无人察觉」）。

3. **批量封存（`seal`）在界面上不存在**。
   `seal_many`（`requirement.rs:1603`）与 `seal_all`（`:1587`）支持一次盖多份，
   且注释写明了理由（`:1598-1601`）：「一次人类命令 = 一次人类意图……若每份各自走
   `seal`，L3 下就要逐张换票，那个摩擦大到会有人干脆不 seal」——
   **这正是界面最该提供的形态**。现在 GUI 的「绑定内容摘要」按钮走的是单需求
   `requirement::seal`（`gui/src/app.rs:372`），一份一份来；TUI 的 `s` 键同理
   （`tui/src/app.rs:469`）。

4. **验收标准（AC）机检在界面上没有报告**。
   `ac::check`（`core/src/ac.rs:213`，规则 A1–A12 + 三段实质正文 + 交叉引用）
   目前**只在批准 testplan 时被动拦截**（`requirement.rs:487` 的
   `ensure_ac_compliant`）。也就是说：**审核人在点「批准」之前看不到这份清单的 AC
   是否合规**，只能靠一次失败的审批来发现问题；而更糟的是「告警」类问题
   （A5 混用、A9 不可度量）**根本不阻断**，于是永远不会被发现。

5. **交叉引用体检在界面上没有入口**。
   `touch::check_cross_refs`（`touch.rs:315`）校验技术方案里
   `docs/xxx.md §n` 形式的引用是否仍有效，同样只在批准时被动触发
   （`requirement.rs:563` 的 `ensure_cross_refs_ok`）。
   引用失效最常见的原因是「设计文档小节被改名」（`touch.rs:302-308` 的注释
   明说「最常见」），而这件事在**写方案时**就该看到，不该等到批准才被打回。

6. **审计摘要（`DIGEST`）无法从界面更新**。
   `gate::audit_digest`（`gate.rs:627`）计算本地审计日志的 SHA-256 并写入入库文件
   `DIGEST`（CLI `audit-digest`，`main.rs:443-455`）。界面有审计日志视图
   （`gate::audit_tail(200)`，TUI `L` 键 / GUI「审计日志」按钮），
   但**看完之后无法更新摘要**，于是「台账被人动过」这件事在本地无法自证。

   附带一个安全观察：`DIGEST` 与 `ledger.md` 都在 `touch.exempt` 豁免集内
   （`.gates/req-guard.yaml`），即 AI 可改。REQ-012 已把
   `.gates/req-guard.yaml` 挪出豁免，但这两项**仍在豁免内**。
   本需求**不改豁免配置**（那是 REQ-012 的地盘），但界面能提供
   「一键刷新摘要」至少让人类更容易维持它是真的。

### 目标

- **G1 变更范围体检视图**：两个界面都能展示当前需求的 `GATE:TOUCH` 声明
  （`touch::declared`，`touch.rs:353`）、本次 staged 改动集、以及
  `touch::check`（`touch.rs:720`）的完整问题列表。判定**只在 core**，界面只渲染。
- **G2 界面上可声明变更范围**：提供 `touch::declare` 的界面入口
  （路径/glob + 原因 + 操作人），并**明确提示它会把技术方案打回 pending**
  （读 `gate::touch_reapprove`），因为这是一个「让方案退回重审」的动作，
  用户必须知道自己触发了什么。scope 用 `ScopeCheck::Any`
  （`touch.rs:801` 是 `Any`，不是 `Exact`）——**这是一处与 done/archive 不同的
  scope 形状，不得统一**。
- **G3 内容一致性体检视图**：两个界面都能跑 `requirement::verify_sums`
  并按 4 类问题分组展示（硬伤 / 告警分色），且**汇总视图要跨全部 live 清单**
  （`verify_sums` 是单清单函数，跨清单汇总由界面遍历 `status::req_list` 得出，
  不在 core 加新 API——见非目标 N2）。
- **G4 批量封存**：两个界面都能一次对**多份**清单执行 `seal_many`
  （勾选多份 → 一次确认 → 一次凭据），并提供 `seal_all` 的一键入口
  （对全部非 done 清单）。⚠️ 这里有**一个可实测的硬差异**：`seal_many`
  只在循环外做一次鉴权与一次票据消费（`requirement.rs:1604` 与 `:1613`），
  而单份 `seal`（`:2080`）是**每次调用都消费**（`:2082`）。故 L3 下
  「循环调 `seal`」第 2 份就会因票据已废而失败——界面**必须走 `seal_many`**,
  这不是风格偏好，是 L3 下的功能必然性。
- **G5 AC 机检报告**：两个界面都能展示 `ac::check` 的结果，
  **硬伤与告警分色**，并按 `AcIssueKind` 分类计数。覆盖范围默认
  `AcTarget::All`（全部 live 清单），也可只看当前需求（`AcTarget::Id`）。
- **G6 交叉引用体检**：两个界面都能展示 `touch::check_cross_refs` 对当前需求
  技术方案段的结果，区分「文件不存在」与「小节不存在」两种失效
  （`touch.rs:302-308` 明确要求两种用不同措辞，因为修法不同）。
- **G7 审计摘要可刷新**：界面提供「刷新审计摘要」动作，走 `gate::audit_digest`，
  显示新摘要与写到的路径。
- **G8 只读体检与写入分开**：G1/G3/G5/G6 是**只读体检**（不碰凭据）；
  G2/G4/G7 涉及写或审批，走凭据。界面必须用视觉区分（分组标题或按钮分区），
  让用户知道哪些点下去不消耗审批资格。

### 非目标

- **N1** 不在界面上做变更范围的**自动扩张**。`touch --declare` 是人类动作，
  界面上必须是人类显式点击 + 填原因，绝不做「AI 改了超范围 → 界面自动 declare」。
- **N2** 不给 core 加「全仓库一次性体检」的聚合函数。
  `verify_sums` 是单清单的（`requirement.rs:1494`），
  跨清单汇总用 `status::req_list`（`status.rs:193`）在前端遍历即可。
  理由：core 的职责是「判定单件事」，聚合是展示关注点；
  而给 core 加聚合函数会让它变成「全仓库体检器」，那属于 CI 的职责
  （`.gates/ci/` 与 `templates/ci/`）。
- **N3** 不改 AC 规则 A1–A12 本身，也不改 `ac::lint` 的任何判定。
  本需求只把既有判定结果**显示出来**。
- **N4** 不改 `touch.exempt` 豁免集配置（见背景第 6 条的附带观察，归属 REQ-012）。
- **N5** 不在界面上做 `install` / `install --verify`（门禁安装自检）。
  那属于「工程卫生」类，与 `ids --check` / 返工率 / 票据管理一起，
  由第四份需求覆盖（见其分解）。
- **N6** 不改 `verify_sums` 的严重级划分（`NotSealed` 是 Warn 而非 Error，
  `requirement.rs:1502`）。这条看似可以「顺手改严」，但它是既有设计决定：
  存量清单大量未启用冻结，一次性改严会让门禁全线变红。界面按原级展示。

## 2. 技术方案


### 总体思路

**界面只做「读 core 的判定结果并按严重级分色」，以及「把 core 已有的写动作接上」。
不新增任何 core 判定，不新增 core API。** 关键设计集中在三处：
批量封存必须走 `seal_many`（L3 下的功能必然性，不是风格选择）、
只读体检与写入动作必须用凭据与视觉双重区分、
GUI 顶栏已经满了所以体检必须收进二级面板。

### 关键设计

1. **批量封存为什么必须走 `seal_many`**（G4 的落点，T11/T14 锁它）：
   两份 API 的鉴权与消费时机不同：

   | API | `ensure_human` scope | `consume_credential_if_scoped` 位置 |
   | --- | --- | --- |
   | `seal`（`requirement.rs:2080`） | `ScopeCheck::Any`（`:2081`） | **调用前**立即消费（`:2082`） |
   | `seal_many`（`:1603`） | `ScopeCheck::Any`（`:1604`） | **循环结束后**消费一次（`:1613`） |

   L3 下票据是「用后即废」的。界面若为了「简单」而写成
   `for id in ids { seal(root, id, reason) }`，则第 1 份成功后票据已废，
   **第 2 份必然失败**。`seal_many` 存在的唯一理由就是这件事
   （`:1598-1601` 的注释：「一次人类命令 = 一次人类意图」）。
   故界面的多选封存**必须**调 `seal_many`，且凭据**签发一次、清一次**。
   测试写法：L3 + 1 张票 + 3 份清单 → `seal_many` 三份全成；
   同一场景改成循环 `seal` → 第 2 份起失败（作为对照实验写进单测）。

   `seal_all`（`:1587`）内部就是 `list()` 过滤掉 done 再转 `seal_many`，
   界面的「一键全封」直接调它，不自己遍历（避免第二个真相）。

2. **`touch::declare` 的 scope 与「会打回技术方案」必须显式告知**（G2）：
   `declare` 的 scope 是 `ScopeCheck::Any`（`touch.rs:801`），
   与 done 的 `done:{id}`、archive 的 `"archive"` 都不同——**三处形状各异，
   界面照抄，不要"统一"**。
   界面必须在对话框里预先显示一句「提交后技术方案将被打回 pending 并需重新过审」
   （条件读 `gate::touch_reapprove`，`gate.rs:1527`，本仓库为 `true`）。
   理由：`reopen_step`（`requirement.rs:2248`）会把该段的 `status` 清成 `pending`
   **且同时清空 `sum=`**（`:2269`，注释解释：旧摘要若留着会继续"保护"一份
   已改动的正文，正是本功能要消灭的形态）。
   即：**用户点一次「声明范围」，会连带丢掉那一段的冻结保护**。
   这是个必须让人知道、而不是事后才发现的副作用。
   另外 `reopen_step` 对 done 需求直接拒绝（`:2255-2259`），
   界面应提前禁用按钮。

3. **GUI 顶栏已满，体检必须收进二级面板**（影响范围末条）：
   `render_bottom`（`gui/src/app.rs:678-766`）现在是一条
   `horizontal_wrapped`，已有 8 个按钮（创建需求 / 刷新 / 执行门禁检查 /
   应急绕过 / 审计日志 / 评论 / 绑定内容摘要 + 消息区）。
   再塞 5 个体检入口会把窗口底栏挤成两行以上，窄窗口下更糟。
   改法：新增一个「体检」按钮，打开一个**体检总览面板**，
   里面分四组（变更范围 / 内容一致性 / 验收标准 / 交叉引用），
   每组一个「查看」按钮进入各自的详细列表。
   这样顶栏只 +1 个按钮，且四类体检在同一个地方，不散落。

4. **只读 vs 写入的视觉与凭据双重区分**（G8）：
   - 只读体检（G1/G3/G5/G6）：**不调用 `prepare_credential`**，不消耗审批资格；
   - 写入动作（G2/G4/G7）：调 `prepare_credential`，动作后 `clear_credential`。
   视觉上：体检总览里每组标题旁标注「只读」徽标；写入按钮一律放在对话框内
   （不在总览面板上直接可点），避免误触。
   ⚠️ `audit_digest`（G7）算哪一类：它**写文件**（`DIGEST`）但不是审批类
   （core 侧不调 `ensure_human`，`gate.rs:627`）→ 归为「只读体检 + 一个写入按钮」，
   点它时**不签发凭据**（L0 下也能用），但要在文案上说明它会改 `DIGEST` 文件。

5. **跨清单汇总的形状**（G3 的落点，N2）：
   `verify_sums(content)` 是单清单纯函数。汇总遍历 `status::req_list`
   （`status.rs:193`，返回 `Vec<ReqStatus>`）。但 `ReqStatus` 里**没有正文**，
   只有状态摘要（`status.rs:131-145`）——所以前端要拿到正文得自己读文件。
   前端**已经有**这个能力：`App::body` 存了当前需求的全文
   （`gui/src/app.rs:48`），`requirement::section_of` 用于分段（`:871`）。
   故汇总写法：对每份 `ReqStatus`，读其 `path` 的全文 → `verify_sums` →
   按 `(id, SumIssueKind)` 收集。**读文件路径用 `r.path`（`ReqStatus` 已带）**，
   不自己拼路径（那会引入第二个真相）。

   ⚠️ 性能：N 份清单 = N 次读盘 + N 次 SHA-256。一次性算完并缓存，
   **不进 3 秒轮询**（同 REQ-015 风险 4 的教训）。

6. **TUI 的四类体检怎么塞进有限高度**：
   TUI 有三个 overlay（`Overlay::{Help, Audit, Comments}`，`tui/src/app.rs:82-88`），
   新增 4 个 overlay 会让按键记忆成本上升。改法：新增**一个** `Overlay::Health`，
   内含四个可切换的子标签（用 `1`/`2`/`3`/`4` 或 `Tab` 切），
   而不是四个独立 overlay。这样 `Overlay` 枚举只 +1。

7. **AC 报告的严重级分色必须复用 GUI 既有色板**：
   `ac::AcIssue::severity` 是 `crate::issue::Severity`（`ac.rs:15`），
   GUI 侧映射到 `palette::Tone`（`gui/src/palette.rs`，已过 WCAG AA，
   浅/深底对比度实测值在单测里）。**不新增颜色**——新增就要重测对比度。
   沿用现有映射：Error → `Tone::Danger`，Warn → `Tone::Warning`。
   TUI 侧沿用现有 `gate::audit_kind` 那套着色方式（`ui.rs:298` 附近已有先例）。

8. **`check_cross_refs` 需要段落切片，界面不能自己找标题**：
   `check_cross_refs(root, section, first_line)` 要传**技术方案段的正文与起始行号**，
   段定位用 `requirement::section_span(content, 1)`（**不能用** `section_of`——
   后者定位失败回退整篇，`requirement.rs:73-80` 的注释专门说明机械校验必须用
   `section_span`）。界面**必须**用 `section_span`，定位失败就如实显示
   「第 2 段定位失败」，不得回退整篇（这与 `ac::check` 的既有做法一致，
   `ac.rs:35-40`）。

### 兼容性、性能与安全影响

- **兼容性**：**不改任何 core 公开 API**（本需求最大的兼容性收益）。
  不改清单格式、不改配置、不改 CLI 行为。前端只新增 overlay / dialog 变体
  与面板函数，既有入口全部保留。
- **性能**：
  - `touch::check` 走 `Changed::Staged`，含一次 `git diff --cached`
    （`touch.rs:462`）——与 REQ-014 的口径一致，**放在按钮点击路径，不进轮询**；
  - AC 机检 + 内容一致性 + 交叉引用三项都是读盘 + 解析 + SHA-256，
    N 份清单时是一次性 O(N) 的本地计算。本仓库 N=15，实测在百毫秒量级；
    界面须缓存结果并只在用户显式刷新时重算；
  - **明确禁止**：不得把任何体检放进 `maybe_refresh`（`gui/src/app.rs:161`、
    `tui/src/app.rs:240` 的 3 秒轮询）。理由同上：读盘 + SHA-256 每 3 秒一次
    在大仓库上是持续 IO。
- **安全**：
  - 本需求**新增了两个写动作**（`touch::declare`、批量 `seal`），
    两者都在 core 侧走 `ensure_human` 且 scope 为 `Any`
    （`touch.rs:801`、`requirement.rs:1604`）——即 L3 下需要一张任意范围的票据，
    而界面 `ui_issue_credential`（`auth.rs:257`）在 L3 下**会**签发范围票据，
    故界面能完成这两个动作。这是既有的信任模型（界面 = 人类在场证明），
    本需求不改变它；
  - 风险点在于 `touch::declare` 的语义是**扩大豁免**（把本来会被拦的文件纳入声明）。
    core 的防护是「AI 不能自己 declare」（`touch.rs:787-789`）+ 「声明后打回技术方案重审」。
    界面上这条防线等价于「只有人类能点」，故对话框必须要求显式的 glob 输入与
    原因（**不得预填建议值**，否则用户会不读就点），
    并把「会打回技术方案、且清空该段冻结」写在按钮上方（关键设计 2）。
  - `GATE:TOUCH` 在 `touch.exempt` 豁免集内（`.gates/req-guard.yaml`），
    即 AI 可改声明块本身。REQ-012 已识别这一类问题但未覆盖 `GATE:TOUCH`。
    本需求**不改配置**（N4），但界面上的「查看声明」让人类更容易发现异常扩张——
    这是缓解，不是修复，如实说明。
- **审计**：`touch::declare` 触发 `reopen_step` 打回并写台账；
  `seal` 首次记 `SEAL`、重绑记 `RESEAL` 且带理由（`requirement.rs:2187-2194`）——
  **这条性质很重要**：界面上「一键全封」如果带了理由，
  台账里每份清单都能数出重绑次数与原因（返工率的另一个信号）。
  `audit_digest` 本身写 `DIGEST` 文件。

### 风险点与回滚方案

- **风险 1（高）**：批量封存被实现成循环单份封存 → L3 下第 2 份起必失败，
  界面看起来「部分成功」，用户可能以为只有那一份需要封。
  缓解：T11 的对照单测（`seal_many` 3/3 成功 vs 循环 `seal` 第 2 份失败）；
  界面上批量结果必须显示 `成功 N / 尝试 M`，M>N 时给出明确失败提示。
- **风险 2（中）**：`touch::declare` 的副作用（打回技术方案 + 清空 `sum=`）
  未告知，用户事后才发现那段内容保护没了。
  缓解：对话框顶部固定文案 + 条件显示（读 `gate::touch_reapprove`）；
  验收条目覆盖。
- **风险 3（中）**：体检被放进 3 秒轮询 → 大仓库上持续 IO。
  缓解：设计约束「只在点击时算 + 缓存」，验收条目用计数断言
  「刷新 5 次读盘调用次数为 1」。
- **风险 4（中）**：误用 `section_of` 而非 `section_span` 做机械校验的切片
  → 标题写坏时拿整篇去判，出现「看着在报、其实报错了段」的假象。
  缓解：关键设计 8 明确要求；单测构造「第 2 段标题被改坏」的清单，
  断言界面显示「第 2 段定位失败」而不是给出 AC / 引用结论。
- **风险 5（低）**：GUI 顶栏继续堆按钮导致窄窗口底栏换行错乱。
  缓解：关键设计 3 的二级面板方案；GUI 侧补一条「底栏在 800×600 下单行不换行」的
  离屏渲染断言（复用 REQ-011/013 已有的 `TestBackend` 离屏手法——
  注意 GUI 侧是 egui 离屏上下文，`render_bottom` 可在 `Context::run` 里直接调用）。
- **风险 6（低）**：`severity` 到 `Tone` 的映射新增颜色 → 对比度未测。
  缓解：明确不新增颜色（关键设计 7），复用既有映射并依赖 `palette.rs` 既有单测。
- **回滚**：`git revert` 即可，无数据迁移、无格式变更、无配置变更。
  ⚠️ 但已经通过界面执行过的 `touch::declare` 与 `seal` **不可回滚**
  （声明块与 `sum=` 已落盘，且写了台账）——这与 REQ-015 同理，
  故对话框文案与批量结果展示是防止不可逆误操作，而非防止代码回滚。

### 边界 / 异常场景

- **B1** 没有任何 live 清单：四类体检各自显示明确空态文案，不显示空白面板，

### AC-001
