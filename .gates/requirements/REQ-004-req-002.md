## 1. 需求分解

### 背景与问题

REQ-002 给 `GATE:STEP` 加了 `sum=`，把"批准"绑定到被批准那一段的内容。这条约束
本身是对的，但它没有回答一个实施期必然出现的问题：**测试跑出来的反馈要求改文档时，
走哪条路**。

当前只有两条路，都不对：

1. `reject` → 改 → 重审。机制正确，但**语义错位**：`reject` 表达的是"这段被否决"，
   而实施反馈里绝大多数情况是"方向没错，只是发现漏了个约束 / 措辞要改"。台账里
   两者混为一谈，事后无法回答"哪几段反复返工 = 方案当初没想清楚"。
2. `seal` → 把摘要重绑到当前正文。**这是一条后门**：它跳过重审，且当前实现
   **不限制调用次数**。真实摩擦下（改完发现要重排评审）人类的第一反应就是 seal；
   习惯一旦形成，REQ-002 就退化成"改了再补个摘要"的橡皮章。而 REQ-002 的 G4
   写得很清楚：seal 的正当用途**只有存量清单首次启用**。

还有一个反向缺口：**`docs/设计/` 下的设计文档完全不受任何约束**。改它不触发内容
冻结（冻结只作用于 `.gates/requirements/` 的三段），而 REQ-002 的 `GATE:TOUCH` 里
`docs/设计` 又在声明范围内，连变更范围检查都不拦它 —— 方案段与设计文档讲的是同一
件事，却只有一侧有门禁。

三者叠加的后果：实施期的合法反馈要么被当成"否决"污染台账，要么被当成"擦屁股"
绕过重审。两种都在削弱门禁本身。

### 目标

- **G1** 承诺的变更区分两种语义：新增 `amend`（修订）承载"方向没错、改内容"，
  `reject`（否决）保持原义；两者机制相同、台账事件独立、按段可计数。
- **G2** `seal` 收敛回 REQ-002 G4 写明的正当用途（存量清单首次启用）：
  对已绑定过的清单再 seal 须显式 `--reason`，并单独计数。
- **G3** 设计文档漂移由机械判据兜住：方案段里对 `docs/设计/*.md §N.M` 的交叉引用，
  目标小节不存在即报硬伤。**不做内容冻结**（理由见 N2）。
- **G4** 返工率成为可观测指标：按 (需求, 段) 统计 amend 次数。

### 非目标

- **N1** 不做"微调 vs 实质变更"的风险分级。分级不可机械判定；不可机械判定就等于
  留了个"由人说了算"的开口。REQ-002 的 N4 已就同一点表过态，本需求不推翻它。
- **N2** 不给设计文档加内容摘要冻结。设计文档是持续演化的"记录"：冻结它会逼着人
  为了改措辞去重审需求清单，那是更大的摩擦。记录靠交叉引用一致性，不靠摘要。
- **N3** 不提供任何绕过口：不提供 `unseal`、不提供"白名单段落"、不放宽归一化。
- **N4** 不改验收标准本身的语义规则（那是 REQ-001 的 A1–A12）。
- **N5** 不动 `touch --declare`：代码改了导致方案要跟着改，那条路已存在且正确。

### 子任务拆解

| 编号 | 子任务 | 预估工时 |

| T1 | `requirement::amend`：与 reject 同构（回退草稿、清 `sum=`、必须 `--comment`），台账写 `AMEND` | 2h |

## 2. 技术方案

### 总体思路

**把"承诺的变更"显式分成两种语义，再把"记录"侧的漂移用机械判据兜住。**

`amend` 与 `reject` 的机制完全相同（同一条合法路径：清 `sum=` → 改 → 重审），
区别只在**台账事件的语义与可计数性**。这是本需求的核心判断：实施反馈不需要一条
新的绕过通道，它需要的是 `reject` 这个名字在说真话。

`seal` 的正当用途只有一个 —— 存量清单首次启用。据此按用途把它锁死，而不是加次数
上限（见关键设计 2）。

设计文档不冻结，靠**交叉引用存在性**兜住：方案段里形如 `docs/<目录>/<文件>.md §<编号>`
的引用，若该小节号在目标文件里不存在 → 硬伤。纯机械判定，不涉及语义。

### 关键设计

1. **`amend` 与 `reject` 同构，零新机制**：

   | 维度 | `reject` | `amend` |
   | --- | --- | --- |
   | 状态回退 | 目标段 → pending | 同 |
   | `sum=` | 写 `-` | 同 |
   | `--comment` | 必填 | 同 |
   | 是否必须重审 | 必须 | 同 |
   | 台账事件 | `REJECT` | `AMEND` |

   刻意不新增字段、不新增状态、不新增绕过：两条路在机械上是同一条，只在台账里
   分开。理由：一旦 `amend` 有任何额外能力（免重审、免 comment），它立刻变成
   `reject` 的绕过口，两个动作会迅速合并回去 —— 那就等于什么都没做。

2. **`seal` 的可绑定集合 = 已批准 且 尚未绑定的段**：
   - **仍有段可绑** → 正常放行，记 `SEAL`。这正是 REQ-002 G4 的场景（存量首次
     启用，**含只绑了一部分**）。
   - **一段都没的可绑**（= 已批准内容全部绑定过）→ 须 `--reason`，记 `RESEAL` 并计数。

   两个条件缺一不可，各堵一个洞：
   - 「已批准」堵 `amend` → 改 → `seal` 的绕道。`amend` 清 `sum=` 是为了强制重审；
     若 seal 照绑不误，它就成了「不重新审批也能让改动过的正文重新获得冻结背书」
     的通道 —— 那恰是 REQ-002 要消灭的形态，只是从 AI 手里换到了人手里。
   - 「尚未绑定」才是"首次启用"的**准确**判据。**部分绑定是常态**（存量清单里
     两段是 REQ-002 上线前批准的、另一段后来重审过），把"仍有段没绑"当成
     "已启用过、需理由"会给**补齐**这条正路强加摩擦。

   为什么不用"次数上限"：上限（第 N 次后禁止）仍在鼓励"攒到上限前多擦几次"；
   而"还有没有段没绑"是**事实判断**，不依赖次数，也不给任何人留下"还剩几次"的算盘。

3. **交叉引用语法必须先约定，否则不可机械解析**：只认行内形式
   `docs/设计/<文件名>.md §<数字>(.<数字>)*`。core 提取 `(文件, 小节号)` 对，
   校验两件事 —— 文件存在；文件内存在匹配该编号的小节标题行
   （`^#{1,6}\s*§?\s*3\.8`）。任一不满足 → 硬伤。

   刻意**不做**：不判断引用描述与目标正文是否相符（N1）。
   刻意**不判定注释与围栏代码块里的引用**：那是模板示例与语法说明，不是作者承诺 ——
   模板自带的引导说明里就写着示例引用，判它失效会让**每份新建清单**一出生就欠一条
   硬伤，而噪音会让整条规则连同其他规则一起被忽略。
   刻意**不判定含尖括号的元变量**（`docs/设计/<文件名>.md §<编号>`）：它是本节的语法
   说明。漏掉这条，「定义该语法的规格文档」会被自己的规则判成硬伤（本清单起草时
   即如此）。HTML 注释与代码块抹成等长空格而非删除 —— 行号必须原样保留。
   刻意**不塞进 `touch-check`**：那是"实际改动 ⊆ 声明范围"的集合判定，交叉引用是
   **文档内部一致性**判定；混在一起会让两者的错误信息互相稀释。改为并入
   `ac check` 的问题枚举，与 REQ-003 的 `EmptySection` 同处一个枚举 —— 它们回答的
   是同一个问题："这份清单的内容是不是自洽的"。

4. **返工率只统计、不阻断**：按 (需求 ID, 段) 统计 amend 次数并在 `status` 展示。
   高返工率是需要复盘的工程信号，不是一条可机械判定的硬伤；做成门禁只会催生
   "少写 amend 来刷分"的规避行为。

### 兼容性、性能与安全影响

- **兼容性**：既有台账无 `AMEND` / `RESEAL` 事件，统计按"事件缺失即 0"处理；
  清单格式不变。唯一收紧的是"对已绑定清单再次 seal"（见影响范围）。
- **性能**：交叉引用检查是逐条正则匹配目标文件，量级与引用数同阶，相对 A1–A12
  的全量解析可忽略；不引入新依赖，不新增 IO 轮次。
- **安全**：`amend` 与 `seal` 同属审批类动作，继续走 `ensure_human`，AI 上下文直拒；
  `--reason` 必填，避免"无理由的橡皮章"在台账上留白。

### 风险点与回滚方案

- **风险 1（高）**：`amend` 被当成"免重审的 reject"使用。若实现时给了它任何免重审
  能力，立刻会这样被用。缓解：T1 的验收条目逐条锁死"必须重审"。
- **风险 2（中）**：`seal` 收窄后，"改完确实无需重审"这种真实场景需要 `--reason`，
  略显繁琐。这是**刻意保留**的摩擦 —— 它让擦屁股在台账上留痕。
- **风险 3（中）**：交叉引用误报（作者用别的写法引用文档）造成 annoyance 而被忽略。
  缓解：只认约定的行内形式，其余写法不判定；命中即报，但文案给出如何改写。
- **回滚**：三部分互相独立，可单独回退。T1+T2 回退后 `reject` 语义不变（未改它）；
  T3 回退即恢复"seal 次数不限"；T4 回退即不再判交叉引用。

### 端到端用例

| 编号 | 步骤 | 期望 |
| --- | --- | --- |
| E1 | approve 三段 → `amend --step solution --comment ...` → 改方案段 → 重新 approve → `check` | 放行；台账有 AMEND 且有两条 REVIEW |
| E2 | approve 三段 → 直接改方案段正文 → `verify-content` | exit 1，报 `ContentChanged` |
| E3 | 已绑定清单上跑 `seal` | exit 1，提示须 `--reason` |
| E4 | 已绑定清单上跑 `seal --reason "..."` | exit 0，台账有 `RESEAL` |
| E5 | 方案段引用 `docs/设计/X.md §99.99` 而 X.md 无该小节 → `ac check` | exit 1，报引用失效并指出小节号 |

### 边界 / 异常场景

- **B1** `--comment` 只有空白 → 与缺省同样被拒。
- **B2** 归档（done）清单上的 `amend` / `seal` → 明确报错，不静默生效。
- **B3** 引用指向 `.gates/requirements/` 下的清单 → 不判定（非 `docs/` 前缀）。
- **B4** 目标设计文档被删除 → 报"文件不存在"，与"小节不存在"用不同措辞区分
  （两种情形的修法不同）。
- **B5** 同一引用出现多次 → 逐条报出，不去重（去重会掩盖重复书写）。
- **B6** 同一段先后两次 `amend` → 两次都进台账，计数为 2，以磁盘现状为准。

### 回归范围与影响面

- `core` 全量单元测试；`verify_gate.py` 全部场景。
- 既有 REQ-001 / 002 / 003 清单的 `check`、`ac check`、`touch-check`、
  `verify-content` 须保持既有结论：**新增判定不得把已通过的存量清单判为失败**。
- 门禁脚本资产的阶段序号：新增能力不得插入既有阶段序号之间，否则已安装的旧脚本
  与新 core 的阶段对不上（本项目已经吃过"落盘脚本是旧版"这个亏）。

### 验收门槛

- `cargo fmt --all --check` 与 scoped `clippy -- -D warnings` 零输出。
- `cargo test -p req-guard-core -p req-guard` 全绿。
- `python3 scripts/verify_gate.py` 全部场景通过（新增场景随实现补齐）。
- core 依赖清单不新增第三方依赖。

### AC-001
- Given: 一份三段均已批准且 `sum=` 已绑定的需求清单
- When: 执行 `amend <需求ID> --step solution --comment "补充异常分支"`

### AC-002
- Given: 一份三段均已批准的需求清单
- When: 执行 `amend <需求ID> --step solution` 且不提供 `--comment`
- Then: 退出码为 1，错误消息含 `--comment`

### AC-003
- Given: 一份三段均已批准的需求清单
- When: 执行一次合法的 `amend`
- Then: 台账含 `AMEND <需求ID>` 且不含 `REJECT <需求ID>`

### AC-004
- Given: 刚刚执行过 `amend` 的需求清单
- When: 执行 `verify-content <需求ID>`
- Then: 输出不含 `ContentChanged` 字样，共 0 项硬伤

### AC-005

- When: 执行 `req-guard check`

### AC-006

- When: 执行 `status <需求ID>`
