## 1. 需求分解

### 背景与问题

`GATE:STEP status=approved` 只锁**状态行**，不锁**内容**：批准人与批准时刻之间没有任何
绑定，于是"已批准"会在一段时间后指向另一份内容。

**本仓 REQ-001 是活证据**：testplan 于 2026-10-03 23:15:02 由 Mike_Zhu 批准；同日约
01:30 我把 AC-047 的断言从 `[core/src, cli/src/cli.rs]` 改成 `[core/src, cli/src]`、
去掉 AC-052 的「待确认」、新增 AC-053 —— **门禁毫无反应**，`check` 依然 exit 0，
提交照常通过。那份被批准的测试计划与最终提交的测试计划已经不是同一份。

后果不是"有人偷改"，而是制度性失效：审批退化为某一时点的橡皮图章；AI 可以在批准后
继续改方案与验收标准，而审核人看到的 `approved` 与他当时审的内容再无关系。配合 L1 的
"清单正文可自由编辑"（设计前提：AI 要能写正文），这就成了一条完整的绕开路径。

与 REQ-001 修掉的两条缺陷同源：那一轮消灭了「三段都是空话」（A1–A12 管住第 3 段）与
「方案与代码脱钩」（GATE:TOUCH）；**"批准后仍可改内容"这条尾巴**当时没人管。

### 目标

- **G1** 批准与内容绑定：`GATE:STEP` 记录被批准那一段的摘要，内容变了就红。
- **G2** 三个强制点，越早越硬：AI 写入时拦 → 判定时重算 → pre-commit 与 CI 兜底。
- **G3** 合法改法唯一：`reject` → 改 → 重新 `approve`；**不提供 `unseal`**
  （多一个逃逸口就多一条绕过路径）。
- **G4** 存量清单可平滑补齐（`seal`），且"未启用内容冻结"必须**显式报出**而非静默跳过。
- **G5** 摘要失效与不可校验一律 fail-closed；只有"字段缺失"一种情况放行且必须报出。

### 非目标

- **N1** 不做语义质量判断（"写得清不清晰""方案是否可行"不可机械判定，误报会催生绕过）。
- **N2** 不冻结文件头与 `## 审核记录`：两者由 req-guard 命令写入，且在任何段之外
  （含进去会让 approve 自毁）。
- **N3** 不引入外部依赖算摘要：core 零依赖是铁律，复用既有 `digest::sha256_hex`。
- **N4** 不做风险分级：改一个 checkbox 与改一段方案同样触发拦截。
  代价是会有"为了改个错别字先打回"这种摩擦 —— 但分级判定本身不可机械判定，
  而 false negative 的代价（批准失效）远高于 friction。
- **N5** 本需求**不**解决"第 1、2 段可以是空话"：那是另一条缺陷（见下）。

## 2. 技术方案

### 总体思路

**批准必须绑定"批的是哪一份内容"。** 给 `GATE:STEP` 行加一个 `sum=` 字段
（该段正文的 SHA-256），判定时重算并比对。

摘要**只覆盖被批准的那一段**，不覆盖整篇。理由是鸡生蛋问题：批准任何一步都会
改写文件头（GATE:STEP 行）并往 `## 审核记录` 追加条目，若摘要覆盖整篇，
则"批准后面试盘"会立刻让自己刚写的摘要失效。分段摘要天然避开：文件头与审核记录
都在任何一段之外。

### 关键设计

1. **摘要只覆盖该步对应的段**（`section_span`），归一化只做两件事：
   行尾统一 `
`（Windows CRLF 必须归一，否则同一内容在两个平台算出两个摘要）、
   去尾部换行。**不做**去空白之类的"更友好"归一 —— 那些归一会让真实改动藏起来。
2. **三个强制点，越早越硬**：
   - **写入时**（`doc_write_guard`）：AI 覆盖写入若改动了"已批准且有摘要"的段 → 直接拦。
     这是最强的一层：改都写不进去。
   - **判定时**（`gate_check`）：pre-commit / CI / 手动 `check` 全部重算比对。
     兜住人类绕过 AI 直接编辑的情况。
   - **摘要缺失时明确报出**，不静默跳过（见「存量与失败模式」）。
3. **合法改法只有一条**：先 `reject`（清空该步摘要）→ 改 → 重新 `approve`。
   **不提供 `unseal`**：多一个逃逸口就多一条绕过路径，而 `reject` 本身就是
   "我要改这段"的正确语义，且带 `--comment` 留痕。
4. **摘要的生命周期跟着状态走**：`approve` 写入本次内容的摘要；
   `reject` 写 `sum=-`（被拒绝的内容没有"已批准"可保护）；
   `touch --declare` 打回 solution 时同步清空 —— 否则契约扩张后，旧的摘要
   仍在保护一份已被改动的正文，那正是本需求要消灭的形态。

### 兼容性、性能与安全影响

- **兼容性**：清单格式新增一个**可选**字段 `sum=`。存量清单无该字段 → 判定时
  **明确报出"该步未启用内容冻结"**并放行（不静默），配套 `req-guard seal` 补齐。
  不选"缺字段即失败"，因为那会把所有存量清单一步卡死在 `check` 上。
- **性能**：每个已批准段算一次 SHA-256（core 里已有 `digest::sha256_hex`），
  单文件量级，微秒级；`HOOK_SH` 不做摘要计算，改为调用 `req-guard verify-content`，
  与第 0 段 `hook-check` 同一形态（缺二进制即 fail-closed）。
- **安全**：摘要不引入新凭据。`seal`（给存量清单补摘要）走 `ensure_human` ——
  否则 AI 可以给自己批过的清单补摘要，等于自证。

### 风险点与回滚方案

| 风险 | 处置 |
| --- | --- |
| **归一化不足/过度**：不足则同一内容跨平台算出不同摘要（误报）；过度则真实改动被藏起来 | 只归一两行尾与尾部换行；两者都写进单测（含 CRLF 用例） |
| **`review` 自毁**：approve 自己写 `sum=`，若摘要范围含该行则自我失效 | 摘要只取段内正文，文件头在任何段之外；用 `review` → `verify` 的端到端用例锁住 |
| 摘要缺失被当成"通过" → 静默失效 | 判定输出显式列出"未启用内容冻结"的段；`verify_install` 另报未 seal 的清单 |
| `touch --declare` 扩张后旧摘要仍保护已改动的正文 | `reopen_step` 同步清空 `sum=` |
| 摘要比较需要 git 无关 | 只用 `section_span` + SHA-256，不依赖 git |

**回滚**：去掉 `sum=` 字段与相关判定即可退回现状（清单内容不受约束）。
旧摘要字段留在文件里无害 —— 判定侧改为"字段缺失即跳过"。

## 3. 测试计划

### 验收标准

### AC-001
- Given: 某清单第 2 段已 approve，GATE:STEP 的 sum= 为该段当前内容的 64 位十六进制摘要
- When: 执行 req-guard check
- Then: 退出码 0，stdout 明示 testplan 之外各段的摘要均一致

### AC-002
- Given: 某已批准且带摘要的清单，第 3 段正文被追加了 1 行
- When: 执行 req-guard check
- Then: 退出码 1，并指名该段摘要不一致、给出期望值与实际值的前 8 位

### AC-003
- Given: 同一份清单内容在 LF 与 CRLF 两种行尾下
- When: 分别计算该段摘要
- Then: 两个 64 位摘要逐字相同（行尾归一生效）

### AC-004
- Given: 某已批准且带摘要的清单的第 2 段被改动
- When: AI 用 Write 整篇覆盖该清单
- Then: 退出码 1 拦截，理由含先 req-guard reject 再改，且该段正文在磁盘上逐字未变

### AC-005
- Given: 某已批准且带摘要的清单，第 1 段（pending，未冻结）被改动
- When: AI 用 Write 整篇覆盖该清单
- Then: 退出码 0 放行（未批准的段不受内容冻结约束）

### AC-006
- Given: 某已批准且带摘要的清单，第 2 段被改动后又改回原样
- When: 执行 req-guard check
- Then: 退出码 0（摘要只认内容、不认改过几次）

### AC-007
- Given: 某清单第 2 段已 approved
- When: 执行 req-guard reject REQ-002 --step solution
- Then: 退出码 0 且 GATE:STEP 的 sum= 变为 -，此后该段可自由编辑

### AC-008
- Given: 某清单第 2 段的 sum= 为 - 且状态为 rejected
- When: 修改该段正文后执行 check
- Then: 退出码 0，且输出提示该段未冻结、不提供内容一致性保证

### AC-009
- Given: 某清单第 2 段已 approved 且带摘要
- When: 执行 req-guard touch --declare 扩张范围
- Then: solution 打回 pending 且 sum= 清为 -，旧摘要不再保护已改动的第 2 段

### AC-010
- Given: 某存量清单的 GATE:STEP 行没有 sum 字段
- When: 执行 req-guard check
- Then: 退出码 0，输出逐条列出未启用内容冻结的步骤，并提示 req-guard seal

### AC-011
- Given: 某存量清单已 approved 且无 sum 字段
- When: 执行 req-guard seal REQ-002
- Then: 退出码 0，三个步骤的 sum= 按当前正文补齐并写 SEAL 审计事件

### AC-012
- Given: 当前处于 AI 执行上下文
- When: 执行 req-guard seal REQ-002
- Then: 退出码非 0（seal 须人类在场，否则等于自证已批内容）

### AC-013
- Given: 某已批准段被删除其二级标题
- When: 执行 req-guard check
- Then: 退出码 1，报该段无法定位因而摘要无法校验，不得静默放行

### AC-014
- Given: 某清单三段均 approved 且摘要一致
- When: 依次执行 approve decomposition / solution / testplan
- Then: 3 段摘要在 3 步之后仍全部一致（approve 不自毁）

### AC-015
- Given: 某清单第 2 段带摘要且状态为 approved
- When: 执行 req-guard verify-content

### AC-016
- Given: req-guard 二进制不在 PATH 且某已批准段带摘要
- When: 执行 git pre-commit
- Then: 退出码 1（内容冻结 fail-closed，不得因缺二进制而放行）
### AC-017

### 单元测试用例（编号 + 断言点）

- **U-01** `digest`：同一段 LF/CRLF 摘要相同；尾部多一个换行也相同
- **U-02** `requirement::section_sum`：只取段内正文，文件头与 `## 审核记录` 不参与
- **U-03** `requirement::review`：approve 写入本次摘要；reject 写 `sum=-`
- **U-04** `requirement::reopen_step`：打回时同步清空 `sum=`（否则旧摘要保护已改动正文）
- **U-05** `gate::doc_write_guard`：改已冻结段 → 拦；改 pending 段 → 放行
- **U-06** `gate::gate_lines` 不受影响（`sum=` 在标记行内，已随状态行整体保护）
- **U-07** 摘要缺失 → 判定放行但输出"未启用"，不静默
- **U-08** 段标题被删 → `SectionNotFound` → 报 fail-closed
- **U-09** `seal`：补齐三步摘要 + 写 SEAL 审计事件；AI 上下文下拒绝
- **U-10** 端到端：approve 三段 → check 绿 → 改一段 → check 红 → reject → 可改 → 重审 → 绿

### 端到端用例（编号 + 执行步骤）

- **E-01** 正常流程：填三段 → 逐段 approve → `check` 放行 → 提交通过
- **E-02** AI 改已批准段 → PreToolUse 写入即拦；改 pending 段 → 放行
- **E-03** 人类直接编辑已批准段 → `git commit` 被 pre-commit 拦（`verify-content`）
- **E-04** `--no-verify` 绕过 → CI 的 `check` 仍红（服务端抵消）
- **E-05** `touch --declare` → solution 打回且摘要清空 → 改动被放行 → 重审后摘要更新

### 边界 / 异常 / 并发场景

- **B-01** 清单带 BOM 或 CRLF → 摘要与判定均正常
- **B-02** 段内只有标题、没有任何正文 → 摘要仍可算（空正文有确定摘要）
- **B-03** 两份清单内容相同 → 摘要相同（摘要不含 id/path，不做跨清单区分）
- **B-04** 归档（done）清单 → `check` 跳过，不校验其摘要
- **B-05** 摘要字段被手工填成非法长度 → 视为"无法校验"并报出，不当通过

### 回归范围与影响面
