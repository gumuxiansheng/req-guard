## 承接 9-29：令牌熵加固（方案 B 在 Windows 上的强度缺陷）

**发现**（回答"令牌如何签发"时顺带审查 `core/src/token.rs`）：
`random_hex` 的弱熵回退把 `now` / `pid` 在循环**外**取一次，32 字节全由同一个 128 位状态派生
（`*b = (mix >> ((i % 8) * 8)) as u8`，mix 只随 i 变）→ **实际熵仅约为"取时间那一刻"的抖动**。
而 `~/.config/req-guard/guard.cfg` 里的哈希与 AI 同用户可读 → AI 可**离线暴力猜原文**再自批，
方案 B 在 Windows 上强度不足（Unix 走 /dev/urandom 不受影响）。

**修复**：
- `random_hex`：改为**逐字节重新采样** `SystemTime` 纳秒抖动 + 混入 **ASLR 栈变量地址**
  （每次进程启动不同、外部不可观测）+ 滚动 state 累积，避免整串由单一状态派生。
- 新增 `token::entropy_strong()`（探测能否读 /dev/urandom），CLI 在弱熵平台打印
  "强度低于内核 CSPRNG，guard.cfg 哈希与 AI 同用户可读，建议缩短 TTL"。
- 补两个单测：连续 8 次调用不得全同（守熵退化）、`entropy_strong` 与平台一致。

**验证**：`fmt --check` / `clippy --workspace --all-targets -D warnings` / `cargo test --workspace`
全绿（core 103 + tui 8）；Windows 熵警告实测出现；端到端 `C:/tmp/rg-token-demo.sh` 复跑通过。

## 令牌签发与 GUI 的口径（已向寇工说明）

- 签发：`token issue [-ttl N]` → `ensure_token_admin`（AI 上下文拒 / 已有令牌须出示当前令牌 /
  严格模式须 TTY 挑战）→ 生成 32 字节原文，只打印一次，落盘仅 SHA-256 哈希 + 到期时间。
- GUI 在严格模式下审批被拒的根因：`ensure_human` 判级里 `is_tty()` 为 false（GUI 无交互终端），
  且无令牌 → 拒。唯一干净的解法是**从已 `export REQ_GUARD_TOKEN` 的终端启动 GUI**（子进程继承）。
  ⚠️ 不可把令牌写进**系统级**环境变量——AI 同用户会继承，令牌即失去意义；只在该终端会话内临时 export。
