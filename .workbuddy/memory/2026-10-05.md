## SDD（spec-kit 类）与 req-guard 的关系与单源路由（结论）

问题：req-guard 与 SDD 工具是否功能重复？SDD 生成的规格会不会与 req-guard 要求的文档形成多源脑裂？

结论（已与寇工对齐口径，未落文档前先记这里）：
- **功能不重复**：SDD = 文档生成 + 一致性建议（`/analyze` 只读、不拦截）；req-guard = 流程判定 +
  fail-closed 硬拦截（hook 拦截、逐段批准、批准即冻结 `sum=`、cross-ref、touch-check）。层级不同。
- **内容层确实重叠**（what/how/verify 三段同时出现）；脑裂风险为真，但属**路由问题**，可收敛。
- 单源路由（唯一真相 = `.gates/requirements/REQ-xxx.md`）：
  - `spec.md` → 第 1 段 需求分解（FR 编号可留，验收口径在第 3 段落成 GATE:AC）
  - `plan.md` → 第 2 段 技术方案，**必须带 GATE:TOUCH**；架构细节不再抄进方案段，只引用
    `docs/<目录>/<文件>.md §<数字>`
  - `design.md / research.md / data-model.md / contracts/ / quickstart.md` → 落 `docs/设计/`，
    由方案段引用（cross_refs 只认这一种写法，落别处会判 `target_missing` 而拒绝批准）
  - `tasks.md` **不等于**第 3 段 测试计划 → SDD 任务清单不入库，AC 只挑可观测条目改写
  - `constitution.md` → 流程相关条款收进 `docs/规范/`，避免与 req-guard 规范两份准则
  - SDD 的 `specs/` 目录只当草稿源（等价 `.gates/drafts/REQ-xxx.draft.md`），
    apply 进清单后不留副本，否则双源。
- **命名澄清**：README §「规格绑定代码（SDD 契约）」里的 SDD **不是** SDD 工具，指清单 frontmatter
  `review_policy=codebound` + `source_refs` 与 doc-guard FRS 族逐字对齐的约定。

两条已有的机械强制力可直接用来约束 SDD 输出位置（不用新写规则）：
1. `cross_refs` 只认 `docs/<目录>/<文件>.md §<数字>(.<数字>)*` → SDD 细粒度文档必须落 `docs/设计/`。
2. `ac::lint` 对第 3 段硬拦（编号连续 + Given/When/Then） → tasks.md 直接当测试计划批不出去。
