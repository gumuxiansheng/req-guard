### 踩坑与实测（重要）
1. **机器的 `~/.config/req-guard/guard.cfg` 是全局开关**：为了跑「L3 下循环 seal 必坏」那条
   判决性实验，我在 GUI 测试里签了一张 scoped 票 → `token_mode()` 对**整个进程树**变真 →
   同一二进制里所有 L0 夹具的 `approve` 开始要凭据，**两条无关用例被带红**。
   处置：撤掉那条 L3 用例，改为**源码形状断言**（`seal_selected` 必须含 `seal_many(`、
   不含 `requirement::seal(`，且 prepare/clear 各一次）。并把我制造的残留
   `guard.cfg` 移到 `guard.cfg.req016-test-residue`（**用户需知**：那是我的测试产物，
   内容 `scope=seal / used=true`；原始文件若存在也已被覆盖）。
   ➜ 纪律：**不要在并行测试二进制里签发真票**。要判 L3 语义就放 core，或只断言调用形状。
2. **`HOOK_STAGED_FILES` 是进程级的**：用它造暂存区会污染并行跑的别的用例（实测把
   `三段通过后显示已解锁` 带红）。改用**真 git 索引**（`git init` + `git add`），按 root 隔离。

   120 列下会把行尾的 `已解锁` **截断成 `已解`**（实测连续 4 次红）。
   修法：① 身份区挪到 footer 的空白行；② 状态旗标 `已解锁/未解锁` **排到项目路径之前**
   ——它是这行里最不能丢的信息。
