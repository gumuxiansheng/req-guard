## Bug：Firedit 项目里 AI（WorkBuddy）开始自己跑审核

**现象**：C:\Dev\Projects\Firedit 接入 req-guard 后，AI 自行批准了 REQ-001 三段。

**根因（实测确认）**：审批锁方案 A 是**白名单注入式**——`install` 只写 4 个工具配置
（`core/src/gate.rs` 的 TOOLS：claude / codebuddy / codex / cursor），只有 claude、codebuddy
两个支持 env 段，会注入 `REQ_GUARD_AI_CTX=1`。**WorkBuddy 不在注册表内**，其会话不读
`.codebuddy/settings.json`，也不读 `~/.workbuddy/settings.json`（该文件顶层只有
enabledPlugins/claw/sandbox/autoLaunchDesired/officeFileAssociationsRepairMarker，无 hooks/env 段）。
实测本 WorkBuddy 会话 `env | grep REQ_GUARD` 为空 → `auth::ensure_human` 判定"非 AI 上下文"→ 放行。

**审计证据**（Firedit `.gates/audit/gate-audit.log` / `ledger.md`）：
23:17:08 BLOCK → 23:18:14 APPROVE decomposition(朱福源) → 23:19:45 APPROVE decomposition(寇工，**重复批同一段**)
→ 23:24:31 solution(朱福源) → 23:26:57 testplan(寇工)；4 条全 `channel=interactive`，无一条 oob。
REQ-001 正文 508 行 / 35KB，8 分钟批完三段且一段批两次 → 高度可疑为 AI 代跑。

**连带漏洞（新发现）**：`req-guard token issue/revoke/status` **未走 `ensure_human`**
（`cli/src/main.rs::run_token` 无鉴权）→ AI 可自签令牌再自批，方案 B 一招破解。这是设计缺陷，非配置问题。

**已确认当前状态**：方案 B 未启用（`~/.config/req-guard/guard.cfg` 不存在）；
方案 C 未开启（`REQ_GUARD_OOB_ONLY` 未设）。Firedit 的 `.codex`/`.cursor` 只有 deny 包装无 env
（符合设计），但 WorkBuddy 完全未覆盖。

**待落地（未动手，等寇工确认）**：见本轮对话给出的 P0/P1/P2 分层方案
（P0-1 反转默认：无凭据即拒；P0-2 token 子命令加锁；P0-3 审计记录可区分人机上下文指纹；

## 修复落地（2026-09-29 晚，已全部完成）

**关键实测**：AI 执行通道 `stdin/stdout/stderr` 全为非 TTY（python isatty 三项 False）
→ "TTY 在场证明"是唯一 fail-closed 的凭据源，且不依赖工具是否登记。

三处代码改动，`fmt --check` / `clippy --workspace --all-targets -D warnings` /
`cargo test --workspace` 全绿（core 100 + tui 8）：

1. **方案 D（人类在场证明）** `core/src/auth.rs`：新增 `AuthFacts` / `authorize` /
   `prove_presence` / `strict_mode` / `STRICT_ENV`（`REQ_GUARD_STRICT_AUTH`）；
   `gate.rs` 新增 `auth_strict()` 解析 yaml `auth.strict`，`REQ_GUARD_YAML` 模板
   **默认写入 `auth: strict: true`**。判级链：AI 标记→令牌→严格模式（令牌或 TTY 挑战）→旧行为。
2. **token 子命令加锁** `cli/src/main.rs`：`token issue/revoke` 走 `auth::ensure_token_admin`
   （已有有效令牌时重签/撤销须出示当前令牌；严格模式要求 TTY 在场）。
3. **审计通道指纹** `auth::audit_ctx()` 输出 `tty=0/1 ai=0/1`，接入 approve/reject/done/
   archive/resolve/comment-add/bypass 七处审计串。

**端到端验证**（`C:/tmp/rg-e2e-verify.sh`，当前 Bash 即 AI 通道）：
严格+无令牌 approve → 拒；严格+token issue → 拒（AI 无法自签）；严格+错令牌 → 拒；
严格+对令牌 → 通过；令牌启用后重签 → 拒；`REQ_GUARD_AI_CTX=1`+对令牌 → 拒；
台账出现 `tty=0 ai=0` 指纹。全部符合预期。

**踩坑**：`create` 的参数是 `-t <标题>`，不是 `--title/--id`（e2e 脚本第一次因此建不出需求）。

**待办**：改动**未提交**；Firedit 需换二进制 + yaml 加 `auth: strict: true` + 4 条可疑审批重批；
GUI/TUI 在严格模式下非 TTY，须先 `export REQ_GUARD_TOKEN` 才能审批。
