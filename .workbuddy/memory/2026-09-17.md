# 2026-09-17 req-guard 工作日志

## GUI：批准完需求分解后无法展开技术方案（寇工报的线上问题）

### 现象
cycooj 项目 GUI 里批准完「1. 需求分解」后，「2. 技术方案 / 3. 测试计划」点不开、无法继续批准。
先查数据文件 `.gates/requirements/REQ-001-cycoo--gates-toolkit.md`：三段 GATE:STEP 行齐全
（decomposition=approved / solution=pending / testplan=pending）→ **排除数据问题，纯渲染缺陷**。

### 根因（gui/src/app.rs::render_center）
1. `CollapsingHeader::open(Some(i == app.step))`：**`open(Some(..))` 每帧强制开合状态**。
   egui 0.36 源码 `begin()` 里是 `if let Some(open) = open { ... } else if clicked { toggle }`
   —— 传了 Some 就**完全忽略点击**，非选中段展不开。
2. `approve()` 成功后 `app.step` **不前进**，光标永远停在段 1，批准/打回按钮也只挂在段 1 下。

### 修复（三处）
- 点击标题 = 选中该段：`let resp = ...show(...); if resp.header_response.clicked() { app.step = i; }`
  （`header_response` 是 `ui.interact(rect, id, Sense::click())`，即使被强制开合，`clicked()` 仍然为真）
- 新增 `jump_to_reviewable()`：批准后光标移到第一个未通过的段（`position(|s| !s.state.is_approved())`）
- 已通过的段不再显示批准/打回按钮（`s.state != StepState::Approved`），避免误导

### 验证（真机 + 端到端点击，见 target/gui-verify-*.png、target/e2e-*.png）
- 初始态：三段全部渲染、已通过段不再挂按钮
- 点击段 2 标题 → 段 2 展开并出现批准/打回
- 临时项目端到端：填审核人 Kou → 确认批准 → 底栏「已批准 REQ-001 / 需求分解」、
  段 1 变 ✓ 自动收起、光标自动前进到段 2 并展开、进度 1/3
- `cargo test --workspace`：core 71 + tui 5 全绿；`clippy -D warnings`、`fmt --check` 零告警

### 本机 GUI 自动化踩坑（可复用）
- **PowerShell `Add-Type` 编译 C# 会被安全策略拦截** → 用 Python venv + ctypes 调 user32。
- **pyautogui.click 在本机被静默吞掉（不报错但无效果）**，改成 ctypes `SendInput` 才真正注入。
- **坐标有 (11,6) 物理像素系统性偏差**：`GetWindowRect` 含 DWM 不可见边框/标题栏，
  egui 逻辑坐标 = (物理 − 客户区原点)/1.5。小按钮（51×31 物理）一偏就脱靶，
  大按钮/整行标题不易察觉 → 曾误判"弹窗渲染坏了"。校准方法：加临时 `eprintln` 探针打印
  `response.rect` 与 `ui.input(|i| i.pointer.latest_pos())`，反推客户区原点。
- **taskkill 输出是 GBK**：Python `subprocess(text=True)` 必须 `encoding='gbk'`。
- 后台起 GUI 必须用 bash 工具的 `run_in_background`；普通 `&` 会随 shell 退出被带走。

## 新增设计文档：AI 协同审核 GUI 自动弹出技术方案.md

- 寇工提需求：让多种 AI 系统检测审核 GUI 存在并自动弹出供人工审核；要求覆盖 4 点（存在性检测、触发条件与时机、多 AI 防重复/冲突协调、结果回传）。
- 方案核心：**一个协调器（审核请求桥 `req-guard ui --request`）· 一份真相（core + .gates/ 文件）· 一把锁（审批 token/OOB）**。
- 关键机制：三层探测（能力/环境/活性）；GUI 单实例 + 原子抢锁 + IPC 信道；以 `(req_id, step)` 为去重键的"审核请求注册表"收敛多 AI 请求为一次人工决策；结果经 IPC 主通道 + 文件真相兜底回传；CI/无 display 不弹窗降级到 CLI 指引。
- 全部复用现有设施（ui 自动探测、core API、L1/L2/L3、审批锁），不新增门禁判定逻辑。

## 上述方案的代码核查（逐条对照源码）→ 新增《AI协同审核GUI落地清单.md》

- **B1（硬阻塞）拦截原因无结构化**：`GateVerdict::Block{detail}` 只是脚本 stderr 中文原文（gate.rs:495,606；脚本 1327-1363），
  唯一机器可读标记是 `REQ_GUARD_BYPASS=1`(gate.rs:1310)。方案依赖的"分类 + req_id/step 去重键"今天拿不到。
  且脚本里的"活跃需求"是**文件名** `$ACTIVE`(gate.rs:1318) ≠ `GATE:HEAD id=` 的需求 ID → 去重键口径必须统一到需求 ID。
- **B2 零依赖下无跨平台 IPC**：Windows 命名管道不在 std、Unix socket 非 Windows 原生 → 只能**回环 TCP(127.0.0.1)+动态端口写锁文件**。
- **B3（最致命，方案原未意识到）**：AI 会话被注入 `REQ_GUARD_AI_CTX`(gate.rs:831)，AI 起的 GUI 会继承它 →
  `requirement.rs:197`→`auth::ensure_human`(auth.rs:59) 会拒绝人类在 GUI 里的批准，**功能自废**。
  必须在请求桥/GUI 启动前清除该变量；代价是方案 A 对 GUI 路径失效 → 生产须用方案 B(令牌)/C。
- 现状：`ui --request/--probe` 不存在（cli.rs:78-81，run_ui 直接起界面 main.rs:348）；`ui_mode::EnvFacts` 无 ci 事实(ui_mode.rs:61-72)；
  单实例锁/IPC 全仓不存在；GUI `run()` 同步阻塞(gui/lib.rs:22-39)。
- 清单 P0–P5，P0 为硬前置；建议 MVP 裁剪：结果回传走**文件兜底通道**（与现有 gate_check 天然兼容、零新增），
  砍掉双向 IPC 与后台监听线程。
