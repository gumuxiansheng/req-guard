# 分级门禁技术方案（按有效改动行数与高危路径自动定档）

> 实施产出物，对应需求清单 `.gates/requirements/REQ-019.md`（三段已批准）。
> 评审以该清单 §2 正文为准；本文写的是**落地口径**与**实施期发现**。
> 口径变更必须先改清单再改本文 —— 反过来就是「文档漂移」，
> 而本仓把「副本等于给文档漂移开一个口子」写成过红线（`core/src/section.rs`）。

## 1. 一句话

**把「这份改动有多重」变成一个可复算的函数，三层共用它。**

```text
final_tier = max(声明档 frontmatter.tier, 派生档 classify(changes, config))
```

- `classify` 是**纯函数**（`core/src/tier.rs`）：入参是有效行明细 + 受管路径 + 配置，
  出参是档位 + **人类可读的理由**。不碰 git、不碰文件系统、不读配置。
- 取 git 的薄壳在 `core/src/tierdiff.rs`（`git diff -U0` + 双侧全文）。
- 组装在 `core/src/tier.rs::gate_for`，裁决接线在 `core/src/resolve.rs`。

## 2. 有效改动行

### 2.1 为什么不能直接数 diff 行

`git diff --numstat` 给的是**物理**增删行。把「加 120 行注释」和「加 120 行逻辑」
算成同一个数，分级就失去意义（清单 G2）。

### 2.2 为什么也不能按 diff 行逐行判注释

`-U0` 的 diff 只有变更行、没有上下文，两类情况判不出来：

| 情况 | 为什么逐行判错 |
| --- | --- |
| 块注释跨 hunk（`/*` 在未改动上下文、`*/` 在变更行里） | diff 里看不到块注释的开头 |
| 字符串字面量里的 `//`（`"https://x"`） | 正则把它当行注释，整行被剔 |

### 2.3 采用的口径：按文件全量重建

1. 解析 `git diff -U0 --no-color` 的 hunk 头 `@@ -a,b +c,d @@` → 每个新增行的
   **新侧行号**、每个删除行的**旧侧行号**；
2. 取**变更后全文**（`git show :<path>` / `git show HEAD:<path>`）与
   **变更前全文**（`git show HEAD:<path>` / `git show <base>:<path>`），
   各跑一遍注释状态机，得到该版本「哪些行是注释/空行」；
3. 用行号过滤：新增行按新侧集合过滤，删除行按旧侧集合过滤；
4. `effective = 有效新增 + 有效删除`（删除侧必须计入：删掉一段校验代码和加一段同样重）。

注释语法按扩展名映射：`rs` → `//` 与可嵌套 `/* */`（含 `///` `//!`、字符串/字符字面量、
raw string）；`sh`/`bash`/`zsh`/`py`/`ps1`/`yml`/`yaml`/`toml`/`cfg`/`ini` → `#`；
`md`/`txt`/`json` → 无注释语法（文档的每一行都是内容）。**未知扩展名一律不剔除**
（等于全算）—— 这是 fail-closed 方向：认不出来时倾向高估，低估才是门禁失效。

### 2.4 三条边界（都是实施期必须写死的）

1. **块注释内部「含代码」的行计入有效行**（清单 U-02）。被注释掉的代码仍是代码改动，
   下一轮就会被放开。判据是启发式：剥掉行首空白与注释装饰（`*` / `#`）后，若含代码记号
   （`;` `=` `{` `}` `(` `)` `=>` `::` 之一）即计入。刻意偏保守：散文注释里出现 `=`
   会被多算（多走一次流程），反向漏算才是门禁失效。
2. **二进制文件按 1 有效行计**（清单 B-03）：无法判注释，给 0 等于让大二进制改动
   （图片、模型文件）免费过档。
3. **读不到内容就报错**（清单 B-05）：`git show` 失败（未提交 / 索引里没有）时
   **不按 0 有效行放行**，直接 `GateError::Validation`。只有「那一侧本来就没有变更行」
   （新增文件读不到旧侧、删除文件读不到新侧）才允许缺内容。

### 2.5 性能

一次 `git diff -U0` + 每个变更文件最多两次 `git show`（走 git 对象缓存）。
变更文件通常个位数；`core/src/**` 命中的提交文件多，但那是 `critical` 档、
本来就要走最重流程。**零外部依赖**（纯标准库调用 `git`），与项目前提一致。

## 3. 路径敏感度

| 表 | 来源 | 语义 | 可否被配置改 |
| --- | --- | --- | --- |
| `locked_paths` | **core 内建常量** `core/src/tier.rs::LOCKED_PATHS` | 恒为 `critical` | **否** |
| `risky_paths` | `.gates/req-guard.yaml` 的 `tier.risky_paths` | 至少 `standard` | 是（可增可删） |
| — | 其余 | 交由行数档决定 | — |

内建锁定项：`core/src/**`、`templates/hooks/**`、`templates/ci/**`、`.gates/req-guard.yaml`
（判定逻辑与拦截脚本本身）。glob 语义**复用** `core/src/touch.rs::glob_match`
（`**` 跨层级、`*` 单层、精确文件名），另接受目录前缀写法（`core/src/`）按向下递归归一 ——
与变更范围契约同一份语义，不另写第二套。

### 3.1 「报错而不是忽略」

配置里出现 `locked_paths` 键 → `GateError::Validation`，消息点名该键与全部内建锁定项。
理由：静默忽略会让维护者以为降级生效了，而实际生效的是另一套语义 —— 那是
「看着在拦、其实没拦」的同族失效。

`risky_paths` 与内建锁定项**重叠不算错误**，内建为准（清单 §2.2 与本节曾有冲突，
见 §7 决策记录 D2）。输出里理由会点名 `locked`，人看得见谁在压住谁。

## 4. 档位与阈值

| 档位 | 判定（取最高者） | 审批形态 | AC |
| --- | --- | --- | --- |
| `trivial` | 有效行 ≤ `trivial_max_lines`（5）且未命中 risky/locked | 免审（已建清单则只留 audit 行） | 不要求 |
| `light` | 有效行 ≤ `light_max_lines`（80）且未命中 risky/locked | `approve --all-steps` | 选填 |
| `standard` | 其余 | 三段逐段批准 | 必填 |
| `critical` | 命中 `locked_paths` | 三段逐段批准 + 附加检查 | 必填 |

### 4.1 回放校准结果（G7）

`python scripts/calibrate_tier.py`（最近 40 个提交）：

| 档位 | 现值（5 / 80） | 阈值 ÷2 | 阈值 ×2 |
| --- | --- | --- | --- |
| `trivial` | 0 | 0 | 1 |
| `light` | 8 | 6 | 8 |
| `standard` | 11 | 13 | 10 |
| `critical` | 21 | 21 | 21 |

**判读（必须写下来，否则下一个人会误以为阈值在拟合噪声）**：

1. 本仓真实改动**普遍远超 80 有效行**，故 `critical`（21/40）由内建锁定项主导，
   不是阈值主导 —— 阈值 ±50% 完全不改 `critical` 计数，这说明锁定项是**稳**的。
2. `trivial` 档在本仓几乎空置（0/40，只有阈值 ×2 时才出现 1 个）。这是**如实结论**，
   不是配置失效：本仓几乎不提交「只改几行」的改动，免审档的收益主要体现在
   *别的*仓库（脚本小改、文档微调、typo）。本仓保留它是为了口径统一与零成本。
3. `light` 档是本仓唯一被阈值影响的一档（8 → 6/8）。若团队觉得 8 太多，
   调 `light_max_lines` 而不是动 risky_paths —— **改阈值不改口径**。
4. 因此保留 5 / 80，并要求任何阈值改动都附一次回放报告（`--json` 可供 CI 比对）。

## 5. 与 R2b 的先后：豁免区不参与定档

REQ-020 的 R2b（改动集整体落在 `touch.exempt` 时直接放行）位置在**候选推导之前**。
定档必须排在它**之后**：

| 顺序 | 结论 |
| --- | --- |
| **R2b 先于定档（本方案采用）** | 豁免区改动不参与定档、不消耗档位 |
| 定档先于 R2b（否决） | 清单正文 / 草稿 / `target/**` / `Cargo.lock` 会被算进有效行，推高档位 —— 提交一份新清单可能因此落到 `critical` |

三条实施细则：

1. **入参是 `managed`（剥除豁免后的路径集）**，不是 `paths`。`classify` 不再读一次
   `touch.exempt` —— 豁免集单源（REQ-005 G3），两处各剥一次必然漂移。
2. 与 G2 是两条不同的路：G2 是「算了之后判为 0 有效行」（→ `trivial`），
   R2b 是「**根本不进入计算**」。留痕也不同：G2 在输出里留档位与理由，
   R2b 在审计里留 `PASS no-managed-path`。
3. L1 / L2 / L3 **三层都在 R2b 之后**。`hook-check` 尤其要注意：单次 Write 的
   payload 路径常常就是 `.gates/requirements/REQ-xxx.md`，若 L1 不短路，
   AI 填清单正文会被自己的档位机制要求先批方案 —— 与 REQ-020 修掉的死循环同源。

`scripts/verify_tier.py` 的 T4 场景反向锁这条：纯豁免变更集放行、审计记
`PASS no-managed-path`，且**输出里不得出现任何档位字段**（出现即说明插错位置）。

## 6. 三层输入边界

| 层 | 可见信息 | 档位来源 | 定位 |
| --- | --- | --- | --- |
| L1 `hook-check` | 单次 Write/Edit 的 payload 内容 + 清单声明档 | `max(声明, 本次写入有效行)` | **下界，乐观放行**；输出明示「最终以 CI 复算为准」 |
| L2 pre-commit | 索引内变更集（看不见未暂存改动） | `max(声明, staged 有效行)` | 下界 |
| L3 `check --base` | `base...HEAD` 完整变更集 | `max(声明, 全量有效行)` | **权威** |
| 前置（三层之上） | 剥除 `touch.exempt` 后是否为空 | 空 → **不走定档**，直接放行 | R2b（§5） |

L1 拿不到整体 diff 是**物理事实**（`hook-check` 只解析 PreToolUse 的 stdin JSON，
`core/src/json.rs`），不是实现偷懒。把它写成显式契约，好过留一层看起来能拦
其实拦不住的假象。L1 的档位提示走 **stderr**：stdout 是 hook 脚本的契约通道
（`ALLOW_DOC_MARKER` 等标记），往那里打会被脚本当标记解析。

**L1 的两条已知边界**（写下来以免日后被当成 bug）：

- 不具备跨调用记忆：同一文件分多次小写入，每次都按下界算，累加值**不保留**
  （清单 U-28）。
- 未暂存改动在 L2 看不见，故 L2 与 L3 **允许**给出不同档位；两层输出都带理由，
  人能看出分歧来源。

## 8. 命令与接口

```bash
req-guard tier check [--staged | --base <ref>]   # 只读：算档位并输出理由
req-guard approve <需求ID> --all-steps           # 轻档：一条命令批三段
```

`tier check` 的退出码只表示「算出来了」，**不表示通过门禁** —— 门禁裁决是
`check` 的职责，两者刻意不合并：档位是解释性输出，门禁是拦截口。

## 8.5 本仓启用后的即时后果（先知道，别当成 bug）

在本仓把 `tier.enabled` 打开后，**任何碰到 `core/src/**` 的提交都会派生 `critical`**，
而存量清单的 `tier` 全是 `standard` → 首次提交本需求的代码时会看到：

```text
TierEscalation：REQ-009 REQ-010 REQ-012 REQ-015 REQ-016 REQ-017 REQ-019 REQ-020
  声明 standard，本次改动派生 critical（有效改动行 …）
```

这不是误报，是「门禁自身源码恒为最高档」这条策略的**直接后果**，且它列出全部相关清单
是刻意的（清单 B-06：并集算一次、逐份按各自声明档校验；漏列某一份等于给它开后门）。
但代价是**一次改动要把所有相关清单按 critical 重新批准一遍**。

三条可选处置（都需要人类决定，工具不替你选）：

1. **接受**：相关清单逐份 `amend` + `approve` 重来一遍，此后每份清单的 `tier` 就是
   `critical`，后续同路径改动不再报升档；
2. **把档位写进清单**：把相关清单的 frontmatter `tier` 改成 `critical` 并重新批准，
   一次性了结；
3. **暂不启用**：把 `tier.enabled` 置 `false`。分级机制本身仍在（代码、命令、
   判决性实验都在），只是不参与裁决 —— 等团队把「critical 要重批」这条成本谈清楚再开。

## 9. 回滚

`tier` 段全部置空或 `enabled: false` → 派生档不生效：

- 判定退回现行三段语义（`derived_tier` 直接返回 `None`，门禁输出与启用前**逐字一致**）；
- 清单里的 `tier` 键**保留即可**（`standard` 在新旧枚举下都合法，不需要改任何清单）；
- 新增命令与模块保留但不被调用，无需回滚二进制。

已批准段若因档位升档需要重新批准（`standard → critical`），走**既有语义**：
`approve` 逐段重来，不引入新状态、不引入新转移（清单 N2）。

## 10. 跨仓依赖

`tier` 与 doc-guard 的 `tier` 是**同一个枚举**，不是平行键（清单 §2.9）：

- doc-guard 侧只需扩 `freshness.rs` 的 `TIERS` 常量（`critical` / `standard` → 四值）；
  新增的 `light` / `trivial` 在 doc-guard 侧**不改变任何一条判定结果**
  （全仓只有 `tier == critical` 触发额外约束）；
- 依赖顺序：doc-guard 先发版 → 本仓再启用。反序的失败态是**响亮的**：
  旧版 doc-guard 对 `tier: light` 报 FRS007 并自带可用取值清单；
- 本仓存量清单全部是 `tier: standard`，新旧枚举都合法，故**不依赖发版顺序**即可兼容。
