### 0.3 同一逻辑在两处已埋下的「跨平台分叉」

第 1 份副本用 `sort -r`，**未固定 locale**；第 3/4/5 份在 Rust 里用
`Path::file_name().cmp(..)`，即 **Unix 字节序**。二者不是同一个序。实测（macOS）：

| 文件名 | `LC_ALL=C`（字节序，与 Rust 一致） | `en_US.UTF-8`（macOS 默认） |
| --- | --- | --- |
| `REQ-a.md` / `REQ-B.md` | 选中 `REQ-a.md` | 选中 `REQ-B.md` |

即：**同一台机器上，脚本（第 1 份）与 `touch --declare`（第 5 份）可以指向不同的需求**，
且 macOS 开发机与 `LC_ALL=C` 的 Linux CI 会得出不同的「活跃需求」。这条与本文 §1 的
前提 ② 同源，修 §1 前提 ② 时必须一并消除 locale 依赖（判定移入 Rust 即自然消除）。

## 1. 根因：「活跃需求单条」假设（S1）及其三个前提

门禁第 2–5 段实际断言的是：

> **S1：仓库存在唯一一份「当前活跃需求」，门禁只需对它判三段 + 阻塞评论。**

S1 由三个隐含前提支撑，**三个都已被证伪**：

| 前提 | 内容 | 证伪 | 出处 |
| --- | --- | --- | --- |
| **S1-a** | 仓库同时只有一份未归档清单 | `create` 从不检查既有 live 清单；`docs/规范/需求编号防冲突命名规范.md` §1 的立项前提就是「团队并行开发时本地各建 `REQ-NNN`」；`touch` 一侧已按并集口径实现 | `requirement::create`、`touch::collect_declarations`、编号规范 §1/§3 |
| **S1-b** | 文件名逆序 ≈ 时间倒序 | `REQ-001`/`REQ-002` 三位补零时成立；`REQ-<owner>-<NNN>` 与 `REQ-<owner>-<YYYYMMDD>-<rrrr>`（编号规范推荐的**并行默认档**）下不成立 —— 字典序最大者恒定胜出，与新旧无关（实测场景 C） | `requirement::normalize_id`、`next_id`、编号规范 §3 |
| **S1-c** | 「当前活跃需求」是全局唯一的裁决对象 | PreToolUse payload 里**带着本次要写的文件路径**；pre-commit 里有 staged 集；CI 里有 diff 集。裁决对象本可以是「本次变更集」，而不是「某一份清单」 | `json::file_path_of`、`touch::STAGED_ENV`、`touch::diff_files` |

**为什么这一个假设同时产生「漏拦」与「互锁」两个方向**：两者都不是判据松紧问题，
而是**裁决对象错位**——

- 判据（"三段是否 approved"）是对的，喂给它的对象是错的；
- 对象错位时，结果只取决于「挑了哪一份」，与「本次改动属于哪一份」无关；
- 于是「挑中的那份已批 → 放行」产生漏拦（场景 A），「挑中的那份未批 → 拦」产生误锁（场景 B/C）。

因此**调松或调紧判据都修不好它**。必须换掉「先挑一份清单，再对它判」这个结构。

### 1.1 次生根因：口径写在了错误的层

第 1/2 份副本把裁决逻辑写在 shell 里，于是：

1. **同一逻辑要镜像两遍**（sh + ps1），任何修复都要改两处、改两遍测试；
2. **locale 依赖**只能靠 shell 的 `sort` 承担（§0.3）；
3. **`gate_check` 依赖已安装脚本的正确性与执行位** —— 脚本被改坏 / 漏 chmod / 版本漂移
   都会让 L3 的裁决静默变化，而 `check` 自己无从察觉（它就是把脚本输出转发出去）。

这三条与 `core/src/lib.rs` 模块文档的既有不变式（「**唯一真相在这里**：门禁判定与清单状态
读写只实现一次，前端只渲染不判定」）以及 `HOOK_TOUCH_SH` 的注释（第 2 条：任何加进
`HOOK_SH` 的判定都必须在 `HOOK_PS1` 里逐行镜像 —— 纯负债）**直接冲突**。
本方案把裁决下沉到 core，一次解决三个问题。

## 3. 方案选型

### 3.1 候选方案

| 代号 | 方案 | 一句话机制 |
| --- | --- | --- |
| **甲** | 全体 fail-closed | 全部未归档清单都必须三段全批，才允许写任何代码 |
| **乙** | 显式选择 | 由人 / 会话显式指定「本次做哪份需求」（`HOOK_REQ` / `--req` / 分支名） |
| **丙** | 变更集反查 | 用本次改动涉及的文件反查它属于哪份需求（借 `GATE:TOUCH` 声明建索引） |
| **丁** | **丙 + 乙 分层** | 先反查，反查不出或有歧义时用显式选择消歧；两者都给不出 → 拦 |
| **戊** | 会话锁 / 租约 | `.gates/active` 记录「当前需求」，AI 与人共用一个可写状态文件 |
| **己** | 门禁分层 | 写路径严（只准写已批清单声明过的文件）+ 提交 / CI 路径宽（沿用并集） |

### 3.2 逐项分析

**甲（全体 fail-closed）**

- 修的方向：G1 ✅（无漏拦）；G2 ❌（**误锁反而加重** —— REQ-002 起草中时连 REQ-001 的
  bug 修复都写不了，正是场景 B 的病根被制度化）。
- 实现面：最小，sh 里把 `break` 改成 `continue` 即可。
- 致命处：把「工作流不便」制度化成门禁必然结果。而 `docs/规范/AI工具合规保证规范.md`
  的部署验收清单要求门禁在真实项目里长期不被绕过 —— **误报是头号死因**。
- 唯一优点：它可以作为**保守档配置**保留（§4.7 `multi.mode: all`）。

**乙（显式选择）**

- 修的方向：G1 ✅（指定的那份未批就拦）；G2 ✅（互锁解除）。
- 误报面：低，但**把负担转给人**：每次开工前必须设 `HOOK_REQ`。
- 致命处：**环境变量不可靠**。`core/src/auth.rs` §4 已记录同款坑 —— 环境变量会被同 shell
  会话的 AI 子进程继承，故 auth.level=2 起「审批凭据只认进程内显式传入，不读环境变量」。
  把裁决正确性挂在 `HOOK_REQ` 上，等于把门禁交给一个本项目已经判定为不可信的通道。
- 结论：**只能作为消歧手段，不能作为唯一手段**（它进了丁的 L1 层）。

**丙（变更集反查）**

- 修的方向：G1 ✅（路径是 REQ-001 声明的、REQ-001 未批 → 拦）；G2 ✅（路径是 REQ-001
  声明的、REQ-001 已批 → 放行，与 REQ-002 是否未批无关）。
- 数据源**现成**：PreToolUse 的 `file_path`（`json::file_path_of`）、pre-commit 的
  `HOOK_STAGED_FILES`、CI 的 `diff_files`；声明源也已落地（`touch::declared` + `glob_match`）。
- 误报面：与 `touch` 的误报面**同源且同解**（复用同一份声明、同一套 glob、同一份 exempt），
  不新增误报来源。
- 致命处：**反查不出时必须有确定行为**，否则要么静默放行（G1 破）要么恒拦（G2 破）。
  这正是「歧义」分支存在的理由 —— 它必须**报错 + 给出路**，而不是猜。
- 结论：作为主路径（进丁的 L2 层）。

**丁（丙 + 乙 分层）**

- 修的方向：G1 ✅、G2 ✅、G3 ✅（歧义即拦）。
- 误报面：歧义分支会产生新误报（「路径未被任何已批清单声明」+ 多份 live）。这是本方案
  唯一的**新增拦截面**，故必须配三张牌（§4.11）+ 合法出路（补声明 / `--req` / 归档）。
  G4 要求单需求仓库不受影响 —— 由「live == 1 时歧义分支不触发」保证。
- 兼容：单需求仓库走 L3 退化分支，与今天逐字同语义。
- 结论：**采纳**。

**戊（会话锁 / 租约）**

- 致命处一：`.gates/active` 落在 `.gates/**` 内，而 `.gates/**` 是 `touch.exempt` 默认集 ——
  即「AI 可以自己写这个文件」，自锁等于可自解。
- 致命处二：它把「本次做哪份需求」这个**上下文**写进仓库工作区文件，会跟着 diff 漂移、
  会在切分支时变成陈旧值，且无 TTY 交互时无法自动续租。
- 结论：**否决**（与 `docs/提案/AI协同审核GUI自动弹出技术方案.md` 的「单实例序列化」
  思路冲突：那是 UI 侧的并发去重，不是裁决对象的选择）。

**己（门禁分层：写路径严 / 提交路径宽）**

- 优点：能保住 CI 侧宽松（并集），只在 AI 写路径上收紧。
- 致命处：**两层口径不同 = 两个真相**。提交路径一旦宽（本机 `--no-verify` 或 CI 配置漏改），
  写路径的严格判定就被整体抵消，而门禁最坏的失效是「看着在拦、其实没拦」。
  AC 方案 §3.6 已就同类问题定调：模板与命令的一致性必须被机械校验，
  而「写严、提交宽」的一致性无法靠机械校验维持（它要求两侧配置永远同步）。
- 结论：**否决**。宁可一套口径 + 歧义时报错。

### 3.3 选型矩阵

评分：✅ 满足 / ⚠️ 有代价 / ❌ 不满足。

| 方案 | G1 不漏拦 | G2 不误锁 | G3 fail-closed | G4 存量兼容 | G5 判定在 core | 新增误报面 | 实现面 | 选中 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 甲 全体 | ✅ | ❌ | ✅ | ❌（多需求仓库恒拦） | ❌ | ❌ 极大 | 最小 | 否（降级为配置档） |
| 乙 显式 | ✅ | ✅ | ⚠️ 忘设即漏 | ✅ | ❌ | ⚠️ 需人配合 | 中 | 否（并入丁） |
| 丙 反查 | ✅ | ✅ | ⚠️ 反查不出需定行为 | ✅ | ✅ | ⚠️ 歧义面 | 中 | 否（并入丁） |
| **丁 分层** | ✅ | ✅ | ✅ | ✅ | ✅ | ⚠️ 仅歧义面，且配出路 | 中大 | **是** |
| 戊 会话锁 | ❌ | ✅ | ❌ | ❌ | ❌ | ⚠️ | 大 | 否 |
| 己 分层宽窄 | ⚠️ | ✅ | ❌ | ⚠️ | ⚠️ | ⚠️ | 大 | 否 |

### 3.4 决策

> **采纳「丁」：以本次变更集为裁决对象，用 `GATE:TOUCH` 声明建反查索引；
> 反查无结果或有歧义时用显式选择消歧；两者皆不可得 → 拦并给三张牌。**
> 裁决逻辑下沉到 core（新增 `core/src/resolve.rs`），shell 脚本收缩为「取参 + 渲染」。

## 4. 目标设计

### 4.1 判定落点与调用链

```
                  ┌───────────────────────── core（唯一真相） ─────────────────────────┐
AI PreToolUse ──▶ │ pretool_verdict   证据保护 / 防自批（语义不变）                      │
（payload）        │        ↓                                                          │
                  │ resolve()      ★ 本方案新增：裁决对象解析 + 三段/阻塞判定 + 审计     │
pre-commit ─────▶ │        ↑                                                          │
（staged 集）      │ gate_check()   渲染 + 退出码（check --staged / --base / --stdin）    │
                  └───────────────────────────────────────────────────────────────────┘
                                        ▲
CI / --base ───────────────────────────┘

HOOK_SH / HOOK_PS1 收缩为：
  §0 取 payload（有则原样透传给 `check --stdin`）
  §1 取 staged 集（无 payload 时 → `check --staged`）
  §2 调用 `req-guard check` 并透传退出码；**二进制不在 PATH → fail-closed**
  —— 不含任何裁决分支（G5）
```

**为什么必须移入 core（而不是在 sh 里改）**：反查索引需要 glob 匹配。
`touch::glob_match` 是零依赖递归回溯实现（`**` 跨层级、`**/*.rs` 匹配零段）；
在 POSIX sh 里重写它需要 `case` 模式，而 `case` 的 `*` 不跨 `/` —— 要在 sh 里正确实现
`**` 只能起子 shell 逐段递归匹配，其代价是：① 第二个 glob 真相源；② `HOOK_PS1`
还要再镜像一遍（纯负债，`HOOK_TOUCH_SH` 的注释第 2 条已定调）；③ locale 分叉（§0.3）
依旧无解。

**一个被迫的连带后果**：`check` 一旦被脚本回调，就**不能再反过来执行脚本**
（否则无限递归）。因此 `gate_check` 必须从「跑 sh 脚本」改成「直接调 `resolve()`」，
`run_hook` 及其解释器选择逻辑退役。这是 §4.1 的必然推论，不是可选项。

### 4.2 数据模型（新增 `core/src/resolve.rs`）

```rust
/// 一份未归档清单的裁决快照（判定所需的全部事实，一次读完）。
pub struct LiveReq {
    pub id: String,
    pub path: PathBuf,
    /// 三段 `GATE:STEP` 的 status 是否全为 approved（**只读 status**）。
    pub approved: bool,
    /// 未过审的步骤（供文案指名，已全批时为空）。
    pub pending_steps: Vec<&'static str>,
    /// 是否有未解决的阻塞性评论（`comment::list` + `is_blocking_open`）。
    pub has_open_blocking: bool,
    /// `GATE:TOUCH` 声明（`touch::declared`；缺块/坏路径在此归一为空）。
    pub declares: Vec<String>,
    /// 内容冻结违规（REQ-002 的 `sum=`；**与候选集无关**，见 §2 的 G7）。
    pub sum_errors: Vec<String>,
}

/// 变更集来源（三个上下文各一种，**互斥**，由 CLI 显式指定）。
pub enum PathSource {
    /// 无变更集：裸 `req-guard check` / 人工查状态。
    None,
    /// pre-commit：`HOOK_STAGED_FILES` 或 `git diff --cached`。
    Staged,
    /// CI / L3：`git diff <base>...HEAD`。
    Range(String),
    /// AI PreToolUse：从 stdin payload 取 `file_path`（单路径）。
    Stdin,
}

/// 裁决输入。
pub struct Ctx {
    pub source: PathSource,
    /// 显式选择（消歧用）：`--req <ID>` > `HOOK_REQ` > 分支名（§4.7）。
    pub hint: Option<String>,
}

/// 拦截理由类别。**枚举即契约**（由 §7.1 的枚举覆盖门槛强制其被测）。
pub enum BlockKind {
    /// 无任何未归档清单（与今天 `BLOCK no-requirement` 同义）。
    NoRequirement,
    /// 显式选择指向的清单不存在 / 已归档 / 不在 live 集内。
    UnknownSelection,
    /// 多份候选，本次改动无法归因于其中唯一一份。
    Ambiguous,
    /// 显式选择与本次变更集不相交（选错了需求，或想用它绕过）。
    SelectionMismatch,
    /// 候选清单三段未齐（指名到具体清单与具体步骤）。
    StepNotApproved,
    /// 候选清单有未解决的阻塞性评论。
    OpenBlockingComment,
    /// 某份非 `done` 清单的已批准段正文与批准时不一致（REQ-002 内容冻结）。
    SumMismatch,
}

/// 裁决结果。
pub enum Verdict {
    Pass { reqs: Vec<String>, note: Option<String> },
    Bypassed { reqs: Vec<String>, expires_epoch: u64 },
    Block { kind: BlockKind, reqs: Vec<String>, message: String },
}
```

**候选集（`Vec<LiveReq>`）不是对外类型**：它由 `resolve` 内部产出，
`Verdict` 只暴露被点名的 ID 列表 —— 渲染与审计都需要「判了谁」，不需要判据内部结构。

**`approved` 只读 status，不重复实现 REQ-003 的段落实质性判定**：
`core/src/section.rs` 的 `is_section_empty` 已挂在 `requirement` 的审批路径上
（空段在 `approve` 时就被拒），故 `status=approved` 已隐含三段非空。
在 `resolve` 里再判一次段空就是第二处真相，会与 REQ-003 的判据漂移。

**`sum_errors` 与候选集正交（G7）**：内容冻结遍历**全部非 `done` 清单**，
不受 `paths` / `hint` / 候选集影响。`judge` 先输出 `sum_errors`，有错即 `SumMismatch`
—— **先于三段判定**，因为「证据已被篡改」比「没审批」更严重。

### 4.3 解析算法

```
resolve(root, ctx):
  # ── 0) 取 live 快照 ────────────────────────────────────────────────
  live = list(root) 过滤 (head_status != "done" 且不在 archive/ 下)
  若 live 为空 → Block(NoRequirement)                     # 与今天同义

  # ── 0.5) 内容冻结自查（G7：与候选集正交，先于一切）──────────────────
  sum_bad = { r ∈ live : r.sum_errors 非空 }
  若 sum_bad 非空 → Block(SumMismatch, reqs = sum_bad.id)
      # 遍历**全部**非 done 清单，不受 paths / hint 影响 —— 「证据被篡改」比「没审批」更严重

  # ── 0.6) 应急绕过窗口（有痕、有时效、入审计）────────────────────────
  若 .gates/.bypass 有效 → Bypassed{reqs = live 全部 id}   # 语义与今天一致

  # ── 0.7) 内容冻结之外的最后一道正交检查已完成，下面进入变更集相关判定 ──

  # ── 1) 变更集取参与归一 ────────────────────────────────────────────
  paths = 取(ctx.source)          # Stdin → 单路径；Staged/Range → 文件集；None → 空
  managed = 归一(paths) 去掉 touch.exempt 命中的路径    # 豁免集单源（§4.6）
  若 managed 为空 → 视为"空集"，**不**降级为"全量"（保持 G4：单需求仓库行为不变）

  # ── 2) L1：显式选择优先（只收窄，不放行）─────────────────────────────
  若 ctx.hint 存在:
      h = live 中 id == hint 的那一份
      若 h 不存在 → Block(UnknownSelection)      # 含"已归档"的显式提示

  # ── 2.5) R2b：受管路径为空 → 放行（REQ-020）─────────────────────────
  #   条件（三者同时成立，缺一不可）：
  #     ① ctx.source ≠ None         —— 裸 check 是"能不能开工"，无变更集就无从归因，
  #                                    放行会把答案变成永远"能"（漏拦，见 §4.8）
  #     ② paths 至少含 1 条非空路径 —— 空变更集 ≠ 全豁免变更集。Stdin 取不到
  #                                    file_path 时返回空集，此时放行等于让 AI 用
  #                                    一个解析不出路径的 payload 穿过 L1
  #     ③ managed 为空              —— 改动集整体 ⊆ touch.exempt
  #   顺序：必须在 0.5) 内容冻结**之后**（证据篡改更严重）、在 2) 之后
  #         （hint 指错是用户犯错，不是"无需归属"）、在 3) 反查**之前**
  #         （否则无 hint 时 H 已先为空，规则永不可达）。
  #   产出：Pass{reqs = [], note = "…未做任何归属判定"}，审计记
  #         `PASS no-managed-path` + `NOTE …`，与"三段已批准"明确区分。
  若 上述三条成立 → Pass{reqs = []}

  # ── 3) L2：反查索引（只用**三段全批**的清单建索引）──────────────────
  idx = { r ∈ live : r.approved }                  # 未批清单不建索引（§4.3.1）
  H   = { r ∈ idx : r.declares 命中 paths 中任一路径 }
  #   H 可能 >1（多份已批清单共同覆盖）—— 那不是歧义，是"多份都已批"，§4.3.2

  # ── 4) 定候选集 ──────────────────────────────────────────────────
  若 hint 存在:
      候选 = H ∪ {h}
      若 h ∉ H 且 H ≠ ∅:
          → Block(SelectionMismatch)   # 你指定的清单与本次改动无关（G3：hint 不是绕过口）
  否则:
      候选 = H
      若 H = ∅ 且 |live| == 1:  候选 = live            # G4：单需求退化，与今天同语义
      若 H = ∅ 且 |live| >  1:  候选 = ∅ → Block(Ambiguous)

  # ── 5) 逐份判定 ──────────────────────────────────────────────────
  failed = 候选中 (¬approved 或 has_open_blocking) 的那些
  若 failed 非空:
      kind = 若存在 ¬approved → StepNotApproved else OpenBlockingComment
      → Block(kind, reqs = failed.id)         # 候选里已批的那几份**不**参与拦截
  若 候选 = ∅ 且 hint 存在且 H = ∅:
      → 候选 = {h} 继续判定（hint 是唯一依据；paths 未被任何已批清单声明）
  → Pass{reqs = 候选.id}
```

#### 4.3.1 为什么索引只用「三段全批」的清单

| 索引口径 | 后果 | 判定 |
| --- | --- | --- |
| 全部 live（含未批） | 未批清单的**草案** glob 进索引 → 写 REQ-001 的文件时因命中 REQ-002 的 `**` 而被 REQ-002 的未批状态拦住 → **误锁，且是必然误锁**（草案声明通常更宽） | ❌ |
| 仅三段全批 | 未批清单不参与放行判定；路径未被任何已批清单声明时走歧义/退化分支 → 要么指名要么报错，都能给出出路 | ✅ |

**推论（须写进代码注释）**：未批清单的 `GATE:TOUCH` 声明**没有放行权**。
它唯一的作用是被 `touch --declare` 打回重审（`touch.reapprove`）时的声明源。
本方案**不使用**草案声明去「指名」拦截对象（可能的增强见 §8 已知代价第 1 条）。

**该推论必须成对实现，两个方向都要有用例**：

| 方向 | 场景 | 期望 | 漏掉会怎样 |
| --- | --- | --- | --- |
| **不误锁** | 已批 A 声明 `core/src/**`，未批 B 声明 `**`，路径命中 A | 放行 | 草案 `**` 吞掉一切 → 必然误锁 |
| **不漏拦** | 未批 A 声明 `core/src/**`，已批 B 只声明 `cli/src/**`，路径命中 A | **拦** | 只测上一个方向时，重构 `judge` 能悄悄打破 G1 而测试全绿 |

#### 4.3.2 为什么 |H| > 1 不是歧义

`H > 1` 意味着多份**已批**清单都声明了这次改动的文件（典型：重构同时落在两个已批需求
的范围内）。此时没有任何未过审的东西被碰到 —— 应当放行。
把这种情况报成 `Ambiguous` 会制造大量无解误报（出路只能是 `--req`，而选哪份都对）。
拦截只在**候选里存在未过审项**时发生（§4.3 第 5 步），这保证了拦截消息永远指名到
一份真实未过审的清单，而不是「请你猜」。

### 4.4 规则表（逐条可单测）

| 编号 | 规则 | 判据 | 严重级 |
| --- | --- | --- | --- |
| **R1** | 无未归档清单 → 拦 | live 为空 | Block |
| **R2** | 命中应急绕过窗口 → 放行并标记 `REQ_GUARD_BYPASS=1` | `.gates/.bypass` 未过期 | Pass(Bypassed) |
| **R2b** | **受管路径为空 → 放行**（REQ-020）：改动集整体 ⊆ `touch.exempt` 时不要求归属 | `ctx.source ≠ None` ∧ `paths` 至少 1 条非空路径 ∧ `managed = ∅` | Pass(`reqs=[]`) |
| **R3** | 显式选择指向不存在 / 已归档的清单 → 拦 | hint ∉ live | Block(UnknownSelection) |
| **R4** | 反查索引只含三段全批清单 | `r.approved` | — |
| **R5** | 变更集先剥 `touch.exempt` 再参与判定 | exempt 单源 | — |
| **R6** | 反查命中集 `H` 非空 → 候选 = `H`（可 >1） | glob 匹配 | — |
| **R7** | `H` 为空且 `\|live\| == 1` → 候选 = 唯一 live（G4 退化） | 计数 | — |
| **R8** | `H` 为空且 `\|live\| > 1` 且无 hint → 拦 | Ambiguous | Block |
| **R9** | hint 存在且 `H ≠ ∅` 而 `hint ∉ H` → 拦 | SelectionMismatch | Block |
| **R10** | hint 存在且 `H = ∅` → 候选 = `{hint}`（hint 是唯一依据） | — | — |
| **R11** | 候选中任一未过审（三段 / 阻塞评论）→ 拦，且**只**点名未过审的那些 | 逐份判定 | Block |
| **R12** | 候选全部过审 → 放行，审计记全部候选 ID | — | Pass |
| **R13** | `multi.mode: all` 时候选恒为 live 全体（保守档，§4.7） | 配置 | — |
| **R14** | 分支名 hint 只在 `H = ∅` 且 `\|live\| > 1` 时参与消歧，且**永不**放行（R9 同样适用） | 分支名含 `REQ-<id>` | — |
| **R15** | 内容冻结：任一非 `done` 清单的 `sum_errors` 非空 → 拦，**且不受 `paths`/`hint`/候选集影响**（G7）；判定**先于** R1–R14 | `requirement::verify_sums` | Block(SumMismatch) |

R15 排在最后但**执行顺序最靠前**（见 §4.3 伪码的第 0.5 步）：`R1` 之前。
理由是「证据已被篡改」比「没审批」更严重，且它与候选集正交、不受本次改动范围影响。

**R2b 的执行位置**（REQ-020）：R15 之后 → R3 之后 → R6/R7/R8 反查**之前**（§4.3 第 2.5 步）。
三处顺序都是硬约束：内容冻结优先于一切；hint 指向不存在的清单是**用户犯错**，
不是「改动无需归属」，若 R2b 抢在前面则 `UnknownSelection` 这条防呆会被静默吞掉；
而无 hint 时 `H` 已先为空，放在反查之后则本规则永不可达。

**为什么必须有 R2b**：豁免的语义是「不要求 `GATE:TOUCH` 声明」，豁免区内也确实没有
可归属的对象。要求归属等于要求「先有已批清单才能提交第一份清单」—— 门禁无法自举，
`--no-verify` 也救不了（CI 侧 `check --base` 同样算出空集，同样拦）。

**R2b 不是「空集一律放行」**，两条边界必须同时守住：

| 边界 | 若放开的后果 |
| --- | --- |
| `ctx.source = None`（裸 `check` / TUI 面板）也放行 | 「能不能开工」永远答「能」—— 单需求仓库的 R7 退化语义被抹掉，**漏拦** |
| `paths` 为空也放行 | `--stdin` 取不到 `file_path` 时返回空集，AI 用一个解析不出路径的 payload 即可穿过 L1 —— **看着在拦、其实没拦** |

### 4.5 三个上下文的取参（脚本职责，仅此而已）

| 上下文 | 脚本/调用方做什么 | `resolve` 收到的 `source` | 备注 |
| --- | --- | --- | --- |
| AI PreToolUse | 把 stdin payload 原样透传 | `Stdin` | 路径由 `json::file_path_of` 真解析（**不得**在 sh 里 `sed` 抠，§0.5） |
| git pre-commit | 设 `HOOK_STAGED_FILES`（`git diff --cached -z \| tr '\0' '\n'`） | `Staged` | 沿用 `touch::staged_files` 的取参口径 |
| CI / L3 | `--base origin/main` | `Range` | 复用 `touch::diff_files` |

**注意**：`PathSource::None`（裸 `req-guard check`）在多需求仓库下会命中 R8 → 拦。
这不是缺陷而是诚实答案（无变更集就无从归因），但**必须**在模板层解决：
`templates/ci/req-guard-ci.yml` 的 `./req-guard check` 必须改为
`./req-guard check --base "origin/${{ github.base_ref || 'main' }}"`，与同文件里
`touch-check --base` 那一行同款（§6 的 P2 会把这条断言加进 `verify_install`）。

### 4.7 配置契约（`.gates/req-guard.yaml` 新增块）

```yaml
# 多需求并行裁决（docs/设计/多需求并行门禁裁决技术方案.md §4）
multi:
  # resolve（默认）= 按本次变更集反查 + 显式消歧（§4.3）
  # all            = 保守档：全部未归档清单都必须三段全批（= 旧方案「甲」，
  #                   不会漏拦但会在多需求仓库里互锁；仅在团队明确接受时开启）
  mode: resolve
  # 分支名消歧：分支名含 REQ-<id> 时作为 hint（只消歧、永不放行，R14）。
  # 默认关闭 —— 分支与需求并非恒等，且 R9 仍会校验它与变更集相交。
  bind_branch: false
```

**hint 优先级**（高 → 低）：`--req <ID>` > `HOOK_REQ` 环境变量 > 分支名（`bind_branch: true` 时）。
三者都缺省即「无 hint」。`HOOK_REQ` 沿用 `cli/src/main.rs` 现有的读法，
**语义收窄**：此前只作用于 `touch-check`，此后同时作用于裁决（§4.2 的 `Ctx.hint`）。

**读取方式**：照抄 `touch_exempt_patterns` / `touch_scope_strict` 的零依赖块级解析
（`yaml_scalar(root, "multi", key)` 已有实现，无需新增解析器）。

### 4.8 CLI 契约

```
req-guard check                          # 全局判定（无变更集）：多需求仓库下按 R8 拦
req-guard check --staged                 # pre-commit：staged 文件集
req-guard check --base <ref>             # CI / L3：git diff <ref>...HEAD
req-guard check --stdin                  # AI PreToolUse：从 stdin payload 取 file_path
req-guard check [--req <ID>]             # 消歧（可与上面任一组合）
```

| 约束 | 理由 |
| --- | --- |
| `--staged` / `--base` / `--stdin` **互斥**，同时给两个即报错退出 2 | 机械可判定；两个变更集混在一起判必然产生无法解释的裁决 |
| `--stdin` 必须显式给出，不做「stdin 非空就自动读」 | CI 里 stdin 常被重定向；隐式读会挂死（`scripts/verify_gate.py` 已为 `cat` 挂死踩过一次坑，见其 `DEVNULL` 注释） |
| `touch --declare` 无 `--id` 且 live >1 → 报错退出 2（§4.6 第 2 条） | G1 的直接延伸：不能往错的清单上写声明 |

**渲染契约**：`GateVerdict` 保持 `Pass{summary, detail, bypassed}` / `Block{summary, detail}`
两个形状（`cli/src/render.rs` 的 `print_verdict` 不改签名）。变化的只有 `detail` 的内容：
从「一份清单的三段状态」变成「本次裁决对象 + 每份的状态 + 出路」。

### 4.9 脚本改造（`HOOK_SH` / `HOOK_PS1`）

`HOOK_SH` 第 2–5 段（`ACTIVE` 定位 / 三段检查 / 阻塞评论 / 评论摘要）**整体删除**，
替换为：

```sh
# ---------- 2) 裁决（判定在 core；脚本只取参与渲染） ----------
# 三种上下文各取一种变更集：
#   有 payload → --stdin（路径由 Rust 真解析 JSON，不在 sh 里抠字段）
#   无 payload → --staged（pre-commit / 人工 check）
if ! command -v req-guard >/dev/null 2>&1; then
  log "BLOCK no-binary"
  echo "[req-guard] ⛔ 拦截：无法裁决（req-guard 不在 PATH），本次写/提交已被阻止。" >&2
  echo "          请把 req-guard 加入 PATH 后重试（安装见 req-guard install）。" >&2
  echo "          确需本次放行：git commit --no-verify / .gates/.bypass 应急窗口。" >&2
  exit 1
fi
if [ -n "${STDIN_DATA:-}" ]; then
  printf '%s' "$STDIN_DATA" | req-guard check --stdin || exit 1
else
  req-guard check --staged || exit 1
fi
exit 0
```

**同一改动必须在 `HOOK_PS1` 逐行镜像**（Windows 资产，`run_hook` 退役后由用户直接
执行 / 由 CI 执行）—— 这是 G5 之后**仍然存在**的唯一镜像负债，且只剩这一处。

**必须保留的三件事**（否则是能力回退，不只是重构）：

1. **评论摘要提示**（今天第 5 段，每次都打，保证 AI 必然看到 open 评论）→
   移入 `resolve` 的 `Pass.note`。
2. **`REQ_GUARD_BYPASS=1` 标记**（`cli/src/main.rs` 的 `BYPASS_MARKER` 契约）→
   `resolve` 的 `Verdict::Bypassed` 路径打印。既有单测
   `hook_脚本输出绕过标记` 锁的是脚本文本，改造后须改为锁 `resolve` 的输出。
3. **★ 内容冻结（REQ-002）不得回退**。脚本 §3.5 当前的条件是
   `grep -q 'sum=[0-9a-f]' "$REQ_DIR/$ACTIVE"` → 调 `req-guard verify-content`，
   **只覆盖被选中那一份**；而 core 的 `sum_check_detail` 遍历**全部非 `done` 清单**，
   覆盖面本就更大。故 §3.5 删除后由 core 独家承担，**不是能力丢失而是覆盖面扩大** ——
   但必须显式写明，否则实现者会以为「漏了一段」而把它加回脚本，造成双重校验。

**`SUM_CHECKED_ENV` 与 `verify-content` 子命令的去留**（`gate_check` 现在用它向脚本
传递「core 已自查过 sum」）：

| 对象 | 处置 | 理由 |
| --- | --- | --- |
| `gate::SUM_CHECKED_ENV` | **删除** | 唯一用途是阻止脚本重复自查；脚本不再自查后无存在意义 |
| `req-guard verify-content` 子命令 | **保留** | 人可直接用（排查「我明明没改为什么报冻结」）；`verify_install` 仍须检出它存在 |
| `gate::sum_check_detail` | **保留并移入 `resolve`** | 改为填 `LiveReq.sum_errors`，覆盖面扩大到全部非 `done` 清单（G7） |

**关于「二进制不在 PATH 就全拦」**：**该行为已由 REQ-002 落地，本方案不再引入新的收紧。**
实测（无 PATH 执行已安装脚本）：


即 `HOOK_SH` §3.5 的条件分支（存在 `sum=` 而无二进制 → fail-closed）早于本方案生效。

### 4.12 刻意不做（及原因）

| 不做 | 原因 |
| --- | --- |
| 拦 `Bash` / `Edit` 之外的工具（如 `Bash` 里的 `sed -i`、格式化器批量改写） | payload 无 `file_path` 时 `pretool_verdict` 只能返回 `Continue`（既有设计）。这类改动由 pre-commit + CI 兜底。**已知洞，不假装覆盖** |
| 审查 payload 里 `content` / `edits` 数组做多文件判定 | 各工具 payload 结构不一致，`json::find_str` 只能取第一个 `file_path`。多文件批量写仍走"逐次判定"或 pre-commit |
| 把声明反查做成「按目录前缀」的近似匹配 | 会把裁决变成模糊匹配，`GATE:TOUCH` 的 glob 语义已足够精确（AC 方案 §3.3 已定死） |
| 给每个需求加"负责人"字段并据此裁决 | 与「谁在写这个文件」无关；AI 的写操作没有作者归属 |
| 子仓库 / submodule 内的清单 | `requirement::list` 只扫顶层，`archive` 子目录的处理已由 §0.5 既定事实保证 |
| `strict` 口径的"自动猜测"行为 | §4.6 第 1 条：候选 >1 时报错，不猜 |
| 用未批清单的草案声明为拦截**指名** | 草案 glob 通常更宽（`**`、`core/src/**`），大量文件都会被指到同一份起草中的清单 → 频繁指错。代价是文案不够精确；可选增强见 §6 的 P6 |

## 7. 测试矩阵

### 7.1 `core` 单测 —— `resolve`（纯函数，不碰 git、不碰文件系统）

把判定拆成两层，这是可测性的前提（同 `touch::check_changes` 的做法）：

```
judge(live: &[LiveReq], paths: &[String], hint: Option<&str>, mode: MultiMode)
    -> Verdict            ← 纯函数：R1–R15 全部在此，table-driven 覆盖
resolve(root, ctx)       ← 薄壳：读 live 快照 + 取变更集 + 调 judge + 审计 + 渲染
```

**必须覆盖的用例**（每条对应 §4.4 的规则）：

- R1 空 live → `NoRequirement`；
- R3 hint 指向不存在 / 已归档 → `UnknownSelection`；
- R4 索引只含全批清单：**live = [已批 A（声明 `core/src/**`）, 未批 B（声明 `**`）]，
  写 `core/x.rs`** → 必须 `Pass{A}`（**不误锁**方向：草案 `**` 不得造成误锁）；
- **R4 对偶（G1 回归，本方案初稿漏掉的一条）**：**live = [未批 A（声明 `core/src/**`）,
  已批 B（声明 `cli/src/**`）]，写 `core/x.rs`** → 必须**拦**（**不漏拦**方向：
  不得因 B 已批而放行）。缺这条时，重构 `judge` 能悄悄打破 G1 而测试全绿；
- R6 `|H| > 1` 且全批 → `Pass{A,B}`（不报歧义，§4.3.2 回归）；
- R7 live==1 且路径无声明 → 候选=唯一 live，**未批则拦、已批则放行**（G4 回归）；
- R8 live>1 且无 hint 且 `H=∅` → `Ambiguous`；
- R9 hint 与 H 不相交 → `SelectionMismatch`（**hint 不是绕过口**，§4.3.2 回归）；
- R10 hint 存在且 `H=∅` → 候选 = `{hint}`；
- R11 候选中部分未批 → 只点名未批的那几份，已批的不出现在 `reqs` 里；
- R13 `mode: all` → 候选恒为 live 全体；
- R14 分支 hint 只在 `H=∅` 且 live>1 时生效，且同样受 R9 约束；
- R5 exempt 路径（`.gates/**`、`target/**`）被剥出后不参与反查；
- **R15 内容冻结覆盖全部非 `done` 清单**：构造 2 份已批清单，只改**与候选集无关**的那一份
  → 仍须 `SumMismatch`（G7 的可执行版；防止被实现成"只查候选集"）；
- 文案三张牌：每种 `BlockKind` 的 message 都断言含候选清单 ID + 三条出路关键字
  （G6）。

**枚举覆盖门槛**（沿用 AC 方案 §6.1 的做法，不用覆盖率工具 —— 本项目无覆盖率测量手段）：

断言每个变体至少被一个 case 命中。**新增 kind 而忘了写测试时该用例必红。**

## 10. 附录 A：被否决方案明细

**甲（全体 fail-closed）的失效演示**：场景 B 修复后必须 exit 0（G2）。若采纳甲，
REQ-002 处于 `draft`（人正在写清单，还没送审）时，AI 连 REQ-001 的一行修复都写不了。
而"有人在起草新需求"恰恰是并行开发最常见的常态。甲唯一可用的场景是
**单人串行仓库**——那里本就不该有多份 live 清单（G1 前提 S1-a 恰好成立）。

**戊（会话锁）的自解性**：`.gates/active` 位于 `.gates/**`，而 `touch.exempt` 默认集
第一项就是 `.gates/**`（理由：AI 必须能改自己的需求文档，否则门禁自锁）。
于是"AI 可以自己把锁指向已批清单" —— 这就是 §4.2 里「hint 不能是覆盖式」的同款论证。

**己（写严 / 提交宽）的对账难题**：若 L2/L3 走并集、L1 走单条精确判定，那么
**任何一次提交都可以绕过 L1 的严格性**（把改动拆成"声明已覆盖"的样子即可）。
AC 方案 §3.6 对同类问题的判词是「模板与命令的一致性必须被机械校验」；
而"写严提交宽"要求两侧配置永远同步，这件事**无法被机械校验**（它跨机器、跨配置）。
本项目的核心不变式是"唯一强制点"，不在一个地方设两个强度不同的口径。
