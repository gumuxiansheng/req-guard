# 需求编号防冲突命名规范

> **状态**：规范主体即刻生效——现有工具实现已直接接受本文格式（约束溯源见 §3，无需改代码）；
> 工具侧支撑**已落地（2026-09-19）**：§8 P1（`ids --check`）与 P3（`create --id` lint）实现并实测，
> P2 依赖使用方在 CI / pre-push 调用 `ids --check`（硬伤退出码 1 即拦截）。
> 制定：2026-09-19。适用对象：一切在 `.gates/requirements/` 下创建需求清单的角色（人与 AI）。

## 1. 结论（先行）

**推荐格式：`REQ-<owner>-<YYYYMMDD>-<rrrr>`**，示例 `REQ-kd-20260919-A7F3`。

| 段 | 取值约定 | 承担的职责 |
| --- | --- | --- |
| `owner` | 2–4 位，**字母开头**的小写作者缩写（花名册登记，全团队唯一，如 `kd`） | 把唯一性冲突域从"全团队"切到"个人 × 单日" |
| `YYYYMMDD` | 创建当日日期（本地时区） | 人类溯源 + 按时间聚合归档；**不承担唯一性** |
| `rrrr` | 4 位 Crockford Base32 大写随机（字符集 `0-9A-HJKM-NP-TV-Z`，共 32^4 ≈ 105 万组合） | 兜底熵，消除"同人同日"的残余碰撞 |

按场景分档（详见 §6）：

- **单人 / 需求序贯**：维持现状自动编号 `REQ-001`（`req-guard new` 不传 `--id`）。
- **小团队（2–5 人）低频并行**：`REQ-<owner>-<NNN>`，如 `REQ-kd-007`（各人自管序号）。
- **中大型 / 多分支并行（默认档）**：`REQ-<owner>-<YYYYMMDD>-<rrrr>`。
- **monorepo 多产品线**：再加模块段，`REQ-<mod>-<owner>-<YYYYMMDD>-<rrrr>`。

## 2. 问题与根因

### 2.1 冲突的三种形态（均有代码依据）

1. **分布式抢号**。`req-guard new` 不传 id 时的防重是**本地文件系统级**的：
   `core/src/requirement.rs` 的 `create()` 仅检查目标路径 `exists()`，而 `next_id()`
   只扫描**本地工作副本**目录取最大编号。两个成员在各自分支各自创建，都会拿到 `REQ-003`：
   - 若派生的 slug 相同 → 合并时内容冲突（可见，尚可救）；
   - 若 slug 不同（`REQ-003-login.md` 与 `REQ-003-pay.md`）→ git **零冲突静默共存**。
     此时 `list()` 产出两条 id 相同的需求，`find()` 按文件名字典序任取其一——
     审批、评论、拦截判定都可能落到错误的文件上，**门禁语义失真**。这是最坏形态。

2. **污染自动编号**。`next_id()` 对 `REQ-` 之后的**连续数字前缀**做解析并参与 max。
   若有人采用日期开头 id（如 `REQ-20260919-xxx`），目录里的"最大编号"会被顶到
   8 位，此后自动编号直接跳变成 `REQ-20260920` 一类的 9 位串，序号语义被永久破坏。

3. **前缀歧义**。`find()` 用 `<id>.md` 或 `<id>-` 前缀匹配文件名。引用需求时把 id
   截短（例如拿 `REQ-kd` 当 id）会误命中同前缀的其它文件。

### 2.2 根因一句话

**中心化序号 + 无协调并行 = 分配即冲突。** 工具只能防"同目录重名"，防不了
"分布式抢号"；唯一性必须由**命名空间分割**（owner 段）加**不可协调的熵**（随机段）
在命名层解决，而不是靠事后合并救援。

## 3. 设计约束（从实现导出，硬性）

| 编号 | 约束 | 溯源（文件名 + 符号名） |
| --- | --- | --- |
| C1 | id 仅可含 ASCII 字母/数字/`-`/`_`；中文、空格、点号一律不可 | `core/src/requirement.rs` `normalize_id()` |
| C2 | `REQ-` 后第一段**必须字母开头**：紧跟纯数字会被 `next_id()` 解析进自动编号 | `core/src/requirement.rs` `next_id()` |
| C3 | 大小写只作写法约定、不作区分依据（Windows NTFS / macOS APFS 默认大小写不敏感）；owner 固定小写、随机段固定大写，禁止仅大小写不同的两个 id | 文件系统行为 |
| C4 | id 全长 ≤ 32 字符（评论文件还要追加 `.comments.md`，兼顾 Windows 短路径环境） | `core/src/comment.rs` `comments_path()` |
| C5 | id 是**永久主键**：GATE:HEAD、评论锚点、审计台账（`audit_ledger`）均引用 id → 不重命名、不复用、归档不复号 | `core/src/gate.rs` / `core/src/comment.rs` |
| C6 | 文件名只承担"唯一 + 溯源"；**状态语义一律放文件内容**（GATE:STEP / GATE:HEAD），禁止把状态、日期以外的人类语义写进文件名，避免改名导致 `find()` 失配 | `core/src/requirement.rs` `find()` / `list()` |
| C7 | 引用 id 必须全文，禁止截短（防 `find()` 前缀歧义，见 §2.1-3） | 同上 |

> 推荐格式逐条满足：字母开头的 owner（C1/C2）、大小写写法固定（C3）、
> 全长 20 字符（C4）、id 与状态解耦（C6）、定长结构使合规 id 之间不可能出现
> "`A` 是 `A-x…` 前缀"关系（C7 的结构性保障）。

## 4. 候选方案对比

| 方案 | 示例 | 唯一性 | 可读性 | 可追溯性 | 排序/聚合 | 与自动编号共存 | 跨平台字符 | 协调成本 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A 中心化序号（现状） | `REQ-001` | 强，但依赖"先合并再建"的中心化节奏，并行即抢号 | ★★★★★ | ★（无谁/何时） | 全局字典序，优 | 共存（本身即数字型） | 优 | **高**（抢号） |
| B 模块/分支前缀 + 序号 | `REQ-PAY-001` | 域内仍靠序号，前缀只降频不归零 | ★★★★（有业务域） | ★★（知域不知谁/何时） | 域内优 | 共存 | 优 | 中（前缀注册表 + 域内抢号） |
| C 作者前缀 + 序号 | `REQ-kd-001` | 个人域内自增，跨人天然不撞 | ★★★★ | ★★★（知谁） | 弱（全局不可排序） | 共存 | 优 | 低（花名册一次性） |
| D 日期时间戳 | `REQ-20260919-1530` | **同分钟多人碰撞**；且数字开头**污染自动编号**（§2.1-2） | ★★★ | ★★（知何时） | 全局时间序，强 | **冲突** | 优 | 零 |
| E 纯短随机 | `REQ-7K3Q9` | 概率唯一（生日界），无协调 | ★（无法口头沟通、易抄错） | ☆（零语义） | 无序 | 共存 | 需去混淆字符集 | 零 |
| **F 混合（推荐）** | `REQ-kd-20260919-A7F3` | owner 分域 + 日期收窄 + 随机兜底，碰撞概率≈零 | ★★★★（三段各司其职） | ★★★★★（谁 + 何时） | owner 内时间序 | 共存（字母开头） | 优 | 低 |

### 4.1 逐方案关键评析

- **A（现状）**：单人/序贯开发完全够用，也是 `req-guard new` 的默认行为；一旦
  多人多分支并行，"分配即冲突"不可根治，只能靠纪律（先 pull 再建号）缓解，而纪律
  迟早失守。**保留为单人档，不作并行档。**
- **B（模块/分支前缀）**：模块前缀在 monorepo 场景有真实价值（见 §6 变体）；
  但**分支前缀应否决**——分支是过程概念，需求是资产概念：需求合并后分支消亡，
  id 却要永久引用审计台账与评论锚点，把永久主键绑在临时过程名上是溯源倒挂；
  且"一分支多需求、一需求跨分支"时映射直接破碎。
- **C（作者+序号）**：可读与协调成本的最优平衡，适合小团队；缺陷是无时间信息、
  全局不可排序，且序号膨胀后归档清理必须打开文件看内容。
- **D（日期时间戳）**：看起来"天然唯一"，实则同分钟多人仍会碰撞，且踩中 C2
  硬约束——数字开头污染 `next_id()`。作为独立方案否决，但其"日期段"被 F 吸收。
- **E（纯随机）**：唯一性与零协调最优，但可读性、可追溯性、口头沟通全面崩溃；
  需求 id 是要在会议、评论、台账里被人类反复引用的，纯随机不符合定位。
  其"去混淆随机段"被 F 吸收。
- **F（混合）**：三段各承担一个正交职责（分域 / 溯源 / 熵），是唯一在三个维度
  上都不存在硬伤的方案；代价是 id 变长（20 字符），在 C4 限额内完全可接受。

## 5. 推荐格式详解

### 5.1 解剖与唯一性论证

```
REQ - kd - 20260919 - A7F3
 │     │       │       └─ 4 位 Crockford Base32 随机（兜底熵）
 │     │       └─ 创建日期 YYYYMMDD（溯源，不承担唯一性）
 │     └─ 作者缩写（花名册唯一，把冲突域切到"个人×单日"）
 └─ 固定前缀（需求清单标识）
```

- 冲突需要**同时满足**：同一 owner × 同一日期 × 相同 4 位随机段。
- 同 owner 同日创建 n 条时的碰撞概率 ≈ n(n−1) / 2^21：
  n=10 时 ≈ 4.3×10⁻⁵，n=50 时 ≈ 1.2×10⁻³。
- 跨 owner 碰撞需两人缩写相同，由花名册登记排除。
- **诚实的边界**：随机只是把概率压到可忽略，不是归零；若碰撞且双方 slug 不同，
  仍会出现 §2.1-1 的静默双 id。因此唯一性闭环 = 概率压低（命名）+ **检测兜底**
  （§7 处置流程与 §8 P1 查重）。这与项目一贯的"脚本真解析、不赌文案匹配"哲学一致。

### 5.2 生成方法（零依赖）

Git Bash / Linux / macOS：

```sh
id="REQ-<owner>-$(date +%Y%m%d)-$(LC_ALL=C tr -dc '0-9A-HJKM-NP-TV-Z' </dev/urandom | head -c 4)"
req-guard new "$id" -t "需求标题"
```

PowerShell：

```powershell
$alphabet = '0123456789ABCDEFGHJKMNPQRSTVWXYZ'
$rrrr = -join (1..4 | ForEach-Object { $alphabet[(Get-Random -Maximum 32)] })
req-guard new "REQ-<owner>-$(Get-Date -Format yyyyMMdd)-$rrrr" -t "需求标题"
```

随机字符集取 Crockford Base32（去掉 `I L O U`），与 `0/1` 易混的 `I/L`、与 `O`
易混的字符全部排除，口头转述与手抄不失真；正则字符类写作 `[0-9A-HJKM-NP-TV-Z]`。

### 5.3 合规示例与违规示例

| 示例 | 判定 | 原因 |
| --- | --- | --- |
| `REQ-kd-20260919-A7F3` | ✅ | 标准默认档 |
| `REQ-pay-kd-20260919-A7F3` | ✅ | monorepo 档（`pay` 为模块段） |
| `REQ-kd-007` | ✅ | 小团队档（§6） |
| `REQ-20260919-A7F3` | ❌ | C2：数字开头污染自动编号 |
| `REQ-寇-20260919-A7F3` | ❌ | C1：非 ASCII |
| `REQ-KD-20260919-a7f3` | ❌ | C3：大小写写法不合规（写法固定，非区分手段） |
| `REQ-kd-20260919-A7F3-v2` | ❌ | C5：id 不可变；修订走内容与审批流，不改名 |

## 6. 场景决策表

| 场景 | 采用格式 | 理由 |
| --- | --- | --- |
| 单人仓库 / 需求序贯产生 | `REQ-NNN`（`req-guard new` 自动编号） | 简单优先；无并行即无抢号 |
| 小团队（2–5 人）低频并行 | `REQ-<owner>-<NNN>` | 跨人天然不撞；比混合格式短；无需掷随机 |
| 中大型 / 多分支 / 高频并行 | `REQ-<owner>-<YYYYMMDD>-<rrrr>`（**默认档**） | 全维度无硬伤，见 §4 |
| monorepo 多产品线 | `REQ-<mod>-<owner>-<YYYYMMDD>-<rrrr>` | 模块段收窄检索域；`mod` 同样字母开头、花名册式登记 |
| 临时草稿 / 未过审需求 | 与正式需求同格式 | C6：状态放内容（GATE:HEAD），不进文件名 |

迁移原则：**存量 `REQ-NNN` 一律不迁移、不改名、不复号**（C5，id 是永久主键）；
本规范只约束增量。小团队档若日后升级为默认档，旧 `REQ-<owner>-<NNN>` 同样原地保留。

## 7. 冲突处置与治理

1. **创建时撞车**：`create()` 报"需求清单已存在"→ 更换随机段重新生成（换 4 位
   重掷即可，概率意义下必成）；禁止手工改老文件让路。
2. **合并后发现双 id**（slug 不同导致 git 零冲突静默共存）：以**先合入者为准**，
   后合入者新建合规 id 迁移内容并作废旧文件（`git rm` + 台账记录作废）；禁止
   双文件并存进入下一个审批循环。
3. **花名册治理**：owner 段全团队登记（本文档附表或 `docs/` 独立页），一人一缩写，
   离职缩写封存不复用（C5 同理）；模块段（若启用）同表登记。
4. **引用纪律**：评论、台账、commit message 引用 id 一律全文（C7）。
5. **合并后查重**：每次合并涉及 `.gates/requirements/` 的 PR 后跑一次查重
   （§8 P1 落地前，可用脚本按 GATE:HEAD 的 `id=` token 分组数数，见 §8 检测语义）。

| P3 ✅ 已落地（2026-09-19） | `create --id` lint 提示 | `core/src/idcheck.rs` 的 `lint_id()`：命中 C2 数字开头、C4 超长（>32 字符）、C3 大小写写法、非推荐档形状时打印 stderr 提示，**不阻断**，保持对存量 `REQ-NNN` 与自由 id（`login-refactor`）的向后兼容；纯数字与自动编号不走 lint |
