# 校验说明

> 回答三个问题：**包有没有被篡改**（校验和）、**版本对不对**（版本自证）、**能不能自己复现**（源码构建）。

---

## 1. 校验和文件

发布包根目录的 `SHA256SUMS.txt` 覆盖包内**所有**文件（二进制、文档、脚本、模板），格式与
`sha256sum` 标准输出一致：

```
<64位十六进制摘要>  <相对路径>
```

路径一律使用 `/` 分隔、相对于**包根目录**，因此在任何系统上的校验命令都一样。

### 1.1 一键校验（推荐）

```bash
bash scripts/verify-checksums.sh          # Linux / macOS / Git Bash
```

```powershell
powershell -ExecutionPolicy Bypass -File scripts\verify-checksums.ps1
```

脚本逐个文件比对并在结尾汇总 `OK / FAILED / MISSING` 计数；**任何一个不一致就以退出码 1 结束**，
可直接放进 CI 或分发前的自检流程。

### 1.2 手工校验

**Linux**

```bash
sha256sum -c SHA256SUMS.txt                       # 全量
sha256sum -c SHA256SUMS.txt --ignore-missing      # 只验存在的文件
sha256sum bin/linux-x86_64/req-guard              # 单个文件，肉眼比对
```

**macOS**

```bash
shasum -a 256 -c SHA256SUMS.txt
```

**Windows PowerShell**

```powershell
Get-FileHash -Algorithm SHA256 bin\windows-x86_64\req-guard.exe
# 与 SHA256SUMS.txt 中 "bin/windows-x86_64/req-guard.exe" 行的摘要比对

# 全量自动比对：
.\scripts\verify-checksums.ps1
```

**Windows CMD**

```cmd
certutil -hashfile bin\windows-x86_64\req-guard.exe SHA256
```

### 1.3 校验的意义与边界

| 能防 | 不能防 |
| --- | --- |
| 下载中断 / 磁盘位翻转导致的损坏 | 发布者本人作恶 |
| 镜像站被替换成旧版或夹带物 | 校验文件本身被一起替换 |

`SHA256SUMS.txt` 与二进制**同包分发**，因此它只能证明"完整性"，不能证明"来源可信"。
要做到来源可信需要签名（见 §4）。

## 2. 版本自证

每个二进制都在编译期写入了版本号，不依赖任何外部文件：

```bash
req-guard -V        # → req-guard {{VERSION}}
```

判定标准：

- 输出必须**等于** [`README.md`](../README.md) 表格里的版本与 `VERSION` 文件中的 `version` 字段；
- 三者（`-V` 输出 / `VERSION` / 文件名中的 `v{{VERSION}}`）任一不符，说明你手上的包被混装或替换，请重新下载。

`VERSION` 文件同时记录了构建日期、源码提交号、工具链与每个二进制对应的 target，
用于追溯"这个二进制是哪次提交、哪条命令产出的"。

## 3. 从源码复现

```bash
git clone <仓库地址> && cd req-guard
git checkout {{GIT_COMMIT}}                  # 与 VERSION 文件中的提交号对齐
cargo build --release -p req-guard                          # CLI
cargo build --release -p req-guard --features tui           # CLI + TUI
sha256sum target/release/req-guard
```

**关于"可复现构建"的诚实说明**：Rust 目前**不保证 bit-for-bit 可复现**——
不同工具链小版本、不同绝对路径、不同构建目录都会让二进制字节不同，摘要自然不同。
因此复现比对的目标是：

| 可比对项 | 是否可复现 |
| --- | --- |
| `req-guard -V` 版本号 | ✅ 完全一致 |
| `req-guard --help` 输出 | ✅ 完全一致 |
| 命令行为与退出码 | ✅ 完全一致 |
| 二进制字节 / SHA-256 | ❌ 不保证（受工具链与路径影响） |

也就是说：**源码构建能验证"行为一致"，不能验证"字节一致"**。
若需字节级复现，需在受控容器（固定镜像、固定路径、固定 toolchain、去除嵌入式时间戳）中构建。

## 4. 签名（当前状态）

| 项 | 状态 |
| --- | --- |
| SHA-256 校验清单 | ✅ 已提供（`SHA256SUMS.txt` + 两个平台校验脚本） |
| GPG / Sigstore 签名 | ❌ **未提供**（本版本未做） |
| 分平台归档校验 | ✅ 已提供（归档文件名与包内一致，见 README §2） |

未做签名的原因：发布链路（CNB Release 附件上传）尚未接入签名密钥管理。
在此之前，请通过**可信渠道**获取发布包（官方仓库 Release 页 / 内部制品库），
并优先使用 `SHA256SUMS.txt` 做完整性校验。

若你的组织要求签名，可在拿到包后自行补签：

```bash
gpg --detach-sign --armor SHA256SUMS.txt      # 产出 SHA256SUMS.txt.asc
gpg --verify SHA256SUMS.txt.asc SHA256SUMS.txt
```

## 5. 分发方自检清单

把包挂出去之前，建议按顺序跑一遍：

```bash
bash scripts/verify-checksums.sh     # 1. 包内完整性
req-guard -V                          # 2. 版本自证（装完后）
bash scripts/selfcheck.sh             # 3. 放行 / 拦截两条路径可用
```

| # | 检查 | 期望 |
| --- | --- | --- |
| 1 | 校验和 | 全部 OK，0 FAILED |
| 2 | 版本号 | 与 `VERSION` 一致 |
| 3 | 自检脚本 | 放行与拦截两个场景都 PASS |
| 4 | 平台数量 | `bin/` 下目录与本包声明的平台矩阵一致 |
| 5 | 文档齐全 | `docs/` 4 份 + `README.md` + `CHANGELOG.md` + `VERSION` |
