## 1. 它到底管什么

一句话：**AI 在写第一行代码之前，必须先交出「需求分解 → 技术方案 → 测试计划」三份清单，并逐份被人类批准；否则物理上写不了文件。**

req-guard 不检查代码质量（那是 sql-guard / java-guard 的事），它只回答一个问题：
**"这次让不让你写？"**

### 1.1 三段状态机

```
        ┌─────────────┐  approve   ┌─────────────┐
        │ decomposition│ ────────► │  solution   │ ──► testplan ──► 解锁
        └─────────────┘            └─────────────┘
              reject ↓                   reject ↓
              (打回 + 写阻塞评论，回到该段重填)
```

- 步骤状态：`pending` → `approved` / `rejected`
- 需求状态：`draft` → `approved`（三段全批）／ `rejected`（任一段被打回且未重批）
- **强制顺序**：`strict_order: true` 时，前一段未 `approved`，后一段不允许审批
- **解锁条件**：三段全部 `approved` **且** 没有未 `resolve` 的阻塞性评论

### 1.2 三层拦截（L1 提醒 → L3 墙）

| 层 | 触发点 | 行为 | 强度 |
| --- | --- | --- | --- |
| **L1** | AI 工具 `PreToolUse`（Write/Edit/MultiEdit/NotebookEdit） | 直接拒绝写文件并给出原因 | 强，但改工具配置即可绕 |
| **L2** | git `pre-commit` | 提交前校验，未过审阻止 commit | 强，**fail-closed**（脚本缺失 = 拒绝） |
| **L3** | CI `req-guard check` + 分支保护 | 服务端判定，红了不能合并 | 最强，抵消本机 `--no-verify` |

> **fail-closed 是刻意设计**：门禁是安全机制，`req-guard` 不在 PATH、脚本丢失、脚本没有执行位
> 都会导致**拒绝**而不是放行。宁可挡住一次正常提交，也不能漏放一次未经审核的写入。
> （这与 sql-guard/java-guard 的 fail-open 取向相反，别混用经验。）

## 2. 命令总览

```
init                       初始化 .gates/ 门禁（脚本 + AI 工具 hook + pre-commit）
create   -t <标题>         创建需求清单（REQ-001…）
approve  <需求ID> --step <步骤> --reviewer <姓名> [--comment <意见>]
reject   <需求ID> --step <步骤> --reviewer <姓名> [--comment <意见>]
comment  <需求ID> --author <姓名> --text <意见> [--step <步骤>]
         [--quote <原文片段>] [--blocking] [--reply <评论ID>]
resolve  <需求ID> <评论ID> --author <姓名>    关闭评论（AI 禁止调用）
status   [<需求ID>]        查看三段状态与是否解锁
list                       列出全部需求
comments <需求ID> [--refresh-anchors]         查看评论 / 重算行号锚点
check                      手动拦截判定（退出码 0 放行 / 1 拦截）
install  [--tool <a,b>] [--verify]           安装或修复拦截；--verify 只校验就位情况
bypass   --reason <原因> [--ttl 60]           有时效的应急绕过（强制审计）
audit-digest               审计日志 SHA-256 摘要写入 .gates/audit/DIGEST
token issue [--ttl 60]     签发审批令牌（方案 B，原文仅打印一次）
token status               查看令牌启用状态与到期
token revoke               撤销并禁用审批令牌
ui       [--gui | --tui]   打开门禁管理台（需 TUI/GUI 变体）
hook-check                 PreToolUse hook 内部命令（由拦截脚本调用，通常无需手工执行）
```

通用选项：

| 选项 | 说明 |
| --- | --- |
| `-p, --path <项目根>` | 指定项目根目录，默认当前目录。**必须写在子命令之后**：`req-guard status -p ../other`；写成 `req-guard -p ../other status` 会被当成未知命令（退出码 2） |
| `-V, --version` | 输出版本号 |
| `-h, --help` | 输出帮助 |
| `--token <令牌>` | 携带审批令牌（方案 B）；也可用环境变量 `REQ_GUARD_TOKEN` |
| `--oob` | 声明本次审批为带外渠道（方案 C）；也可用 `REQ_GUARD_OOB` 或 `req-guard oob <命令>` |

环境变量：

| 变量 | 作用 |
| --- | --- |
| `REQ_GUARD_REVIEWER` | 缺省审核人（`--reviewer` 未给时使用） |
| `REQ_GUARD_AI_CTX` | AI 会话标记，置 1 后 `approve/reject/resolve/bypass` 全部拒绝（**审批锁**） |
| `REQ_GUARD_TOKEN` | 审批令牌（方案 B） |
| `REQ_GUARD_OOB` | 带外审批声明（方案 C） |
| `REQ_GUARD_OOB_ONLY` | 置 1 时**只接受**带外审批（禁止交互审批） |

## 3. 命令详解

### 3.1 `init` —— 接入门禁

```bash
req-guard init            # 幂等，可重复执行修复缺失项
```

产出（均随仓库提交，clone 即生效）：

```
.gates/
├── req-guard.yaml                  门禁声明（可改 strict_order / enforce.*）
├── README.md                       给审核人的 30 秒说明
├── requirements/                   需求清单 REQ-00N.md + REQ-00N.comments.md
├── hooks/req-guard-check.{sh,ps1}  拦截脚本（L1/L2 判定唯一真相）
├── hooks/req-guard-deny.{sh,ps1}   deny 包装（Codex/Cursor 用 exit 2 表达拦截）
├── ci/req-guard-ci.yml             L3 流水线样例
└── audit/                          审计日志与 DIGEST（不入库）
```

同时注入 AI 工具配置（按实际检测到与否）：`.claude/settings.json`、`.codebuddy/settings.json`、
Codex / Cursor 的原生 hook，并为 Claude Code / CodeBuddy 注入 `REQ_GUARD_AI_CTX=1`。
已存在的配置文件会被**合并**而不是覆盖，pre-commit 也是追加而非替换。

### 3.2 `create` —— 新建需求清单

```bash
req-guard create -t "用户登录改造"
# ✅ 已创建需求清单：REQ-001 用户登录改造
```

编号自增（`REQ-001`、`REQ-002`…），模板自带三段骨架与检查项，由 AI 填写正文。

### 3.3 `status` / `list` —— 看状态

```bash
req-guard status REQ-001
# 需求 REQ-001 用户登录改造
#   状态 : draft
#   步骤 :
#     [ ] decomposition pending
#     [ ] solution pending
#     [ ] testplan pending
#   判定 : 未解锁，AI 不得编写/修改源码（门禁拦截）

req-guard list            # 全部需求（摘要）
```

### 3.4 `approve` / `reject` —— 审核（人类动作）

```bash
req-guard approve REQ-001 --step decomposition --reviewer 寇工
req-guard approve REQ-001 --step solution      --reviewer 寇工 --comment "回滚方案 OK"
req-guard approve REQ-001 --step testplan      --reviewer 寇工

req-guard reject REQ-001 --step solution --reviewer 寇工 --comment "缺回滚方案，重做"
# 打回会写入一条**阻塞性**评论，未 resolve 前持续拦截
```

规则：

- `--step` 取值 `decomposition` / `solution` / `testplan`
- `strict_order: true` 时跳步审批会被拒绝（先把前段批完）
- **AI 不能审批**：处于 `REQ_GUARD_AI_CTX=1` 的会话里，`approve/reject` 直接被拒
- 审核人写进 GATE 行与审计日志，事后可追溯"谁、何时、批了哪一段"

### 3.5 `comment` / `resolve` —— 评论（不改正文）

```bash
# 普通评论
req-guard comment REQ-001 --step solution --author 寇工 --text "回滚方案需补充 DB 迁移回退"

# 锚定到原文 + 阻塞（未 resolve 前拦截编码）
req-guard comment REQ-001 --step solution --author 寇工 --quote "回滚方案" --blocking --text "必须给出回退步骤"

# AI 只能 reply，不能新开、不能 resolve
req-guard comment REQ-001 --author ai --reply C001 --text "已补充迁移回退步骤"

# 审核人关闭
req-guard resolve REQ-001 C001 --author 寇工
```

关键约束：

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 审核人（人类） | 新开评论、加 `--blocking`、resolve | — |
| AI | 只能 `--reply <评论ID>` | 新开评论（被拒）、resolve（被拒） |

- 评论存在独立文件 `REQ-001.comments.md` —— 与清单正文分离，防止"改正文时顺手删评论"
- `--quote` 记录原文片段 + 行号锚点；正文改动后可用 `req-guard comments REQ-001 --refresh-anchors` 重算锚点
- **未 resolve 的 `--blocking` 评论 = 拦截**，即便三段全批也不放行

### 3.6 `check` —— 判定（CI 用得最多）

```bash
req-guard check
# 退出码 0 = 放行；1 = 拦截
```

判定顺序：清单是否存在 → 三段是否全批 → 是否有未解决的阻塞评论 → 绕过令牌是否在有效期内。
**唯一真相是 `.gates/hooks/req-guard-check.{sh,ps1}` 的退出码，`req-guard check` 只做透传**，
因此"命令行手工 check"与"AI 工具被拦"永远是同一套判定。

### 3.7 `install` —— 修复 / 校验就位

```bash
req-guard install                    # 安装或修复（覆盖脚本、补 hook、补 pre-commit）
req-guard install --tool claude,codebuddy   # 只为指定工具注入
req-guard install --verify           # **只校验不修改**；有缺口 → 退出码 1
```

`--verify` 检查五项：核心资产（`req-guard.yaml` / `requirements/`）、拦截脚本存在、
脚本**执行位**、各 AI 工具 hook 配置、pre-commit 注入。
CI 里务必加这一条——它专门抓"配置写了但没生效"。

### 3.8 `bypass` —— 应急绕过（有痕、有时效）

```bash
req-guard bypass --reason "线上热修，事后补审" --ttl 60
```

- 必须填 `--reason`；默认 TTL 60 分钟（可在 `req-guard.yaml` 的 `bypass.default_ttl_minutes` 改）
- 绕过**不覆盖评论证据保护**：有未 resolve 的阻塞评论时，绕过也放不了行
- 每次绕过写入审计日志与入库台账，事后可查

### 3.9 `audit-digest` —— 审计摘要

```bash
req-guard audit-digest
# ✅ 审计摘要已写入：.gates/audit/DIGEST
#    sha256 : 75393de7…
```

把本机 `gate-audit.log` 的 SHA-256 落盘为 `DIGEST` 并随改动提交；
PR 复核时比对本机日志摘要即可发现"删日志/改日志"这类篡改。

### 3.10 `token` —— 审批令牌（方案 B）

```bash
req-guard token issue --ttl 60     # 签发，原文**仅打印一次**，人类带外保存
req-guard token status             # 查看启用状态与到期
req-guard token revoke             # 撤销并禁用
```

启用令牌后，所有审批动作必须携带 `--token <令牌>`（或 `REQ_GUARD_TOKEN`）。
AI 拿不到令牌 → 无法自批，比方案 A 的软标记更硬。

### 3.11 `ui` —— 门禁管理台

```bash
req-guard ui            # 自动探测：桌面环境 → GUI，SSH / 无图形栈 → TUI
req-guard ui --tui      # 强制终端界面
req-guard ui --gui      # 强制桌面界面（GUI 启动失败会自动回退 TUI）
```

仅 TUI / GUI 变体支持（CLI 变体执行会提示需用哪个变体）。

### 3.12 `hook-check` —— 内部命令

由拦截脚本调用，从 stdin 读 AI 工具的 PreToolUse JSON，做证据保护判定。
**Rust 真解析**（不是正则抠字段），因此路径写成 `.gates\u002f…comments.md` 这类 Unicode 转义
也能正确识别，不会被绕过。`req-guard` 不在 PATH 时脚本退回正则粗判（保底但不完备）。

## 4. 典型工作流

### 4.1 审核人视角（人类）

```bash
req-guard list                                     # 有哪些需求
req-guard status REQ-001                           # 看三段进度
req-guard comments REQ-001                         # 看别人的意见
req-guard approve REQ-001 --step decomposition --reviewer 寇工
# …逐段批完
req-guard check                                    # 确认解锁
```

界面派可用 `req-guard ui`：左栏选需求、右栏展开段落看只读正文、点"批准/打回"；
批准或打回后光标自动前进到下一个未通过段。

### 4.2 AI 视角

1. 人类 `create` 出需求清单
2. AI **填写** `.gates/requirements/REQ-001.md` 的三段正文（整篇 Write 允许，不等批准，否则自己把自己锁死）
3. AI 写代码？不行——三段未批完，Write/Edit 被 L1 直接拒绝
4. 人类逐段批准 → `check` 退出码 0 → AI 才被允许写源码
5. AI 对审核意见只能 `--reply`，不能关评论

### 4.3 一次完整会话示例

```bash
req-guard init
req-guard create -t "支付回调幂等改造"        # REQ-002
# （AI 填三段正文）
req-guard check                              # exit 1 —— 被拦，正确
req-guard approve REQ-002 --step decomposition --reviewer 寇工
req-guard approve REQ-002 --step solution      --reviewer 寇工
req-guard comment REQ-002 --step testplan --author 寇工 --blocking --text "需补充并发幂等用例"
req-guard check                              # exit 1 —— 阻塞评论未处理
# （AI reply 说明已补）
req-guard resolve REQ-002 C001 --author 寇工
req-guard approve REQ-002 --step testplan      --reviewer 寇工
req-guard check                              # exit 0 —— 解锁
req-guard audit-digest                       # 摘要入库，随 PR 提交
```

## 5. 界面操作

### 5.1 TUI（终端管理台）

| 键 | 动作 |
| --- | --- |
| `↑` `↓` | 选择需求 |
| `←` `→` / `Tab` | 切换段落 |
| `a` | 批准当前段 |
| `r` | 打回（原因必填，落为阻塞评论） |
| `n` | 新建需求 |
| `g` | 门禁检查 |
| `b` | 应急绕过 |
| `L` | 审计日志 |
| `R` | 刷新 |
| `?` | 帮助 |
| `q` | 退出 |

### 5.2 GUI（桌面管理台，Windows）

三面板布局：

- **左**：需求列表（红=被卡 / 绿=已解锁）
- **右**：三段折叠清单（状态、审核人、只读正文、批准/打回按钮）
- **底部**：创建 / 刷新 / 检查 / 绕过 / 审计，可切换项目根目录

> 界面只做**管理台**：状态读写全部走与 CLI 相同的 `core`，不会出现"界面放行、CLI 拦截"。
> 清单正文在界面中**只读**——正文由 AI/编辑器维护，界面只负责审核决策。

## 6. 配置（`.gates/req-guard.yaml`）

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 总开关；false 时判定恒放行（放行也会留痕） |
| `strict_order` | `true` | 强制按 分解→方案→测试计划 顺序审批 |
| `enforce.ai_tool_hook` | `true` | L1：AI 工具 PreToolUse 拦截 |
| `enforce.pre_commit` | `true` | L2：git pre-commit 拦截 |
| `enforce.ci` | `true` | L3：CI 需调用 `req-guard check` 并设为必需检查 |
| `blocked_tools` | `Write/Edit/MultiEdit/NotebookEdit` | 被拦截的 AI 写操作 |
| `bypass.enabled` | `true` | 是否允许应急绕过 |
| `bypass.default_ttl_minutes` | `60` | 绕过默认有效期 |
| `bypass.require_reason` | `true` | 绕过必须填原因 |

改完 yaml 建议跑 `req-guard install --verify` 确认没被改坏。

## 7. 退出码

| 退出码 | 含义 | 常见出处 |
| --- | --- | --- |
| `0` | 放行 / 命令成功 | `check`（已解锁）、`approve`、`init` |
| `1` | 拦截 / 参数或前置不满足 | `check`（未过审）、`install --verify`（有缺口）、跳步审批 |
| `2` | deny 包装的拦截语义 | `.gates/hooks/req-guard-deny.{sh,ps1}`（Codex/Cursor） |

CI 里判断"过没过"只看退出码，不要去 grep 中文输出（文案会变）。

## 8. 目录与文件说明

```
.gates/
├── req-guard.yaml                 门禁声明（入库）
├── requirements/
│   ├── REQ-00N.md                 清单正文（入库；GATE 行是判定依据，勿手改）
│   └── REQ-00N.comments.md        评论（入库；AI 只能追加 reply）
├── hooks/req-guard-check.{sh,ps1} 拦截脚本（入库，**必须有执行位**）
├── hooks/req-guard-deny.{sh,ps1}  deny 包装（入库）
├── ci/req-guard-ci.yml            L3 样例（复制进 .github/workflows/）
├── audit/gate-audit.log           本机审计（不入库）
├── audit/DIGEST                   审计摘要（入库，PR 比对用）
└── .bypass/                       绕过令牌（不入库）
```

清单正文中的判定行长这样，**不要手工编辑**：

```
<!-- GATE:HEAD id=REQ-001 status=approved created=… -->
<!-- GATE:STEP name=decomposition label=需求分解 status=approved reviewer=寇工 updated=… -->
```

AI 可以整篇重写正文，但 GATE 行必须与磁盘状态逐行一致，改动即拦截（防 AI 自批）；
片段式编辑（Edit）无法与基线比对，一律禁止。

## 9. 与其他工具的关系

| 工具 | 管什么 |
| --- | --- |
| **req-guard** | 流程门禁：**该不该写**（需求→方案→测试是否经过批准） |
| sql-guard | SQL 质量门禁：写得对不对（DDL/DML 规则、MyBatis Mapper 扫描） |
| java-guard | Java 质量门禁：写得对不对 |
| wan / bug-guard | 家族其他成员 |

配套：`setup-gates` 用片段 `030-reqguard` 装配；dev-scaffold `new` 默认启用，`--no-req-guard` 关闭。
